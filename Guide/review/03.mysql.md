# MySQL 八股评审

对照现行 InnoDB / MySQL 8.0（并标清 5.7 仍常见的差异）看了 `Guide/content/中间件/MySQL` 下 `_index.md` 和 1–6 全部正文。

Buffer Pool 冷热链表、B+ 树最左与覆盖/ICP、RR 幻读三条路径、Redo 与 Binlog 的 2PC 这几块整体能讲。问题集中在把估算当硬上限、范围条件与锁区间写反、以及日志章几乎没接到 crash-safe 参数和复制。

## 结论

先改这三处，面试里不能照背：

1. `LIKE 'abc%'` 还能用联合索引的后续列做定位
2. 非唯一索引等值查询的 Next-Key 区间把 `id` 和 `age` 混在一起
3. 单表 2000 万、树高变 4 就多 33% 磁盘耗时并触发 Swap

## 发现列表

### 错误（说错了）

| 级别 | 章节 | 位置 | 问题 | 改法 |
| --- | --- | --- | --- | --- |
| 阻断 | 索引3 | 遇上范围查询第 2 条 | 写成 `LIKE 'abc%'` 是前缀范围，可以继续利用后续索引。前缀 LIKE 就是当前列上的 range，和 `b > 2` 一样会截断后面的列，不能再用后续列做索引定位。ICP 只能在叶子上过滤，不是继续 seek。 | 改成：`LIKE 'abc%'` 能用当前列走 range；后续列不能用于定位。`LIKE '%abc'` 连当前列都不能 seek。对比留给 `a IN (...)` 那种可拆成多组等值的情况。 |
| 阻断 | 锁 | 行锁的退化第 3 条 | 数据是 `age=20, id=5` 和 `age=30, id=10`，却写成 Next-Key `(10, 20]`。10 是主键，20 是 age，两个列被塞进同一个区间。 | 区间只写二级索引列：命中的 `age=20` 加 Next-Key（前一档, 20]，下一条 `age=30` 加 Gap `(20, 30)`；对应主键 `id=5` 另加 Record Lock。 |
| 阻断 | 索引1 | 后果整节 | 写成树高 3 变 4，最坏多一次 I/O 就让单次查询耗时加 33% 以上；上层索引页内存装不下；Buffer Pool 换页被写成 OS Swap；P95/P99「下跌」字面是延迟变好。点查时前几层通常已在 Buffer Pool，多一层不等于多一次磁盘。 | 删掉 33%、Swap、断崖。改成：多一层是最坏多一次页访问；真正变慢的是叶子页变多、范围扫和回表变贵。2kw 只是行约 1KB、高度 3 的估算。 |
| 重要 | 索引1 | 表的最大长度是？2kw | 标题把估算说成上限。16KB 页的 InnoDB 表空间上限约 64TB，不是 2000 万行。后文又说不一定分表，和标题打架。 | 标题改成「为什么常说单表 2000 万」。第一句写清：这是典型行长、树高约 3 的数量级，不是引擎限制。 |
| 重要 | 架构 | ChangeBuffer 开场 | 「基本等价于唯一索引和普通索引在实现上的区别」。两者还差唯一性检查、加锁方式。Change Buffer 只覆盖非唯一二级索引，且页不在 Buffer Pool 时才缓冲。 | 删掉「基本等价」。改成：普通二级索引页不在内存时，写入可记 Change Buffer，省随机读；唯一索引插入必须当场判重，不能缓冲。 |
| 重要 | 架构 | 两次写「共享表空间」 | 机制（先顺序留底再打散写 `.ibd`）对。落盘位置过时：8.0.20 起 Doublewrite 在独立 `.dblwr` 文件，不再放系统表空间。 | 自救两种停电场景保留。补一句：8.0.20 前在共享表空间，之后是 doublewrite 文件。 |
| 重要 | 索引2 | type：eq_ref / ref | 两者捆成「普通索引等值查询」。`eq_ref` 是 JOIN 里主键或唯一索引一次命中一行；`ref` 才是非唯一索引等值。 | 拆开写。`system`/`const` 补一句：最多一行。 |
| 重要 | 事务 | 读未提交，都不能解决 | 四大问题含丢失修改，锁章又写任何隔离级别都不会出现理论上的丢失修改。InnoDB 的 UPDATE 自带行锁，RU 也不会两个 UPDATE 互覆盖。 | 隔离级别表只对脏读、不可重复读、幻读。丢失修改放到锁章的「先查后改」。 |
| 重要 | 事务 | MVCC 总体规则 | 写成只能看创建 ReadView 前已提交的事务。漏了自己未提交的改动对本事务可见。 | 补：自己写的可见；别人的版本要在 ReadView 创建前已提交，且不在活跃事务列表里。 |
| 重要 | 锁 | 悲观策略 SELECT ... FOR UPDATE | 写成后续想读写的事务都会立刻阻塞。普通 SELECT 是快照读，默认不等 X 锁（SERIALIZABLE 除外）。 | 改成：阻塞其他当前读和写；普通 SELECT 仍走 MVCC。 |
| 重要 | 索引3 | 字段顺序原则（区分度优先） | 和后文三星索引「等值列在前」冲突。区分度最高的列若是范围条件、或查询根本不带最左列，索引用不上。 | 先按查询排：等值 → ORDER BY → SELECT 覆盖。区分度只在同是等值的列之间做次序参考。 |

### 遗漏

| 级别 | 章节 | 位置 | 问题 | 改法 |
| --- | --- | --- | --- | --- |
| 重要 | 日志1 | Redo / Binlog / Undo 区别 | Binlog 只写「逻辑/行级」，三种格式没出现。一面常问 STATEMENT 复制不安全、ROW 体积大、MIXED 怎么折中。 | 补 STATEMENT / ROW / MIXED。默认记一句 8.0 是 ROW。STATEMENT 举 `NOW()`、`LIMIT` 无 ORDER 这种主从不一致。 |
| 重要 | 日志2 | 提交 2PC / 崩溃恢复 | 写了 prepare → binlog → commit，没写两个刷盘参数。没有 `innodb_flush_log_at_trx_commit=1` 且 `sync_binlog=1`，2PC 也不能保证 crash-safe。 | 补双 1：1 是每次提交刷 Redo，1 是每次提交刷 Binlog。并写 2 和 0 各丢什么。 |
| 重要 | 日志1 / 整栏 | Redo 不能用于主从之后 | 解释了为什么不用 Redo 做复制，主从怎么走、延迟从哪来完全没有。 | 补一条链路：主库 dump Binlog → 从库 IO 线程写 relay → SQL 线程回放。延迟先看 SQL 线程是否追上；5.7 默认单线程回放，8.0 有并行复制。 |
| 重要 | 锁 | 行锁的退化之后 | 只写 RR 下 Next-Key 很霸道。RC 几乎不加 Gap（外键、唯一冲突除外），所以 RC 当前读仍可能幻读。这是追问 RR 幻读时的下一句。 | 补一张 RR / RC 对照：RR 当前读 Next-Key；RC 等值命中多半是 Record Lock。 |
| 重要 | 锁 | 锁的类型 / 整章 | 意向锁只出现名字。插入意向锁、死锁检测都没有。 | 意向锁：表上先放 IS/IX，避免查行锁才能加表锁。插入意向锁：多个事务往同一 Gap 插不同位置可以并存。死锁：wait-for 成环立刻回滚代价低的一方，和 `innodb_lock_wait_timeout` 不是一回事。 |
| 重要 | 命令 | JOIN 是否快 | 只写关联字段有没有索引。缺驱动表、Nested Loop，以及 8.0.18 起的 Hash Join。 | 小表驱动大表；被驱动表关联列要有索引。8.0.18+ 等值 JOIN 才可能走 Hash Join，不要只背 NLJ。 |
| 重要 | 索引3 | 联合索引对 ORDER BY / GROUP BY | 只剩一句「叶子按联合索引列顺序排」，什么时候能免 `Using filesort` 没写。这是最左前缀之后最常见的追问。 | 补：`WHERE a=? ORDER BY b` 能顺着索引走；`ORDER BY b, a` 或前缀范围后再排序通常还要 filesort。8.0 起 `GROUP BY` 不再隐式排序。 |

### 可以更好

| 级别 | 章节 | 位置 | 问题 | 改法 |
| --- | --- | --- | --- | --- |
| 建议 | 架构 | Master Thread | 写成核心调度者、负责把缓冲池异步刷到磁盘。5.6 起刷脏主要是 Page Cleaner，Master Thread 不再是刷盘主角。 | 第一句改成：Master Thread 做调度；脏页由 Page Cleaner 刷；Purge 回收 undo。IO Thread 分 read/write 回调，不是只处理写。 |
| 建议 | 架构 | Purge Thread | 「事务被提交后，负责顺手回收」。Purge 要等没有 ReadView 再需要这些 undo 版本，不是 commit 立刻删。 | 改成：提交后旧版本留在 undo，Purge 等到最小活跃视图不再引用才物理删除。 |
| 建议 | 索引2 | key_len | 写成联合索引命中了多少列。它是用到的索引前缀字节数，还要算字符集、NULL 标记、varchar 长度字节。 | 改成：看用了多长前缀，再反推列数。举 utf8mb4 下一列 varchar 怎么加长度。 |
| 建议 | 索引2 | like '%xxx' | 原因写成「可能有很多情况，所以不能用索引」。真正卡住的是前导通配无法 seek。覆盖索引仍可能 `type=index` 扫叶子。 | 改成：`%` 在前不能定位；结果多少是优化器估成本的事。覆盖索引可以只扫二级索引。 |
| 建议 | 事务 | 幻读 | 写成「读两次数据量不一致」。幻读是同一条件再次读到新行，不一定表现成 COUNT 变了。 | 改成：同样的 WHERE 第二次出现了之前没有的行。 |
| 建议 | 索引2 | Index Merge | 写成分别并发扫描两个索引再在内存求并。Index Merge 是优化器把两次索引扫描的结果做 union/intersect，不保证并行。 | 去掉「并发」。写清 OR 常是 union，AND 才可能 intersect。 |
| 建议 | 命令 | 文件标题 / 开篇 | 目录是「命令」，正文 title 是「索引」，内容却是 JOIN。复习时对不上。 | 标题改成 JOIN。开篇补：MySQL 没有 `FULL JOIN` 语法。 |
| 建议 | 命令 | FULL JOIN 用 UNION 模拟 | `UNION` 会去重，可能把本来就重复的行吃掉。 | 改成 `UNION ALL`，或说明去重是额外语义。 |

## 面试高频但几乎没写的

覆盖索引、最左前缀、Gap / Next-Key、RR 下幻读、EXPLAIN 字段，正文里已经有。缺的是这些能接上现有章节的一面题。

### 5.日志 — 有 2PC，缺格式和双 1

prepare / binlog / commit 和崩溃后看 Binlog 是否完整，这条链能讲。一面更常问：Binlog 三种格式差在哪、怎样才 crash-safe。

`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 都是 1，才是「双 1」。只背 2PC 流程图，问参数会对不上。

Undo 现在只够支撑 MVCC 版本链。Purge、history list 可以各补一句，不要写成 DBA 课。

### 主从复制

日志章证明了 Redo 不能当复制介质，但复制本身没出现。补最短链路即可：dump → relay → 回放。延迟先看从库 SQL 线程，再提并行复制。不要展开 GTID 全家桶。

### 4.锁 — 退化写了，RC 和死锁没写

Record / Gap / Next-Key 和三种退化是够用的主链。缺的是：RC 为什么几乎没有间隙锁、意向锁解决什么、死锁是成环立刻破还是等超时。

这三句都是 RR 幻读、FOR UPDATE 之后的自然追问。

### 慢 SQL — 有字段，缺顺序

EXPLAIN 的 type / Extra、失效规则、「用了索引还是慢」是散装要点。缺一条口述顺序：慢日志定位 SQL → EXPLAIN 看 type、rows、Extra → 改条件或联合索引 → 再 EXPLAIN / 看慢日志。

不要把优化器内部全写上。有这条顺序，现有条目才接得起来。

## 三处建议改口

### RR 会不会幻读

现在：可重复读，解决不可重复读，减轻幻读。

更好：同类读可以避免幻读。普通 SELECT 用第一次的 ReadView；`FOR UPDATE` 用 Next-Key。先快照读再当前读，可能看到中间提交的新行。不要说「减轻」了事。

### 单表 2000 万

现在：表的最大长度是 2kw。层高变 4，耗时加 33%。

更好：行大约 1KB 时，高度 3 大概两千万这一量级。点查时上层页通常在 Buffer Pool，多一层不是多 33% 磁盘时间。要不要拆表看扫描、JOIN 和内存，不看这个整数。

### Change Buffer 开场

现在：基本等价于唯一索引和普通索引在实现上的区别。

更好：二级索引页不在内存时，普通索引的写入可以先记在 Change Buffer，省一次随机读。唯一索引插入必须当场判重，页得读进来。这是写多读少时的优化，不是两种索引的全部差别。

## 写得比较稳的部分

`1.架构` 的 LRU Midpoint（冷区约 3/8、观察期约 1 秒）和脏页 Flush List，能讲圆缓存污染。`2.索引1` 的 B+ 非叶子当路标、叶子双向链表，以及 `2.索引2` 的隐式转换方向（字符串列比数字会毁索引，整型列比字符串还能用）是对的。`2.索引3` 的最左物理顺序、覆盖索引、ICP 减少回表，作为口述主链够用。`3.事务` 后半的快照读 / 当前读和「混用才露幻读」，比开场那句「减轻幻读」完整。`5.日志2` 的执行顺序（先 Undo 再改行）和崩溃恢复三步（两次写修页 → Redo 重放 → 按 prepare/Binlog 裁决）可以直接背。
