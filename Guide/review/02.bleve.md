# Bleve 1–3 八股评审

对照 bleve v2.5.5（笔记自称的源码版本）看了 `Guide/content/中间件/Bleve` 下 `_index.md`、概览与 Mapping、写入与 Segment、倒排索引 / 查询与更新。

Scorch 写入四步、段只追加、删改靠标记、按字段组织 term 这几块能讲圆。问题集中在把 API 默认值说反、把 Lucene 经典 posting 说成 Bleve 实现、以及项目里真正会被追问的中文分词 / 选型几乎没接上。

## 结论

先改这五处，面试里不能照背：

1. store / doc values 写成默认关闭
2. 多词查询把 AND 当主路径
3. posting 用 gap 编码当成 Scorch 的存储
4. 默认 `standard` 示例里还留着停用词 `is`
5. 关 `_all` 却不改 `DefaultField`，无字段查询会落空

## 面试高频但几乎没写的

不是要把 Bleve 写成 zap 格式课。下面这些是文档中心 / 本地搜索一面里比 gap 编码数字更常出现的。

### 中文分词 — 现在零提及

项目里已经写了 `standard` 单字、误报、倒排过长、自研词表。中间件章只说「默认 analyzer 通常是 standard」，等于把最会被追的那句留给临场编。

建议顺序：默认 standard 做什么 → 中文为什么不行 → 查询/索引必须同一 analyzer → 再谈自定义分词。

### 为什么是 Bleve — 开篇太短

「单机少运维、集群用 ES」半句不够。一面通常要：嵌入式像 SQLite、Go 同进程、没有 JVM 堆、没有独立集群；代价是没有跨机分片、聚合和生态弱于 ES。和文档中心选型章对齐，这里给口播骨架即可。

### 打分和查询类型 — 现在只有交集/并集

缺：Match 会分析、Term 不分析、短语要位置；默认 TF-IDF，BM25 要开 mapping。搜「raft consensus」先问默认 OR，再问 AND 怎么开。

### 写入后能不能搜到

段引入 root 即可搜，这是近实时。默认 API 还等 persister，保证返回后已落盘。`unsafe_batch` 换吞吐、丢耐久。和 ES 的 refresh interval 对比就停在这一层。

## 四处建议改口

### Mapping 默认

现在：是否存原文，默认不存；是否建 doc values，默认不建。

更好：文本字段默认会索引、存原文、建 doc values、记位置、进 `_all`。这是搜索开箱能用的代价。索引胖了，优先关 `_all`、store、doc values，不是怀疑倒排写错了。

### 多词查询

现在：搜索 `raft consensus` → AND 取交集。

更好：默认 OR/SHOULD，命中一个词就进结果，词越多分越高。要两个词都在，显式 AND 或 Query String 的 `+`。不要把 Lucene 教材里的交集例题当成 Bleve 默认。

### 写入可见性

现在：等引入应用到 root，默认再等持久化回调。

更好：applied 到 root 的那一瞬，新快照会包含这批文档，其它请求已经能搜到。默认还堵到磁盘，是为了 `Index()` 返回后崩溃不丢。要继续灌下一批，才考虑 `unsafe_batch`。

### standard 分词

现在：默认 analyzer 通常是 `standard`，示例里 `is` 仍在词典。

更好：`standard` = unicode 切词 + 小写 + 英文停用词。`is`/`the` 不会进倒排；中文按字切。路径、ID 用 keyword；正文中文要自己换分析器。

## 写得比较稳的部分

`2.写入与Segment` 的 `Scorch.Batch`：补 `_id`、`analysisQueue`、`segPlugin.New`、`prepareSegment` 算 obsolete、送 `introductions`、默认等 persist，和 v2.5.5 源码顺序一致。「倒排按词存、不能原地插 posting，所以旧段只读、新数据新段」这条主链能讲圆。`3` 的删改模型也对：删除打标、修改 = 删旧 + 写新、merge 才物理清理。按字段区分 `title:raft` / `content:raft`、persister / merger / epoch 加引用计数回收旧文件，作为口述骨架够用。
