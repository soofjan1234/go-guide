# Lang-Agent 八股评审

对照现行 LangChain Python v1（LCEL、`create_agent`、LangGraph checkpointer / `interrupt`）看了 `Guide/content/其它/Lang-Agent` 下 `_index.md` 和 1–8 全部正文；`pic/` 只扫了第二阶段分层图上的文字。

主线已经在 v1 上，没有停在 `LLMChain` / `AgentExecutor`。为什么 Chain 不够、`bind_tools` 不执行工具、超步骤同轮不可见、`interrupt` 节点从头跑，这几块能讲。问题集中在把 checkpointer 当成短期记忆的全部、RAG 评估把正确和忠实捆在一起，以及流式、失败重试、手写工具图几乎没写。

不要和 `Guide/content/其它/Agent` 混背：那边总览仍把 LangChain 写成 2022 的 Chain 框架，入门记忆用 `RunnableWithMessageHistory` + `session_id`；这边是 `create_agent` + checkpointer / `thread_id`。

## 结论

先改这四处，面试里不能照背：

1. 短期记忆就是 `InMemorySaver` + `thread_id`
2. 生成质量「对照参考答案」同时覆盖正确和忠实
3. LCEL 也能做 Workflow
4. 手写 Graph 时消息字段也用 `operator.add` 拼接

## 面试高频但几乎没写的

为什么从 Chain 到 Graph、HITL、checkpoint / `thread_id`，正文里已经有。缺的是这些能接上现有章节的一面题。

### AgentExecutor 还在被问

笔记直接用 `create_agent`，口径是对的。一面仍常从旧教程问起：`LLMChain` 路径写死，`AgentExecutor` 能循环调工具，但状态、重试、暂停、恢复都不好收。

补最短对照即可：Executor 是外挂循环；Graph 把循环画进边，状态进 State，恢复靠 checkpointer。`create_agent` 是后者的高层 API。不要把 LangChain 和 LangGraph 答成两个竞争运行时。

### 流式和失败重试 — 有方法名，缺行为

第 4 章列出 `stream()`，第 7 章演示 `stream_mode="updates"`，第 1 章 Runtime 图里也有 Streaming。面试问的是：token 从哪来、工具调用怎么流、429 怎么重试、主模型挂了怎么换备用。

LCEL 用 `with_retry` / `with_fallbacks` 包模型，不包整条链。Graph 的 `recursion_limit` 防的是超步骤失控，不是 HTTP 重试。这两句和第 7 章已有的 `MAX_ATTEMPTS` 不重复。

### RAG 评估 — 有 IR 指标，缺点名 faithfulness

检索侧 Recall@K / Precision@K 能讲，生成侧也写了「碰巧正确」和「忠实但过期」。缺的是面试官用的名字：ragas 的 faithfulness、answer relevancy、context recall / precision。

不要展开成评测平台课。有这四个名字，现有表格才接得上。

### 手写 Agent 图 — 有 State/Edge，缺消息和工具节点

第 7 章用摘要例子把超步骤讲清楚了，第 3 章用 `create_agent` 把工具循环藏起来了。中间缺一张图：`ToolNode` + `tools_condition` + `add_messages`。

问「LangGraph 怎么接工具」时，现在只能重复 `create_agent` 已经封装。

## 四处建议改口

### 短期记忆

现在：LangChain v1 的短期记忆是 `create_agent` + checkpointer + `thread_id`。

更好：checkpointer 按 `thread_id` 把这一轮线程的 State 存下来，下次才能续。窗口满了要裁消息或做摘要，那是 middleware / `trim_messages`，换 PostgreSQL Saver 解决不了超窗。

### RAG 生成好不好

现在：看是否正确、完整且忠于资料，对照参考答案。

更好：先问检索有没有把证据拿到。生成再拆：有没有答对问题，每句能不能在本轮上下文里找到依据。对了但没依据，是 faithfulness 失败；依据过期但复述对了，是知识源失败。

### 为什么用 Graph

现在：Chain 路径预先确定，Agent 有循环和分支，所以用 State + Node + Edge。

更好：LCEL 适合无环组合。Agent 要反复决策、把工具结果写回状态、失败重来、中途暂停等人。这些是运行时问题，不是再多写几条 `|`。`create_agent` 已经跑在这张图上；要自定义节点和回退，再手写 `StateGraph`。

### `bind_tools` 和 Agent

现在：`bind_tools` 只把工具定义给模型，`create_agent` 封装循环。

更好：`bind_tools` 改的是请求侧 schema，一次 `invoke` 最多拿到带 `tool_calls` 的 `AIMessage`。本地函数、校验、`tool_call_id`、再送回模型，都要自己做。缺任一步就是断环。`create_agent` 把这张环画成图；审批暂停另走 interrupt，不是把环拆掉。

## 写得比较稳的部分

`1.基础` 从 Chain 到有状态图的那条理由（循环、条件、checkpoint、HITL）可以直接背，v1 和 LangGraph 的关系也写对了：`create_agent` 底层就是 Graph Runtime。`2.核心` 把「能解析 JSON、满足字段、符合事实」拆开，以及 `with_structured_output` 的工具调用 / JSON Mode / 严格 Schema，口径是现行的。`3.记忆` 的 `bind_tools` 不执行函数、`thread_id` 不是鉴权、工具调用和 `ToolMessage` 必须成对裁剪，这些是对的。`4.LCEL` 并行分支吃同一份完整输入、字典简写才变成 `RunnableParallel`、`assign` 留原字段，这是 LCEL 执行模型的面试第一句。`5.RAG` 的 Header 分割进 metadata、FAISS L2 越小越近而不是 0～1 置信度、权限过滤不能靠 Prompt，能挡住常见胡话。`7.LangGraph` 的同轮并行互不可见、固定边不要和条件边混、`recursion_limit` 不是模型调用次数。`8.HITL` 的「节点从头重跑、不要用宽 `except` 吞掉 interrupt、副作用放在中断后面」是现行合同，可以当口述主链。
