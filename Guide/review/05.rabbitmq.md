# RabbitMQ 基础 / 进阶八股评审

对照 AMQP 0-9-1 与现行 RabbitMQ（3.13 及 4.0–4.3）看了 `Guide/content/中间件/RabbitMQ` 的 `_index.md`、基础、进阶。

Exchange 四种类型、可靠性三段、消费幂等、死信不是一种队列、TTL 队头阻塞、重试不要直接 `requeue=true`，这几块能讲圆。问题集中在把 Classic Queue 口诀套到所有队列、镜像队列没标 4.0 已删，以及事务 / prefetch / 默认交换机这些一面高频点几乎没写。

## 结论

先改这五处，面试里不能照背：

1. 持久化不要背 Exchange + Queue + Message「三者缺一不可」
2. 镜像队列是 3.x 历史，4.0 已删除，现行 HA 答 Quorum Queue
3. Confirm 的 `ack` 不等于进了队列，`nack` 也不是路由失败
4. 选型不要把「事务、延迟」整段让给 RocketMQ
5. 补 AMQP 事务 vs Confirm，以及 `basic.qos` prefetch

## 发现列表

### 错误（说错了）

| 级别 | 章节 | 位置 | 问题 | 改法 |
| --- | --- | --- | --- | --- |
| 阻断 | 进阶.一.2 | 内部持久化「三者缺一不可」 | 把 Exchange durable、Queue durable、Message persistent 写成重启保消息的充要条件。Exchange 持久化管的是拓扑还在不在；已经进入 durable queue 的 persistent 消息，不依赖 exchange 是否 durable。Quorum Queue 队列必 durable、消息始终落盘，源队列还忽略 `delivery_mode`。 | 改成两条：Classic 看 **Queue durable + Message persistent**；Confirm 用来关掉内存到磁盘的窗口。Exchange durable 单独说「重启后交换机还在」。QQ 不要套这三句。 |
| 阻断 | 进阶.七.2 | 镜像队列整节 | 把 Classic Mirrored Queue 写成现行 HA 选项，只补一句「较新版本更推荐 Quorum」。镜像队列 3.9 弃用，**4.0（2024）删除**。2026 年照背「主从镜像」会打脸。 | 镜像队列标成 3.x 历史。现行复制：Quorum Queue（队列语义）和 Stream（日志语义）。Classic Queue 4.0 起不再复制。 |
| 重要 | 基础.一 | 选择建议第 3 条 | 写成需要事务、延迟消息就优先 RocketMQ。后文自己在讲 TTL+DLX 和延迟插件；RabbitMQ 也有 AMQP `tx`（只是不该用）。RocketMQ 事务消息是半消息提交，和 AMQP 事务不是一回事。Kafka 也有事务。 | 选型改成：灵活路由 / 低延迟 / 死信用 RabbitMQ；海量日志回放用 Kafka。RocketMQ 的产品能力是**事务消息和多级延迟**，不要说 RabbitMQ 做不了延迟、没有事务原语。 |
| 重要 | 进阶.一.1 | Confirm 的 ack / nack 两行 | 写成 `ack`＝已接收、`nack`＝无法完成接收。路由不到的消息**仍然 `basic.ack`**，消息被丢（除非 `mandatory` / Alternate Exchange）。Publisher `nack` 只在队列内部错误等例外。 | 改成：入队成功后 ack（持久化消息要等落盘，QQ 要等多数派）；**路由不到也是 ack**；`nack` 罕见。没进队列靠 Return / AE，不靠 nack。 |
| 重要 | 进阶.四.3 | 延迟消息插件 | 只说装 `rabbitmq_delayed_message_exchange` 更简单、能处理不同延迟。插件把消息放**本节点 Mnesia 单副本**，丢该节点就丢延迟消息。4.3 起社区插件已弃用归档；开源 4.3 的 QQ delayed retry 是消费侧延迟重投，不是通用定时投递。 | 先写 TTL+DLX。插件必须带限制：Mnesia、单节点、不适合大规模。4.3 标清版本，不要说「装插件就等于官方延迟队列」。 |
| 重要 | 进阶.四.1 | 死信原因第 3 条 | 写成 Queue 达到最大长度就会淘汰旧消息。这只是默认 `overflow=drop-head`。`reject-publish` 是拒收新消息，走 publisher confirm/nack，不是丢队头。 | 写明两种 overflow。死信只发生在丢弃/过期/拒绝且配置了 DLX 时。 |

### 遗漏

| 级别 | 章节 | 位置 | 问题 | 改法 |
| --- | --- | --- | --- | --- |
| 重要 | 进阶.一.1 | Confirm 之后 | 一面常问「用事务还是 Confirm」。正文只写 Confirm，没写 AMQP `tx.select` / `tx.commit`。官方说法：事务能保证，但吞吐大约差 250 倍；channel **不能同时**开事务和 Confirm。 | 补三句：协议里有事务；生产不用；和 RocketMQ 半消息、Kafka EOS 分开讲。 |
| 重要 | 进阶.三 / 进阶.一.3 | 积压里只出现「Prefetch 过大」 | 官方教程第二课就是 Work Queue + QoS。缺 `basic.qos`：prefetch 是 Unacked 窗口；`0`＝不限制；`1`＝公平分发但吞吐差；文档常见更合适的是 100–300。QQ 不支持 global QoS，消费者 prefetch 还有约 2000 的上限。 | 消费确认后单开一小节。先说窗口，再讲 1 和 100+ 的取舍，不要只当积压原因。 |
| 重要 | 基础.二 | 概念表 | 缺默认交换机。官方教程第一课：无名 Direct Exchange，`routing key = 队列名`，每个队列自动绑上去。 | 概念表加 Default Exchange。强调「看起来像直发队列」，实际仍经过交换机。 |
| 重要 | 基础.一 | Kafka / RocketMQ 对比表 | 表有吞吐和顺序，缺一面更常问的模型差：RabbitMQ 是 broker **push**，ack 后消息删掉；Kafka 是 consumer **pull**，按保留策略存放，可回放。缺这一点，后面「不适合当事件日志」没有落点。 | 对比表加两行：投递模型、保留策略。Stream 队列一句即可，不要说 RabbitMQ 完全不能回放。 |
| 重要 | 进阶.三 / 进阶.七.4 | 流控 | 积压写了可能阻塞生产者，高可用写了内存高水位，都没说机制。内存超过水位（默认约 40%）或磁盘过低会 `connection.blocked`；**集群一节点报警，所有节点都阻塞生产者**；只消费的连接不堵。另有 credit-based 瞬时流控。 | 积压或高可用补「资源报警 = 堵生产、放消费」。客户端要处理 blocked / unblocked。 |
| 重要 | 进阶.五 | 顺序之后 | 用户常把顺序和优先级混在一起。Classic Queue 用 `x-max-priority` + 消息 `priority`；有额外开销。QQ 到 **4.0** 才支持优先级。 | 顺序章后补五句话：优先级不是全局插队到任意位置，是队列内有限档位；和「按业务键分片保序」不是同一题。 |

### 可以更好

| 级别 | 章节 | 位置 | 问题 | 改法 |
| --- | --- | --- | --- | --- |
| 建议 | 进阶.一.1–2 | Confirm 与落盘窗口 | 先说 ack＝已接收，后说内存到磁盘仍有窗口所以要 Confirm。两段对上了，口述容易说成「ack 只表示进了内存」。 | 合并：持久化消息的 ack 发生在落盘之后（QQ 是多数派）；瞬时消息是入队即可。没有 Confirm，重启仍可能丢掉尚未落盘的 persistent 消息。 |
| 建议 | 进阶.一.3 | ack / nack / reject 表 | 表把 `nack` 和 `reject` 写成几乎一样。`basic.reject` 只能单条；`basic.nack` 是 RabbitMQ 扩展，可 `multiple`。ack 必须在**投递的同一 channel**。 | 表加两列：是否批量、是否协议原语。Go 里不要跨 goroutine、跨 channel 去 ack。 |
| 建议 | 进阶.一.3 | 自动 ACK | 写成消费者收到后立刻宕机，消息可能已删。更准确的是：broker **写入 TCP 套接字**就认为投递成功，应用进程未必已经读到。 | 改成：auto-ack 在写 socket 时删消息。重要业务手动 ack，并设 prefetch。 |
| 建议 | 进阶.五 | 只使用一个 Consumer | 人为只挂一个实例，挂了就停。RabbitMQ 有 Single Active Consumer：多实例在线，同一时刻只有一个消费。 | 保序方案写成：同一业务键进同一队列 + SAC 或单消费者串行 + 失败不要随便 requeue。 |
| 建议 | 进阶.四.1 | Quorum 投递次数 | 只写「超过配置的投递次数」。4.0 起 QQ **默认 `delivery-limit=20`**，超限死信或丢弃，用来防止无限 `requeue` 撑爆 Raft log。 | 死信原因里写上默认 20，并链到重试章：不要靠无限 nack 重入队。 |
| 建议 | 基础.二 | Connection / Channel | 写了少连接、每协程一 channel、channel 错了不必断连接。缺心跳，也缺生产/消费分连接——资源报警时同一条连接上既发又收会被一起拖住。 | 补 heartbeat 探活；生产、消费分开 Connection。Channel 不是线程安全，Go 不要共享。 |
| 建议 | 基础.一 | 对比表「消息顺序」 | 「单队列、单消费者下有序」作为第一句可以，但 prefetch>1 且消费者并发处理会乱序；`nack` 重入队不一定回到原位。 | 基础表加括号：还要串行处理和谨慎 requeue。细节放到进阶第五章。 |
| 建议 | 基础.一 | 与 Kafka 对比 | 没提 Stream。RabbitMQ 3.9+ 的 Stream 是追加日志，可多消费者回放，语义更靠近 Kafka，不是普通队列。 | 对比补一句：要回放先问能不能上 Stream；真要长期事件日志再上 Kafka。 |

## 面试高频但几乎没写的

不是要把进阶写成运维手册。下面这些是 3 年 Go 社招一面里比 Headers Exchange、Raft 日志截断更常出现的。

### Confirm 旁边缺事务

可靠性章已经把三段丢失讲清楚了。面试第一句经常是「RabbitMQ 的事务和 Confirm 怎么选」。现在正文像 Confirm 是唯一原语。

建议补在 Producer 段末尾：协议有 `tx`，生产不用；Confirm 是轻量替代；channel 两者互斥。RocketMQ 事务消息、Kafka 事务另说。

### Prefetch 只出现在积压排查

Work Queue 官方教程的核心是竞争消费者 + 手动 ack + QoS。现在只在 Unacked 原因里提了一句「Prefetch 过大」。

建议顺序：手动 ack → prefetch 是 Unacked 窗口 → `1` 公平、`0` 不限制、常用几十到几百 → 再谈积压。

### 默认交换机

概念从 Exchange / Queue / Binding 起，没写空名字那一个 Direct。很多面试从「能不能不经过交换机发到队列」入题。

### 和 Kafka 的第一句

现有表用吞吐、顺序、运维复杂度。一面更常问：push 还是 pull、消费完还在不在、能不能从旧偏移回放。这三句有了，「不适合当事件日志」才接得上。

### 优先级和流控

顺序章写了分片保序，没写 `x-max-priority`。积压/高可用写了会堵生产者，没写 `connection.blocked` 和集群级报警。都是追问，不是主链。

## 四处建议改口

### 持久化第一句

现在：Exchange、Queue、Message 都要持久化，三者缺一不可。

更好：消息能不能活过重启，看队列是不是 durable、消息是不是 persistent；再用 Confirm 确认已经落盘（QQ 则是多数派）。交换机 durable 只保证拓扑还在。

### 高可用第一句

现在：普通集群 / 镜像队列 / Quorum Queue 并列，然后说较新版本更推荐 Quorum。

更好：要复制就用 Quorum Queue，不要答镜像队列。镜像是 3.x 的 HA，4.0 删了。普通集群只复制元数据，Classic Queue 仍在单节点。

### Confirm 和事务

现在：只讲 Confirm 的 ack / nack。

更好：AMQP 有事务，太重，吞吐差两个数量级，生产用 Confirm。Confirm 成功不表示路由到了队列；路由失败要 `mandatory` 或备用交换机。`nack` 不是「没匹配到队列」。

### Prefetch 第一句

现在：Prefetch 过大导致大量 Unacked。

更好：`basic.qos` 限制这条 channel 上未确认的条数，防止消费者被推爆。设 1 是公平分发；为了吞吐通常比 1 大。不要开自动 ack 还不限窗口。

## 写得比较稳的部分

基础篇四种 Exchange、Topic 的 `*` / `#`、Fanout 多队列广播 vs 同队列竞争，口述不容易说乱。进阶把丢失拆成 Producer → Broker → Consumer，Confirm 和 `mandatory` / AE 分开，自动 ack 与手动 ack 的取舍清楚。幂等四种手法（唯一约束、消费表、Redis、状态机）有边界。死信写成「普通队列 + DLX」而不是一种队列类型，TTL 队头阻塞和按延迟分队列，以及「不要 `nack(requeue=true)` 打满 CPU」，这些作为一面主链是够用的。Ready / Unacked 排查和 Quorum 多数派停写，也经得住追问。
