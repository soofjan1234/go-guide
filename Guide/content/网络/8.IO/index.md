常见的 I/O 模型主要有 BIO（阻塞 I/O）、NIO（非阻塞 / 多路复用 I/O）、AIO（异步 I/O），此外还有在 Linux 内核底层扮演重要角色的信号驱动 I/O 以及当下高并发性能天花板 io_uring。

## IO阶段

- 阶段 1：等待数据准备好（网卡收到网络包，并拼装好写入内核缓冲区）。
- 阶段 2：将数据从内核空间拷贝到用户空间（从操作系统内存复制到你的程序内存中）

可以通过 “阶段 1” 和 “阶段 2” 来区分这两对概念：
- 阻塞/非阻塞（Blocking / Non-Blocking）：当数据还没准备好时，你的线程是挂起睡觉，还是立刻返回？
- 同步/异步（Synchronous / Asynchronous）：当数据准备好后，到底是谁负责把数据搬进程序内存？是线程亲自搬，还是内核搬好通知你？
    - 如果是应用线程自己去读，就是同步
    - 如果是操作系统内核读完通知你，就是异步

# 一、 常见 I/O 模型全景图

## 1. BIO（Blocking I/O，同步阻塞 I/O）

- 工作模式：一个连接对应一个线程（One Thread Per Connection）。
- 过程：应用程序发起 `read()` 调用，如果数据还没准备好，线程就会被一直阻塞，直到内核准备好数据并拷贝到用户空间，线程才被唤醒。
- 致命缺点：面对高并发场景（如 10 万个并发连接），需要创建 10 万个线程，内存会被撑爆（每个线程栈占用内存），且 CPU 绝大部分时间都消耗在线程上下文切换上。
- 应用场景：连接数较少且固定的架构（如传统的 Socket 编程、早期的 Tomcat）。

---

## 2. NIO（Non-blocking I/O / I/O Multiplexing，同步非阻塞 / I/O 多路复用）

- 工作模式：一个/少数几个线程就可以管理上万个连接（Reactor 模式）。
- 过程：
    1. 应用线程把成千上万个 Socket 注册到操作系统的多路复用器（如 Linux 的 epoll）上。
    2. 一个单独的 Poller/Selector 线程轮询 epoll，只有当某些 Socket 发生可读/可写事件时，才返回这些就绪的 Socket。
    3. 应用线程接管就绪的 Socket，进行真正的 `read/write`（数据拷贝阶段线程依然是同步阻塞的）。
- 核心优势：大幅减少了线程数量和切换开销，能轻松应对高并发长连接。
- 应用场景：现代高性能网络框架的标准配置（Netty、Redis、Nginx、RPC 框架、Kafka）。

---

## 3. AIO（Asynchronous I/O，真正的异步非阻塞 I/O）

- 工作模式：基于事件驱动和回调机制（Proactor 模式）。
- 过程：
    1. 应用程序向内核发起异步读写请求，并传入回调函数，然后立即返回，继续做别的事。
    2. 操作系统内核在后台等待数据准备完毕，并且主动把数据拷贝到应用程序的缓冲区（Buffer）中。
    3. 这一切完成后，内核通知应用线程或直接触发回调函数。
- 核心优势：整个过程应用线程完全无需阻塞等待，甚至连“数据拷贝”这一步都是内核帮着做好的。

# 二、 还有什么 I/O？（进阶与底层 I/O 模型）

除了 BIO、NIO、AIO，在操作系统层面和最新技术演进中，还有以下几种极其重要的 I/O 模型：

## 4. 信号驱动 I/O（Signal-driven I/O）

- 原理：应用程序向内核注册一个信号处理函数（`SIGIO`），然后立刻返回。当内核数据准备好时，发送 `SIGIO` 信号通知应用程序，应用程序在信号处理函数中调用 `recvfrom` 将数据从内核拷贝到用户空间。
- 局限性：信号处理在 TCP Socket 中极其繁琐（产生 `SIGIO` 的事件太多，如握手、断开、出错等），难以区分具体是哪个事件，因此在实际高并发网络编程中很少使用。

---

## 5. io_uring（Linux 新一代异步 I/O 的终极方案）

这是近年来 Linux 内核（自 Linux 5.1 起引入）最重要的创新之一，也是真正的高性能 Linux 异步 I/O。

- 诞生背景：原生的 Linux AIO 只支持 `O_DIRECT` 磁盘文件，不支持 Socket，且系统调用（Syscall）开销极大。`io_uring` 就是为了全面超越 `epoll` 和旧 AIO 而生的。
- 核心机制：无锁无系统调用的共享环形缓冲区（Ring Buffer）。
  1. 在内核与用户空间之间共享两个无锁环形队列：提交队列（SQ, Submission Queue）和完成队列（CQ, Completion Queue）。
  2. 应用把 I/O 请求写入 SQ，内核处理完后把结果写入 CQ。
  3. 在极高的 IOPS 场景下，可以通过内核轮询（SQPOLL）模式，实现 0 次系统调用（Syscall-free）完成大规模 I/O 操作。
- 发展趋势：目前 Netty 已经推出了基于 `io_uring` 的传输层扩展（`netty-transport-native-io_uring`），在许多吞吐量测试中超越了传统的 `epoll`，是未来高性能 I/O 的重要演进方向。

---

## 6. 零拷贝与 Direct I/O（磁盘/网络数据传输优化）

在谈论 I/O 时，除了网络模型的阻塞/非阻塞，还有关于“数据拷贝路径”的优化：

- mmap / sendfile（零拷贝）：绕过用户空间内存缓冲，直接在内核空间将磁盘文件数据通过网卡发送出去（Kafka 和 Netty 大量使用）。
- Direct I/O（直接 I/O）：跳过操作系统的 Page Cache（页缓存），由应用自己直接读写物理磁盘（如 MySQL 数据库的 InnoDB 存储引擎，为了避免双重缓存而使用 `O_DIRECT`）。

## 三、Go协程的网络阻塞呢？

这种机制通常被称为 “用同步的代码风格，实现异步的并发性能”（Sync programming, Async execution）：

- 在操作系统（OS 内核）视角： Go 的底层依然是标准的 “同步非阻塞 I/O + I/O 多路复用（epoll/kqueue）”，它不是真正的异步 I/O（AIO）。
- 在业务代码（Goroutine）视角： 它看起来是 “同步阻塞” 的（你写 conn.Read() 代码会卡在那里等，不需要写繁琐的异步回调函数）。
- 在物理线程（Thread / M）视角： 它是 “非阻塞并发” 的，M 从不真正被内核挂起，而是把卡住的 G 丢给 Netpoller，自己去跑下一个 G。
