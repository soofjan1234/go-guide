# 全双工半双工

1. 单工：单向流动
2. 半双工：双向流动，不能同时
3. 全双工：双向流动，且能同时进行

## 传输层：TCP

- TCP 连接有两个独立的缓冲区：发送缓冲区（Send Buffer）和接收缓冲区（Receive Buffer）。
- 代码体现：
    - 在同一个 TCP 连接上，线程 A 可以死循环不断地往外发数据（Write）
    - 与此同时，线程 B 也可以死循环不断地读取对方发来的数据（Read）。两边互不影响，不会因为正在发送就无法接收。
- TCP 的四次挥手也完美体现了全双工：
    - 客户端发送 FIN，表示“我的发送通道关闭了（我不再发数据了）”；
    - 但此时连接并没有完全死掉，它进入了半关闭（Half-Close）状态——客户端依然可以继续接收服务端发来的数据，直到服务端也发了 FIN，整个全双工连接才彻底关闭

## 应用层：HTTP

1. HTTP/1.1 
    - 虽然底层跑在全双工的 TCP 上，但它的应用层协议模型是 Request - Response（请求-响应）严格一问一答的
2. HTTP/2 & HTTP/3 
    - 引入了 Stream（流） 和 二进制分帧（Binary Frames）。
    - 客户端可以在同一个连接上同时交织发送多个请求帧，服务端也可以同时并发交织回传多个响应帧，甚至服务端还能主动向客户端推流（Server Push），实现了高并发下的全双工应用层通信。
3. WebSocket —— 典型的应用层“全双工”
    - 浏览器向服务器发起 HTTP 握手后，协议升级（Upgrade）为 WebSocket。
    - 之后连接建立，客户端可以随时给服务端发消息，服务端也可以在任何毫秒主动推消息给客户端，双方地位对等，是标准的实时全双工协议。

### 关于HTTP/2 & HTTP/3 

1. 在单一的“语义层面”（单条请求维度）：HTTP/2 和 HTTP/3 依然保留了“请求-响应”（Request-Response）的经典语义，你发一个 GET /api，服务端依然要针对它回一个 200 OK。

2. 在底层的“传输连接层面”（多流与帧的维度）：它彻底摆脱了 HTTP/1.1 那种“你一句、我一句”的半双工阻塞机制，变成了真正的多路复用全双工。

HTTP/2 的单连接时间线（全双工并发）：
[客户端 -> 发送 Req 1 的一部分] ──┐
[服务端 -> 发送 Resp 0 的一部分] ─┼──> (在同一时刻，数据在网线上双向飞驰，互不干扰！)
[客户端 -> 发送 Req 2 的一部分] ──┘

3. 在高级功能层面（如 gRPC / 双向流）：它甚至打破了传统的一问一答，允许“客户端一边连续推、服务端一边连续回”。

# Socket

## 什么是socket

1. 从应用开发视角（API）：
    - Socket 是操作系统内核提供给程序员的一套网络通信编程接口（API）。
    - 无论上层是写 HTTP、RPC、WebSocket 还是 FTP，它们的底层归根结底都是在调用 Socket API（如 socket(), bind(), listen(), connect(), read(), write() 等）。
2. 从操作系统视角（文件/描述符）：
    - 在 Unix / Linux “一切皆文件” 的哲学中，Socket 本质上就是一个特殊的文件描述符（File Descriptor, fd）。
    - 读写网络数据，在系统调用层面和读写普通本地文件几乎一模一样：都是用 read() 和 write()。
3. 从网络协议视角（通信端点）：
    - Socket 是网络上一个唯一的通信端点。
    - 它在逻辑上由 “IP 地址 + 端口号 + 传输协议（TCP/UDP）” 唯一定位。

##  Socket 的底层长什么样

- 发送缓冲区（Send Buffer）：你的代码调用 write(fd, "hello") 时，并不是直接把数据送上了网线，而是拷贝进了内核的 Socket 发送缓冲区就返回了。网卡会在合适的时候自己从这里取走数据并打包发出。
- 接收缓冲区（Receive Buffer）：网卡收到网络数据包，拼装好后放入这个缓冲区。当你的代码调用 read(fd, buf) 时，CPU 负责把数据从接收缓冲区拷贝到你的程序内存。
- 协议状态机：记录连接当前的状态（比如 TCP 的 LISTEN, SYN_SENT, ESTABLISHED, CLOSE_WAIT 等）。
- 等待队列：当没有数据可读时，发起 read() 的线程会被挂起到这个等待队列中休眠；当网卡收到数据后，硬件中断触发，内核再从这个队列里唤醒你的线程。

## 通信流程

       服务端 (Server)                          客户端 (Client)
  --------------------------               --------------------------
  1. socket() 创建监听套接字
  2. bind()   绑定IP和端口
  3. listen() 开启监听 (进入 LISTEN)
  4. accept() 阻塞等待客户端连接
             ▲
             │       TCP 三次握手 (SYN -> SYN/ACK -> ACK)
             └──────────────────────────────── 5. connect() 发起连接
  (返回一个新的已连接套接字 conn_fd)
             │
  6. read()  阻塞等待读取数据 ◄──── 业务数据 ──── 7. write() 发送数据
  8. write() 发送响应数据    ──── 业务数据 ────► 9. read()  读取响应
             │
  10. close() 关闭连接      ◄──── 四次挥手 ──── 11. close() 关闭连接

## Unix Domain Socket 

- 以文件形式存在：在文件系统中，UDS 通常表现为一个特殊的文件（文件类型为 s，如 /var/run/docker.sock）。进程通过这个文件路径来建立连接，而不是通过 IP:端口。
- 纯内核内存拷贝：当两个进程通过 UDS 通信时，数据直接在内核缓冲区中复制，完全绕过了网络协议栈（不需要经过网卡、不需要封包/拆包、不需要计算校验和、不需要处理路由等）


1. 寻址：UDS 用文件路径（如 `/tmp/app.sock`）；网络 Socket 用 IP + 端口（如 `127.0.0.1:8080`）
2. 性能：UDS 直接内存拷贝，不走协议栈；`127.0.0.1` 仍要走完整 TCP/IP
3. 资源：UDS 只占文件描述符和内核内存；网络 Socket 还占端口号、TCP 缓冲区
4. 跨主机：UDS 只能本机；网络 Socket 改 IP 就能跨机器
5. 权限：UDS 用文件权限（chmod、chown）；网络 Socket 靠防火墙或应用层鉴权
6. 特殊能力：UDS 能传文件描述符；网络 Socket 不能


## SSE 和 WebSocket

1. SSE是单向推流；WebSocket是双向流。
2. SSE是http/https协议；WebSocket 协议（通过 HTTP 握手升级为 ws:// 或 wss://）
3. SSE支持 UTF-8 文本；WebSocket 不仅支持文本，还支持二进制流
