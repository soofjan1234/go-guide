## 分层理解单双工、TCP 与 HTTP

### 单双工：主要描述链路收发能力

单工、半双工、全双工通常用于描述物理层或链路层的收发能力：单工只能单向传输，半双工双方都能发送但不能同时发送，全双工则允许双方同时收发。

### TCP：全双工的可靠字节流

TCP 可以认为是天然全双工：连接两端都能同时发送与接收数据，各自维护发送和接收方向的状态。应用程序可以在同一个 TCP 连接上并发 `Read` 和 `Write`。

TCP 的 FIN 只结束本端的发送方向。客户端发送 FIN 后，仍可以继续接收服务端尚未发送完的数据；双方都发送 FIN 后，连接才完全关闭。这是连接关闭过程，不要和链路层的半双工混为一谈。

### HTTP：关注消息模型，而不是单双工

- **HTTP/1.1**：底层仍是全双工 TCP；应用层以请求—响应为主，同一连接上的响应顺序可能造成应用层队头阻塞。它不应被简单称为半双工。
- **HTTP/2 / HTTP/3**：核心改进是多路复用。多个 Stream 可以在同一连接上交错传输，但单个 Stream 仍遵循请求—响应语义。
- **WebSocket**：完成 HTTP 握手后升级为独立协议，客户端和服务端都可以主动发送业务消息，适合聊天、实时通知和协同编辑。

## 面试怎么回答

**问：TCP 是全双工吗？HTTP/1.1、HTTP/2、HTTP/3 又该怎么理解？**

答：单双工一般描述链路收发能力。TCP 可以认为是全双工的可靠字节流，两端都能同时读写。HTTP/1.1 不应简单叫半双工，它底层仍是全双工 TCP，只是应用层采用请求—响应模型，响应顺序会造成队头阻塞。HTTP/2 和 HTTP/3 的核心改进不是把连接变成全双工，而是在已有双向传输能力上实现多路复用；如果业务需要双方随时主动发送消息，通常使用 WebSocket 或 gRPC 双向流。

# 分片上传
和 HTTP/1.1 的 Range **不是同一件事**：Range 主要是下载时按字节区间取；分片上传是应用层自己切块、自己记账。

## 怎么设计

大文件一次 POST 容易超时、失败要整文件重传。前端按固定大小切块（如 5MB），每块一个请求，后端收齐再拼。

1. **初始化**：前端上报文件名、大小、hash；后端发 `uploadId`，建临时目录
2. **传块**：每块带 `uploadId`、序号、块 hash；后端写成独立文件，记下已收序号
3. **并发**：块之间无依赖，可并行；同一序号重复到就丢弃
4. **合并**：已收块数 = 总块数后按序号拼接，算整文件 hash，和初始化时比对；对上再落到正式路径

后端接口大致三步：创建任务 / 收一块 / 完成合并。进度用「已收序号集合」记，不要只记一个数字（中间缺块时数字会骗人）。

## 断点续传怎么做

刷新或断网后，不要从头再传。

1. 前端用文件 hash（或 `uploadId`）问后端：哪些块已经在
2. 后端返回已收序号列表
3. 前端只补缺的块，再走合并

临时文件要设 TTL（例如几小时）：用户取消或半途跑了，后台清过期目录。取消当下可以停后续块；已落盘的先留着，同一文件再传还能续。
