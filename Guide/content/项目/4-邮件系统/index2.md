## 图里有哪些节点？

```
邮件标准化 / 去重
→ 分类与风险判断
→ 检索与证据评估
→ 草稿校验
→ 审核
```

### 1. 分类与风险判断

1. 简单的垃圾邮件过滤：邮件服务商本身已经过滤大部分了，所以这边只做简单过滤，客服可以加过滤词以及分数，超过2分就丢弃
2. 自动回复检测：比如Auto、Out of Office等词
3. 提示词注入检测：
   - 首先是常用词：ignore、previous等等
   - 提示词也说明：邮件内容是不可信数据，不能改变系统规则
   - Agent权限只是生成草稿，由人工审核
4. 正常邮件

### 2. 检索与证据评估

1. 不相关：再次检索一次
   - 从邮件提取问题主体
   - 读取首次评估指出的缺口
   - 构造一个更聚焦的查询
2. 信息不足：询问明确缺少的信息
3. 高风险回答：人工接管
4. 信息充足：生成草稿

## State 保存什么？

| 类别 | 字段 | 用途 |
| --- | --- | --- |
| 流程身份 | `email_id`、`workflow_generation`、`phase` | 知道正在处理哪封邮件、第几次处理、当前走到哪里 |
| Agent 判断结果 | `category`、`priority`、`risk`、`decision` | 保存分类、风险、草稿、引用等处理结论 |
| 重试与校验记录 | 三个 `*_attempts` / `*_count`、`validation_errors` | 防止检索、改写、生成无限循环，并记录失败原因 |
| 人工审核结果 | `review` | 审核恢复后记录人工动作 |

## PostgreSQL Checkpointer 保存什么？

Checkpointer 保存的是流程运行态：当前停在哪个节点、State、interrupt 产生的暂停点和恢复所需 checkpoint。它解决的是‘从哪里继续’

### 服务重启后如何继续？

当前每封待处理邮件生成类似 email:{email_id}:generation:1 的 Graph thread_id

服务重启后，调度器会从 PostgreSQL 读取该 thread_id 的 checkpoint 决定继续位置

## 人工 interrupt 如何暂停、恢复？

- 草稿完成后，Graph 执行 interrupt()，LangGraph 先持久化 checkpoint，再把任务停在审核点。

- 先读取最新 checkpoint，再比较前端提交的 checkpoint_id；不一致说明页面已过期或流程已变化，拒绝恢复。
- 验证通过后才执行 Command(resume=review)，从 interrupt() 停下的位置继续。

## 怎么保证“审核通过才出站”？

后端判断 action 是否为 approve / edit_and_approve
   ├─ 是：写入模拟发件箱
   └─ 否：拒绝或转人工，不写模拟发件箱

# 重复问题

- 重复点击批准：用户连点按钮；前端因网络慢超时后自动重试；请求其实已成功，但响应在路上丢了。
- 重复恢复：审核记录已落库，但服务在 Command(resume=...) 前退出；重启后的补偿任务或用户重试会再次尝试恢复同一个 checkpoint。
- 发送失败重试：真实邮件服务调用超时、连接中断时，客户端可能无法判断“服务端根本没收到”还是“已发送但响应丢失”，因此必须按可能已成功处理。

## 防“同一次 HTTP 请求被重发”

前端这次点击会带一个请求 ID：review_request_id。通常由前端在用户点按钮时生成一个 UUID。

假设服务端已经把审核记录写进数据库，但响应因为网络问题没返回。用户再次点击或前端重试时，仍应携带同一个 R1。

代码会先按 R1 查已有审核记录；找到了就复用，而不是再插入一条审核记录。若同一个 R1 却带了不同的邮件、审核点或动作，则返回 409，防止一个请求 ID 被错误复用。

所以它解决的是：“我不知道上次点成功没有，于是把同一个请求又发了一遍。”

## 防“同一个审核停点被做两次不同决定”

假设两个审核员都打开了同一封邮件：
审核员甲：R1 + T1 + C1 + approve
审核员乙：R2 + T1 + C1 + reject

这里 R1、R2 不同，所以只靠请求 ID 拦不住；但两人操作的都是同一个 Graph 停点 T1 + C1（graph_thread_id + checkpoint_id）。

reviews 表对此有数据库唯一约束：UniqueConstraint('graph_thread_id', 'checkpoint_id')

因此只能有一个人成功落库。后到的请求会冲突，不能把已经批准的草稿改成拒绝，也不能覆盖审核结论。

所以它解决的是：“不同请求同时处理同一份待审核草稿。”

## 防“同一条审核结论重复产生发件副作用”

审核记录落库后，服务端会生成内部 review_id。之后无论工作流恢复几次，模拟发件箱都按这个 ID 写入

例如：
审核记录 review_id = V1 已保存
↓
恢复工作流时进程异常
↓
用户用 R1 重试，或后台补偿恢复
↓
再次尝试写模拟发件箱

因为 simulated_outbox.review_id 唯一，第二次插入会被数据库忽略，最终仍只有一条模拟发件记录。
