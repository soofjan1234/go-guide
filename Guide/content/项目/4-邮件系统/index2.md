## 图里有哪些节点？
```
邮件标准化 / 去重
→ 分类与风险判断
→ 检索与证据评估
→ 草稿校验
→ 审核
```
### 1. 分类与风险判断

1. 简单的垃圾邮件过滤：邮件服务商本身已经过滤大部分了，所以这边只做简单过滤，客服可以加过滤词以及分数，超过2分就丢弃
2. 自动回复检测：比如Auto、Out of Office等词
3. 提示词注入检测：
   - 首先是常用词：ignore、previous等等
   - 提示词也说明：邮件内容是不可信数据，不能改变系统规则
   - Agent权限只是生成草稿，由人工审核
4. 正常邮件

### 2. 检索与证据评估

1. 不相关：再次检索一次
   - 从邮件提取问题主体
   - 读取首次评估指出的缺口
   - 构造一个更聚焦的查询
2. 信息不足：询问明确缺少的信息
3. 高风险回答：人工接管
4. 信息充足：生成草稿

### 3. 草稿校验

1. 自动校验覆盖输出字段、引用片段、草稿非空
2. ai核实草稿内容是否真的被引用材料支持

## 4. 审核

1. 草稿完成后，Graph 执行 interrupt()，LangGraph 先持久化 checkpoint，再把任务停在审核点。
2. 审核之后，先读取最新 checkpoint，再比较前端提交的 checkpoint_id；不一致说明页面已过期或流程已变化，拒绝恢复。
3. 验证通过后才执行 Command(resume=review)，从 interrupt() 停下的位置继续。

## State 保存什么？

| 类别 | 字段 | 用途 |
| --- | --- | --- |
| 流程身份 | `email_id`、`workflow_generation`、`phase` | 知道正在处理哪封邮件、第几次处理、当前走到哪里 |
| Agent 判断结果 | `category`、`priority`、`risk`、`decision` | 保存分类、风险、草稿、引用等处理结论 |
| 重试与校验记录 | 三个 `*_attempts` / `*_count`、`validation_errors` | 防止检索、改写、生成无限循环，并记录失败原因 |
| 人工审核结果 | `review` | 审核恢复后记录人工动作 |

## PostgreSQL Checkpointer 保存什么？

Checkpointer 保存的是流程运行态：当前停在哪个节点、State、interrupt 产生的暂停点和恢复所需 checkpoint。它解决的是‘从哪里继续’

### 服务重启后如何继续？

当前每封待处理邮件生成类似 email:{email_id}:generation:1 的 Graph thread_id

服务重启后，调度器会从 PostgreSQL 读取该 thread_id 的 checkpoint 决定继续位置

# 搜索
## 为什么分路检索？

产品文档提供型号、版本、功能边界和排障步骤等事实依据；已审核案例提供客服表达方式、追问思路和处理经验

把它们混在一个池子里，案例的措辞可能压过官方事实，所以系统对两类来源分别做全文和向量检索，各自融合后最多保留 3 条，总数最多 6 条。

## 全文检索
全文检索擅长精确词：型号、错误码、DSM 版本、命令和产品专有名词

- `english` 是“分词和归一化规则”。它决定 content 怎样被处理成可检索的词项，例如去停用词、处理词形变化。
- `GIN` 是“索引结构”。它让 PostgreSQL 不必扫描每个文档片段，而是快速找到包含这些词项的行。

### 怎么提取关键词

去掉停用词，对词打分，得出前x个

## 向量检索
向量检索擅长客户的口语化描述，例如客户没说‘挂载失败’，而是说‘电脑找得到 NAS，但打不开共享目录’。

## RRF 是什么，为什么用它融合？

RRF 是 Reciprocal Rank Fusion，按每个候选在不同检索通道里的名次累加分数。当前固定公式中的常量是 RRF=60

不直接把全文分数和余弦相似度加权相加，是因为它们的量纲和分布不同：全文分数会受词频和查询长度影响，向量相似度受模型和语料分布影响，直接相加很容易让某一路主导。RRF 只关心排名，相对更稳健。

融合是在每个来源内部发生：产品文档的全文与向量结果先融合、去重、取前 3；案例也独立执行同样过程、取前 3。每个通道先取最多 20 个候选，再做融合。
