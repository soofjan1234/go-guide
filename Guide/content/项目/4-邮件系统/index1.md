# 项目背景

这是一个面向 NAS 售后的邮件智能助手，结合知识检索与人工审核，为客服生成可追溯、可控风险的英文回复草稿。

## 主要是什么售后问题？

主要是硬件和系统相关问题，然后是设备的使用，接着是应用功能：

- 系统与固件：下载、升级、服务管理、Docker 功能。
- 设备使用：开机界面、网络连接、系统重建、数据迁移。
- 硬件与配件：硬盘稳定性、风扇噪音、触控笔配件。

## 数据

1. 邮件总共2000多份，800多配对，也就是500多待测邮件
2. 知识库有2000多个片段，主要是配对和8个产品文档
3. 上线一个月已经处理200多封邮件

## Agent 线上观测应该记录哪些指标？

1. 我会先看任务成功率和人工接管率，确认 Agent 到底能完成多少任务。
2. 再看总耗时，以及检索、模型、工具调用各阶段的耗时，重点关注 P95，定位慢在哪里。
3. 成本方面记录模型调用次数、Token 用量和重试次数。
4. 质量方面记录检索空结果、草稿校验失败，以及人工直接批准、修改后批准、拒绝的比例。

## 评估一个 RAG 系统

1. 检索层：在固定的脱敏邮件、知识库、分块与 Top-K 下，评估 Recall@K、MRR、型号/错误码 Top-K 命中率、无答案误召回率、P95 延迟。
2. 生成层：评估回答相关性、事实正确性、每条事实是否被引用片段支撑、错误引用率、无依据时是否主动追问信息或转人工、结构化输出与安全规则通过率。
3. 业务层：看人工直接批准／编辑后批准／拒绝比例、平均审核耗时、最终是否减少客服检索成本；同时监控模型或检索服务失败率、知识版本变更后的回归情况。

# 技术选型

## Http 框架

1. FastAPI 基于 ASGI，适合异步 HTTP 接口：邮件系统有大量外部IO，比如调用模型网关、查询PostgreSQL
2. FastAPI 是直接把 Pydantic 作为“底层基石”来构建的，可以统一处理参数校验

### 对比

1. Flask 更轻，但项目需要类型校验、OpenAPI、异步接口和较多业务契约。如果用 Flask，这些能力通常需要额外组合多个扩展；FastAPI 在这些方面提供了相对统一的默认方案
2. Django 的后台管理、ORM很成熟，对于当前项目可能稍重

## 数据库

PostgreSQL 同时承载：

- 邮件、审核、候选案例和审计等业务数据；
- LangGraph checkpoint、interrupt 和恢复所需的运行状态；
- 使用 `tsvector` 和 GIN 的关键词检索；
- 使用 pgvector 的向量语义检索。

选择 pgvector 的原因：业务数据本就需要 PostgreSQL，将向量存入同一数据库可以减少独立向量数据库、跨库同步和一致性处理

### 对比

1. SQLite：无服务器；单进程/线程内，库级写锁；弱类型；WAL 模式支持读写并发，但只支持单写
2. MySQL： 单进程多线程 模型；高级数据类支持有限；生态工具极丰富，DBA 好找
3. PostgreSQL：多进程 模型（每个连接一个进程）；最严格遵循 SQL 标准，功能最全面；基于 Tuple 多版本（堆内） 实现 MVCC；极强生态（插件机制，如 pgvector, PostGIS）

## 框架

本项目需要展示非线性的高级 RAG 工作流：
- 判断邮件类型
- 检索不相关时重写查询并再次检索
- 证据不足时补充检索或转人工
- 生成结果不合格时重新生成
- 超过重试上限后人工兜底
- 等待人工审核

# Embedding
## embedding 选型主要关注什么

看语言、文本长度、领域、向量维度、吞吐和成本

## 技术选型怎么做的

对比了 Qwen3 0.6B、Nomic v1.5、Snowflake Arctic M v1.5 和 BGE-M3 

1. 先做合成基准集：用固定的问题—知识片段构造测试集，保证知道每个 Query 应该召回哪个 Chunk，用来快速比较 4 个候选 Embedding 模型。
2. 再用真实邮件验证：把历史售后邮件作为 Query，在冻结知识库上实际检索，避免模型只在人工构造问题上表现好。
3. 比较的不只是准确率：主要看 Recall@K、MRR，同时记录 P95 latency 和内存占用。也就是同时考虑“能不能找到”“正确答案排得够不够前”“部署成本怎么样”。
4. 最终按实际业务效果选模型：不是单纯选择参数最大或者 Benchmark 分数最高的，而是在召回质量、延迟、资源消耗之间取适合本地部署的方案。

补充：
- Recall@K（召回率@K）：检索出的前 K 个结果中，有没有包含标准答案（Ground Truth）
- MRR（Mean Reciprocal Rank，平均倒数排名）：结果排好后，看第一个相关答案排在第几名。第 1 名得 1 分，第 2 名得 ½ 分，再对所有问题取平均。

## 合成集有什么？

合成基准集本质上是人为构造“Query → 正确知识”的标准答案集。

例如知识库有一个 Chunk：做了xxx，需要xxx，可以围绕它构造不同难度的 Query，也就是Query → 对于chunk_123

所以可以快速得出Recall、MRR

## 为什么不直接全部用历史邮件？

1. 真实邮件没有天然对应的“标准 Chunk ID”，手工标耗时极大，只能用模型快速标
2. 真实邮件高度遵循“二八定律”，80% 的客户都在反复咨询 20% 的常见问题
