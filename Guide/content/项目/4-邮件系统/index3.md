## 产品文档和历史案例为什么分路检索？

产品文档提供型号、版本、功能边界和排障步骤等事实依据；已审核案例提供客服表达方式、追问思路和处理经验

把它们混在一个池子里，案例的措辞可能压过官方事实，所以系统对两类来源分别做全文和向量检索，各自融合后最多保留 3 条，总数最多 6 条。

## 全文检索和向量检索各解决什么问题？

全文检索擅长精确词：型号、错误码、DSM 版本、命令和产品专有名词；向量检索擅长客户的口语化描述，例如客户没说‘挂载失败’，而是说‘电脑找得到 NAS，但打不开共享目录’。两路结合能减少任意一侧漏召回。

### 全文检索

```
search_vector = to_tsvector('english', content)
CREATE INDEX ... ON knowledge_chunks USING GIN(search_vector)
```

- `english` 是“分词和归一化规则”。它决定 content 怎样被处理成可检索的词项，例如去停用词、处理词形变化。
- `GIN` 是“索引结构”。它让 PostgreSQL 不必扫描每个文档片段，而是快速找到包含这些词项的行。

### 向量检索

```sql
embedding = EmbeddingModel(content)
SELECT ...
FROM knowledge_chunks
WHERE document_status = 'active'
  AND index_version = :current_index_version
ORDER BY embedding <=> :query_embedding
LIMIT 20;
```

- `EmbeddingModel` 会把文本转换成固定维度的浮点数向量。语义相近的文本，其向量距离通常更近；例如客户说“共享文件夹打不开”，可能召回写着 “SMB access failure” 的文档。
- `query_embedding` 是用同一模型把用户问题转换出来的查询向量。
- `<=>` 表示按余弦距离排序，距离越小，语义越相似。
- `active` 只查询已经审核发布、当前有效的知识文档，避免候选案例或历史归档内容参与回答。
- `index_version` 保证查询向量和文档向量来自同一套 Embedding 模型、版本、维度和模板；换模型后必须重建或重新嵌入，不能混合比较。
- 当前采用精确向量距离排序，结果稳定；数据规模增长后，可评估 pgvector 的近似索引以换取更低延迟。

## RRF 是什么，为什么用它融合？

RRF 是 Reciprocal Rank Fusion，按每个候选在不同检索通道里的名次累加分数。当前固定公式中的常量是 RRF=60

不直接把全文分数和余弦相似度加权相加，是因为它们的量纲和分布不同：全文分数会受词频和查询长度影响，向量相似度受模型和语料分布影响，直接相加很容易让某一路主导。RRF 只关心排名，相对更稳健。

融合是在每个来源内部发生：产品文档的全文与向量结果先融合、去重、取前 3；案例也独立执行同样过程、取前 3。每个通道先取最多 20 个候选，再做融合。

## 怎么判断“依据不足”或“资料冲突”？

当前判断分三层：

1. 硬规则先拦截
没有任何产品文档候选，就不允许生成确定性的技术处理方案；最多生成“依据不足，请人工核实”的草稿。

2. 模型输出结构化判断
模型需要给出知识状态、风险、引用片段等字段。例如标记为“依据不足”或“资料冲突”时，必须要求人工审核，不能直接走后续自动路径。

3. 后端校验引用边界
引用必须来自本次检索到的片段；而且型号、版本、命令等产品事实，必须引用产品文档，不能只引用历史案例。

## 防止邮件或检索文档中的提示注入

1. 邮件正文被明确视为不可信数据。系统提示词要求邮件不能改变系统规则，产品事实只能来自本次检索到的产品文档
2. 当前代码还会先用规则识别部分明显的英文提示注入模式，例如ignore previous/system.../reveal ... prompt
3. 人工审核通过后，后端才允许发送

## 哪些属于高风险问题？怎么识别？

高风险是可能造成数据、安全或不可逆影响的问题，例如存储池异常下继续写入、数据删除或恢复、账号权限变更、远程访问暴露、凭据泄露等

模型以结构化字段输出风险和 knowledge_status。当状态是 high_risk、资料冲突、无可靠依据或缺少必要信息时，不能给出确定性操作步骤，只能请求补充信息、提示风险或转人工

## 模型答非所问、引用错文档，你怎么判断是检索环节的问题还是生成环节的问题

| 现象 | 判断 | 优先排查 |
| --- | --- | --- |
| 正确文档不在 Top-K | 检索召回问题 | 查询改写、分块、Embedding、关键词/向量通道、过滤条件 |
| 正确文档在 Top-K 但排得靠后、没进最终上下文 | 排序/融合问题 | RRF 参数、各路候选数量、后续是否需要 Rerank |
| 正确文档已给模型，但回答仍答非所问或引用了另一篇 | 生成忠实性问题 | Prompt、上下文组织、模型能力、输出校验 |
| 引用了根本没检索到的文档 | 生成越界 | 应被后端拦截 |

## 评估一个 RAG 系统

1. 检索层：在固定的脱敏邮件、知识库、分块与 Top-K 下，评估 Recall@K、MRR、型号/错误码 Top-K 命中率、无答案误召回率、P95 延迟。
2. 生成层：评估回答相关性、事实正确性、每条事实是否被引用片段支撑、错误引用率、无依据时是否主动追问信息或转人工、结构化输出与安全规则通过率。
3. 业务层：看人工直接批准／编辑后批准／拒绝比例、平均审核耗时、最终是否减少客服检索成本；同时监控模型或检索服务失败率、知识版本变更后的回归情况。

## 向量检索召回率低怎么优化

查询，不是先换模型。 Graph 已有有上限的 query rewrite。一封信两个互不相关的故障，单向量几乎只会贴其中一个（评测里 DDNS + CGNAT 就是这类）。先拆成多次检索再合并，比加大 K 更有效。查询侧要用 embed_queries，文档侧用 embed_documents，前缀和角色不要混。

切分和入库。 按标题/段落切、超长再拆，这是对的；若答案和适用条件（型号、版本、RAID 级别）不在同一片段，向量会漂到同类故障。优先让「现象 + 结论 + 约束」同块，而不是盲目加大 max_tokens。换模型或维度必须新建索引并全量重嵌，不能混在同一列。

用关键词补精确标识。 NAS 标识、错误码、协议名本来就该走受保护全文，不要指望向量分清 RAID5 / RAID6。检查 normalize_query 有没有把标识切碎；自然语言词用 OR 是为了避免多余词把全文整段滤掉，不要改成必须全词匹配。

再考虑调参。 技术选型写明：没有保留集对比，不改 RRF_K、每路 20、每源 3。召回尚可但前三名经常排错，才测重排；先加 Cross-Encoder 解决不了「相关片段根本不在 20 条里」。HNSW 只在规模和 P95 成为瓶颈时再比，MVP 精确余弦是为了不把漏召回赖给近似索引。

最后才换 Embedding。 扩展集上 Snowflake 产品/回复 R@3 已是 100%，换模型解决不了「真实邮件和合成夹具分布不同」。真邮件召回低，优先补真实标注集，而不是在合成集上继续刷分。

### 有什么方法

1. 有标准答案时：代码直接跑
    - 原理：评测集里每条 Query 已经天然或人工绑定了命中片段的 ID
2. 人工标注
    - 原理：由业务专家或标注人员，人工阅读「Query vs 候选片段」，判定 Relevant (1) 或 Not Relevant (0)。
3. LLM / Agent 当裁判
    - 原理：由强模型/Agent 充当 Judge，审查检索出来的片段并打标，以此计算代理 Recall
4. 间接指标 / 端到端业务指标
    - 原理：不纠结于底层具体召回了哪条 chunk，而是关注系统最终交付的效果。
