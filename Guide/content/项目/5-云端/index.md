# 一、穿透
## 客户端、服务端、云端及穿透端的通信流程

**情境** 

1. 核心问题是 NAT 会拦截无状态入站流量：内网设备只有先出站建立映射，外部回包才进得来
2. 所以要进行双方通信，会通过P2P穿透，那要进行穿透就得知道对方的公网地址
3. 而我负责的项目主要是信令服务器，在双方还没建立起直连通道之前，提供一个互相交换信息的媒介

**角色**

- 客户端：手机
- 服务端：nas
- 云端：我负责的项目，信令服务器
- 穿透端：公网上的"穿透服务器"

**链路**

1. 首先，都在同一局域网的时候，手机点击开启穿透，nas会请求云端领一些东西
    1. 穿透凭证，用于nas开启穿透
    2. 验证码，用于手机向云端获取信息，在明，可展示给用户
    3. 校验码，用于验证身份
2. 然后nas会拿着穿透凭证，去公网上的"穿透服务器"那里注册或创建会话
3. 手机现在在外面了，把验证码给云端，问他这人在哪，云端查到后就给他穿透测入口，并给他校验码
4. 最后就是完成身份校验与通道建立

## 怎么得到的公网 IP 地址和端口？

1. 在原理中，是通过stun服务器获取的，设备发送 Binding 请求，STUN 服务器把它观察到的公网 IP 和端口返回给设备
2. 在我们的实现中，客户端不需要得到公网地址，只需要知道对端是谁，然后调用穿透sdk封装了ConnectAdd即可

## 手机上的 HTTP 请求如何找到 NAS 上的服务

手机用这个 peerID 和 accessVerify 调 pgJniTunnel.ConnectAdd 建立映射

1. 在局域网内，手机可以用 NAS 的局域网 IP 访问 50080 端口。
2. 到了外网，手机先通过穿透 SDK 建立一条到 NAS 的通道。
    - SDK 同时在手机本地监听 127.0.0.1:50080。
    - App 请求这个本地端口后，SDK 把请求沿通道转给 NAS 的 50080 服务，再把响应传回来。
    - 所以地址看起来没变，是因为手机本地多了一个“转发入口”，不是 NAS 的 127.0.0.1 跑到了手机上。

# 二、加密
## 为什么要加密

若在 VPN 场景，常见链路是：`设备 -> [VPN 隧道] -> VPN 节点 -> [公网 TLS] -> Cloudflare`。

有些公司或特殊网络会要求在设备上安装其自有根证书（Root CA）。此时需注意：

- 一旦你信任了该根证书，VPN/代理节点理论上可以做“解密后再加密”（TLS 卸载 / 中间人代理）。
- 建立了两次独立的 HTTPS/TLS 连接

## 双方加密流程

角色是Host设备和云端通信

1. Host设备rand生成AES密钥，使用AES-GCM加密明文，得到data,nonce
2. Host设备使用**云端**的RSA公钥加密AES密钥，得到key
3. Host设备将data,nonce,key发送给云端

4. 云端调用DecryptAESString，使用**云端**RSA私钥解密key，得到AES密钥
5. 云端使用AES密钥解密data,nonce，得到明文
6. 云端调用EncryptAESString，再生成新AES，使用**Host**的RSA公钥加密返回

7. Host端用**自己**的RSA私钥解密AES密钥，再解密响应

## 云端、Host端私钥如何保存？

云端：

1. 托管在云端KMS中，私钥在 KMS 内部生成，物理锁死，没有任何 API 能导出私钥明文。
2. 需要解密或签名时，通过 IAM 角色授权，调用 KMS 接口在 KMS 内部完成，Go 服务只接收结果

Host：

1. 存在磁盘上，但是被加密锁死的。采集 Host 端的硬件唯一指纹（如：CPU 序列号 + 主板 UUID + 网卡 MAC 地址）融合成一个解密 Key。
2. 启动 Go 服务读取本机硬件指纹 -> 计算解密 key -> 读取磁盘上的私钥密文 -> 在内存中解密出私钥 -> 用私钥做签名/解密
3. 磁盘上始终没有私钥明文

## 公钥如何分发？

1. Host 首次启动，在本地生成 host 公私钥。
2. Host 联网后把 host_public_key 上报给 Cloud。
4. Cloud 验证通过后，保存 sn -> host_public_key。
5. Cloud 把 cloud_public_key 或 cloud 证书链返回给 Host。
6. Host 保存 cloud_public_key，用于后续验签或加密。

### 初次验证

1. 每台 Host 出厂时内置一个设备证书和设备私钥，Cloud 预先信任厂商 CA。
2. 初次验证会发请求：SN、host_public_key、device_cert、signature
3. Cloud 验证：
    - device_cert 是不是厂商 CA 签发的
    - cert 里的 SN 和上报 SN 是否一致
    - signature 能不能用 device_cert 里的 public key 验过
    - timestamp / nonce 防重放

# 三、设计核心

## 1. 先定要解决什么

- 核心矛盾：NAS 在内网，外网手机**不能直连**
- 产品目标：C 端用户远程访问

## 2. 拆成子问题

### 使用什么穿透技术？NAT怎么打通

1. WebRTC ICE：标准思路，兼顾成功率与成本
    - 先 STUN 打洞，失败再 TURN 兜底。
2. 端口映射：门槛高、安全风险大：公网少，直接暴露端口
    - 端口映射是在网关上做 DNAT，外网直达 NAS。
    - UPnP 是自动要这条 DNAT
2. VPN：粒度更大、部署更重
    - 在手机和 NAS 侧（或 VPN 服务器）之间建一条网络层隧道，连上后手机相当于进了内网网段，。
3. 纯云端反向代理：和turn类似，多一跳，没有能直连就直连
    - 内网 NAS 作为客户端，主动连公网上的中继服务器，服务器暴露一个公网入口，外网用户连服务器，服务器把流量转发给 NAS
4. 自建打洞：运维和客诉成本高
    - 要自己处理各种 NAT 类型、超时、重试、日志

### 双方如何找到对方

1. **向日葵邀请码**：用户心智成熟，「输入数字远程访问」，不需要账号体系
2. **开源双用户系统方案**：云端一套账号、NAS 一套账号——功能全但各端代码多、边界 case 多，**否决**

# 其它

## 手机突然连不上 NAS，如何逐段定位？

1. **先分局域网和外网**：确认手机网络正常。同一局域网先请求 NAS 的局域网 IP:50080；如果也失败，优先查 NAS 网络和网关服务。
2. **查云端信令**：外网访问时，确认手机能用访问码从云端取得 peerID 和校验信息，区分访问码或云端接口问题。
3. **查手机侧映射和穿透连接**：确认 SDK 已建立到目标 peerID 的连接，手机本地 127.0.0.1:50080 能否连通；结合 SDK 状态判断是连接建立失败，还是建立后断开。
4. **查 NAS 侧**：确认穿透服务仍在线、身份校验通过，并在 NAS 本机请求 127.0.0.1:50080。若本机请求失败，问题在 NAS 网关或业务服务；若本机正常而手机不通，重点查隧道和网络切换后的重连。

最后对照手机、云端、NAS 同一时段的请求和错误日志，定位请求停在哪一段。SDK 内部打洞及中继选择，以它提供的状态和日志为准。
