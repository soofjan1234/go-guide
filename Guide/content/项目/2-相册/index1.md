# 模糊

一个图片越清晰，边缘就锋利，那么拉普拉斯方差通常更大，所以可以用一个阈值快速判断清晰度。

除此之外还可以使用 Sobel 等梯度方法，还可以训练 CNN 模型直接输出图像清晰度评分。拉普拉斯方差最简单高效

## 拉普拉斯方差

1. 拉普拉斯算子：负责找“边缘”
    - 图像处理中的二阶微分算子（求二阶导数）。
    - 物理意义：它对图像中像素灰度发生**剧烈变化的地方（即边缘、纹理、轮廓）**极度敏感。
        - 清晰图像：边缘锐利，像素明暗跳变大，经过拉普拉斯卷积后，边缘处会产生极大的正值和极大的负值。
        - 模糊图像：边缘被抹平（平滑过渡），像素变化平缓，经过拉普拉斯卷积后，所有响应值都接近 0。
2. 方差（Variance）：负责统计“响应的剧烈程度”
    - 方差衡量的是一组数据的离散程度（波动大小）。

常用的 3×3 拉普拉斯卷积核：
```
0  1  0
1 -4  1
0  1  0
```

## 并行处理

1. 先决定开多少个消费者：min(CPU 核数, 8, 图片数量)
2. 再决定有上限的任务队列：jobs := make(chan blurJob, workers*2)
    - 图片可能有几千、几万张，放全部占内存
    - 太小，例如 workers：队列很快满，投递方经常阻塞。
3. 生产者发送任务；消费者并行干活：读取、解码图片，再计算清晰度/模糊度
4. 遍历slots，顺序添加到数据库里
6. 支持取消：函数不断检查 ctx.Err()

## 单 Writer 批量写库

1. 为什么是单 writter
    - SQLite 的 WAL 模式允许读写并发，但同一数据库在同一时刻仍只有一个 Writer 能写；多个 Writer 会争用写入机会，不能同时提交
    - 实验也证明多writer写入反而变慢
2. 批量写多少，为什么是100
    - 因为主要链路的阻碍点不在这
    - 我测了 25、50、100、200、500 条，两者约 **4.429 s 和 4.428 s**，没有可辨认的稳定收益。所以目前保留 100

# 相似检测

1. 传统哈希（MD5 / SHA）：

一张图片，只要修改其中 1 个像素的颜色，生成的 MD5 就会天翻地覆、完全不同。它用来验证“绝对一致性”，无法感知“长得像不像”。

2. 感知哈希（pHash / dHash / aHash）：

它会主动扔掉微观噪点和色彩细节，只提取图像的“宏观结构骨架”。如果两张图视觉上长得很像，生成的 64 位二进制指纹（如 11001010...）绝大部分位就会是一模一样的。

图片解码轻量，pHash、dHash可缓存。SIFT/ORB 局部特征匹配太重，深度学习提取图片 Embedding要占算力和存储

## 算法要点

1. 感知哈希

例如 aHash、dHash、pHash，通过生成视觉特征哈希并计算汉明距离判断相似度；
- aHash (Average Hash - 平均哈希)：极快，比较扁平，适合粗筛
- pHash (Perceptual Hash - 感知哈希)：它更关注图片整体视觉特征，速度一般，免疫一定程度的裁剪
- dHash (Difference Hash - 差异哈希)：更关注图片局部特征，对比的是相邻像素的“相对差值”，适合连拍照片

2. 汉明距离

汉明距离就是统计两个等长二进制串中，有多少个对应位置的 bit 是不相同的（异或操作 XOR 后数 1 的个数）。

例如两张图算出来的 8 位 Hash：
```
图 A：1 1 0 0 1 0 1 0
图 B：1 1 0 0 1 1 1 0（仅第 6 位不同）
汉明距离 = 1。
```

## 流程

1. 每张清晰照片准备 dHash、pHash、原图宽高和清晰度分数。
2. 先与已有相似照片组比对：相似加入该组，不再参与后续分组。组内有清晰照片时，选择清晰度最高的照片作为 keeper。
3. 相似规则：
    - 两侧尺寸都已知时，要求 abs(宽A/高A - 宽B/高B) <= 0.05，这是宽高比的绝对差
    - dHash 汉明距离不超过 4，并且 pHash 汉明距离也不超过 4，两关都通过才认为相似。

## 定位瓶颈

1. 起初看到两层循环，怀疑几千张照片的比较拖慢了扫描；最坏情况下确实是 O(n²)。
2. 3000 张扫描 13.914 分钟，其中比对含进度仅 1.962 秒；哈希准备 5.654 分钟、重复结果保存 4.929 分钟才是主要耗时。

## 解决方案

1. 原来逐条保存重复组及成员，有多少个组员就有多少次创建操作。改为按完整组分批，在一个事务中批量插入；失败时回滚当前批，保证组和成员完整
2. 原来是每10张就更新数据库的进度。改为每10张就看是否符合条件
    - 距离上次写库，有没有过去至少 2 秒？进度有没有增长至少 1 个百分点？
3. 优化前，同一张清晰照片会经历两次解码：一次是模糊评分，一次是哈希计算。
    - 改为在同一个 worker 中流水处理，清晰照片只解码一次，先算模糊分数，再算哈希。
    - JPEG 文件存的是压缩数据，算法不能直接把它当像素使用。程序需要读取文件，把压缩数据还原成内存中的像素，这就是解码

3000 张板端全量从早期约 14 分钟降到最新约 4 分 27 秒
