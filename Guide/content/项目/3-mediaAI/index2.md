## 正常流程

```
ACQUIRE
  ├─ 可立即授权 ──────────→ GRANTED
  └─ 需要排队 → QUEUED
                  ├─ 等到授权 → GRANTED
                  └─ 等待超时 → TIMEOUT（结束）

GRANTED → 执行推理
  ├─ 正常完成 → RELEASE
  └─ 租约到期 → EXPIRED（进入回收流程）
```

## 等待超时

```
SDK 先发现超时：SDK → CANCEL → ai-control-svc 清理申请
服务先发现超时：ai-control-svc 清理申请 → TIMEOUT → SDK 结束等待
```

因为 SDK 和 ai-control-svc 是两个独立运行的进程。即使看的是同一个截止时间，线程调度、消息传输也有延迟，所以谁先发现超时不固定

## 授权与取消同时发生

```
SDK                         ai-control-svc
等待到期                     已发出 GRANTED
  ────── CANCEL ──────────→ 发现已授权，进入回收
  ←───── GRANTED ───────── 收到迟到授权
  ────── RELEASE ─────────→ 归还租约
向业务返回超时
```

## 心跳延迟，误回收怎么办

1. 使用unix domain socket，降低了常规延迟
2. 租约时长会大于续约间隔，比如 30 秒租约、10 秒续约，并使用单调时钟判断是否真正过期。  
3. 每个租约都带 lease ID，租约过期并重新分配后，旧持有者后续的续约、释放或执行请求都会因为 lease ID 不匹配被拒绝，不能影响新持有者。

## 心跳活着，推理已死

短任务不用心跳，语音长任务有最长时长限制

## 断联，调度器重启之后

```
排队 → 占用落盘 → 授权送达 → 执行推理 → 推理结束 → 释放落盘
          ↑                                          ↑
       开始保留占用                            可以重新授权
```

| 重启时的位置 | 重启后可能看到什么 | 怎么处理 |
| --- | --- | --- |
| **排队中，占用尚未落盘** | 排队请求丢失，没有旧占用 | 客户端重连重新排队 |
| **占用已落盘，授权是否送达不确定** | 有占用记录，但不知道 worker 是否开始执行 | 进入 `RECOVERING`，与旧 owner 对账，核对 PID、启动时间、client、request_id |
| **授权已送达，推理尚未结束** | 旧 worker 可能正在执行，也可能尚未提交 | 保留占用；按租约策略恢复，或终止旧 worker 并确认设备安全 |
| **推理已结束，释放尚未落盘** | NPU 可能已经空闲，但记录仍显示占用 | owner 重发原 `RELEASE`，确认后清占用 |
| **释放已落盘** | 记录为空，或者下一任务的占用已经落盘 | 以最新持久化记录为准；旧 `RELEASE` 不得影响新租约 |

如果推理服务在持有租约后崩溃，无法主动发出 RELEASE，应由调度器发现进程退出并回收：
  - 调度器定期检查租约里记录的 PID 和进程启动时间。

## 超时回收，但npu依旧在用

如果rknnrun一直占用 导致超时 即使调度器强行回收 npu依旧被霸占:
1. 首先这种情况极少发生 超时并且rknn那边没捕获到错误
    - Rockchip 官方的 RKNPU 内核驱动在提交硬件任务时，内部本身就挂了带有超时时限的等待队列（一般是 3~5 秒）
    - 如果硬件真挂死了，驱动自己大概率会超时抛错返回，rknn_run 绝大多数情况下都会返回一个错误码（如 RKNN_ERR_FAIL），而不会无限期挂死。无限挂死往往只出现在驱动极低概率的死锁、或者内存破坏踩了内核态这种极端边界场景。
2. 我们可以sigkill该进程 或者把worker放子进程里杀死子进程
