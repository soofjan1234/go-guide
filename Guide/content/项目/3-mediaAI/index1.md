# 算法
## RKNN 平台是什么？和你的 NAS 有什么关系？

RKNN 是瑞芯微的模型转换工具链和设备侧推理运行时。当前 MediaAI 面向 RK3576：独立的 `rknn-ai-svc` 在设备上调用 RKNN Runtime 执行模型，上层通过服务接口请求分析；NPU 资源由 `npu-scheduler` 协调。

RK3576 的标称 NPU 算力为 6 TOPS。

## 人脸检测和识别的流程

1. 用 YuNet RKNN 模型检测人脸；对检测结果做 CPU 对齐。
2. 用 MobileFaceNet 提取 512 维特征向量并归一化。YuNet 和 MobileFaceNet 分别执行一次 NPU 推理，中间的 CPU 对齐不占租约。
3. 将向量与当前模型版本、聚类代际下的所有有效 cluster 中心比较；符合合入条件就归入已有 cluster，否则创建新 cluster。
4. 合入后按已有 `face_count` 加权更新中心，再做 L2 归一化。中心代表已有样本的平均方向，但错误合入仍可能污染中心。

## 为什么使用这个聚类？

相册的照片会持续增加，不能每来一张就重算全部人脸。当前规则逐张分配：对归一化向量计算到各中心的余弦距离 `1 - clamp(cosine, 0, 1)`，再决定合入或新建 cluster。它能增量处理，但结果受模型质量、阈值和输入顺序影响。

## 怎样避免把两个人合并？

同时检查距离与区分度：最佳距离必须不大于 `0.50`，并且次佳距离减最佳距离至少为 `0.08`；否则新建 cluster，不强行归入最接近的人。还要按模型版本和聚类代际隔离中心，避免不同特征空间混用。这些规则降低误合并风险，不保证误合并为零。

## 数据集

人脸：
1. 人脸检测用了 WIDER val 全量 3226 张
2. 人脸识别/验证 LFW (Labeled Faces in the Wild) 人脸识别数据集 1000 pairs

检测指标是：
 - recall：真实目标有多少被找到了; 
 - precision：检测出来的人脸有多少是真的；
 - AP：综合结果
 - 通用性能：内存、cpu、峰值、耗时

 ## 自己建立数据集该怎么做

1. 先明确任务和业务场景。比如是做人脸检测、人脸识别；室内还是室外、光照如何，是否有遮挡、模糊特殊情况。

2. 基于真实业务分布采集数据，可以来自用户授权数据、内部测试采集、公开数据集补充和合成增强。

3. 制定标注规范。检测任务标人脸框、关键点、遮挡、模糊、姿态等；

4. 最后划分`train`（训练集）、`val`（验证集）、`test`（测试集）。

# NPU调度

以下交互按当前 MediaAI 工作区代码和设计描述；相关 Linux 测试、构建不能代替完整服务联调或 RK3576 板端验收。

## 架构

- ai-manager：负责服务的启停，模型的管理
- npu-scheduler：NPU 租约、优先级与资源准入
- 推理服务：持有模型，完成输入校验、推理、后处理

相册发起分析请求，`rknn-ai-svc` 执行分析并返回结果；每次实际运行 NPU 模型前，推理服务向 `npu-scheduler` 申请租约。调度器只负责准入，不加载模型或传输推理输入。

面试官问“是不是微服务”时，可说这是部署在同一设备上的独立进程和服务边界；重点是模型管理、资源准入、推理执行的职责分离，不把进程拆分本身当作完整的微服务治理。

## 优先级

选择规则依次是：

1. 先选最高优先级；
2. 若有不同 PID 的 P0 同时等待，刚刚获批的 P0 PID 不能连续再次获批；
3. 在剩余候选中，deadline 更早者优先；
4. deadline 相同，再按先入队者优先。

它一次只维护一张 active lease，目标是让遵守协议的服务不同时进入 NPU 推理。当前严格优先级保证 P0 先于相册 P3；如果 P0 持续到来，P3 可能等待到截止时间，不能承诺它一定及时获批。

## 交互

`rknn-ai-svc` 执行 YuNet 前，向 `npu-scheduler` 发送一次 `ACQUIRE`：

| 参数 | 示例 | 含义 |
| --- | --- | --- |
| `pid` | 服务当前进程号 | 租约持有者；调度器还会核对连接的真实进程身份 |
| `request_id` | `abc-123:yunet` | 标识这一次模型调用 |
| `client` / `workload` | `rknn-ai` / `yunet` | 调度器据此校验工作负载并确定优先级 |
| `deadline` | 单调时钟截止时间 | 限制**等待和接受授权**的时间，不截断已开始的 `rknn_run` |

```text
A 持有租约，正在执行 rknn_run
B 发送一次 ACQUIRE → 调度器将 B 入队并回复 QUEUED
B 保持连接等待，不重复发送 ACQUIRE
A 发送 RELEASE → 调度器先持久化空占用记录
调度器选中 B → 先持久化 B 的占用记录，再主动推送 GRANTED
B 在等待期限内收到授权 → 执行 rknn_run，完成后 RELEASE
```

等待超时时，调度器可发 `TIMEOUT`，客户端也可发 `CANCEL`；超时与授权竞争时，客户端只能接受其中一个结果，迟到的授权要归还。断连或授权是否送达不确定时，调度器进入 `RECOVERING`，确认旧持有者状态前不再授权下一位。YuNet 检测完成并释放租约后，MobileFaceNet 特征提取再独立申请一次租约。

## 心跳和超时回收

这里的“心跳”是持有者在推理期间发送 `RENEW`。当前白名单工作负载的获批租约窗口为 30 秒；执行器按窗口的一半、且最多每 10 秒续一次。申请中的 `deadline` 只限制排队与接受授权，不截断已开始的 `rknn_run`，调度器也不因原请求的等待截止时间到达就直接拒绝有效持有者续租。

- 租约到期或连接状态不确定：调度器保留占用记录并进入 `RECOVERING`，暂停新授权；同一持有者可凭原租约对账，不能直接把 NPU 当作空闲。
- 确认持有进程已退出：核对 PID 和进程启动时间后，先将空占用记录持久化，成功后才允许调度下一项。
- 正常执行结束：持有者以原 `lease_id` 发送 `RELEASE`。释放未确认时保留待释放状态并重试；达到重试上限仍不能确认时报告故障，不能直接申请新租约。

## 心跳延迟，误回收怎么办

不能只回答“Unix domain socket 很快”。即使续租延迟导致租约到期，调度器也不会马上发放第二张，而是进入 `RECOVERING` 并保留原占用；原持有者可用相同 `lease_id` 和进程身份恢复续租或完成释放。若无法确认它是否仍在执行，就继续阻塞新授权。

租约 ID、调度器 epoch 和进程身份用于协议校验，但当前没有能拦住底层 `rknn_run` 的 fencing 闸门。已获批的旧进程仍可能继续执行，因此安全边界是先确认旧进程退出或完成释放，再给下一位授权。

## 怎么证明这次调度交互优化有效？

旧交互涉及短连接轮询；当前方案改为一次 `ACQUIRE`、保持 UDS 连接等待调度器推送 `GRANTED`。验证时应在相同负载下比较连接次数、进程 CPU/唤醒次数，以及 `RELEASE` 到下一次 `GRANTED` 的延迟分布。当前相关 Linux 测试和服务构建只能证明对应本地路径，完整联调、板端运行和优化幅度需要另行验收。
