## 为什么使用C++

MediaAI 主要负责模型推理和 NPU 调度。我们调用的 RKNN Runtime 提供的是 C 接口，用 C++ 对接比较直接，也方便复用 OpenCV 等图像处理库

# 算法
## 人脸检测和识别的流程

1. 人脸检测：使用 yunet rknn 模型，返回人脸的位置信息
    - retinaface速度快，但漏检多；scrfd误检偏多
2. 识别：使用了 mobileFaceNet 模型 ，并提取人脸特征向量
    - sface rknn 精度一般；arcface、iResNet 速度不如 mobileFaceNet
3. 和所有已有 cluster 中心比较，合并到最像的人 / 创建新 cluster
4. 合入后，做累计平均，再做一次 L2 归一化
    - 一个 cluster 的中心会随着同一人不同角度、光线、年龄阶段的照片逐渐稳定，而不是被某一张极端照片带偏

### 余弦距离是什么

模型将人脸转换为特征向量，通过比较向量方向来衡量两张人脸的相似程度。

余弦相似度的公式是 `s = (x · y) / (||x||₂ × ||y||₂)`，越大越相似；常用的余弦距离是 `d = 1 - s`，越小越相似。

### L2 归一化是什么，有什么作用？

L2 归一化就是把向量除以自身长度。归一化后长度为 1，方向不变；两个归一化向量的余弦相似度可以直接通过点积计算。

## 为什么不使用其他聚类算法？

相册的特点是照片持续新增、人物数量未知，需要增量处理。基于人物中心和阈值的在线聚类比较适合这一需求：每张新照片与现有人物中心比较，满足条件就更新中心，否则建立新人物，无需每次重新处理整个相册。

K-means 通常需要预先指定人物数量，而相册人物数未知 

DBSCAN 标准算法按数据集计算；增量更新需要额外机制；min_samples > 1 时，孤立照片可能成为噪声

## 怎样避免把两个人合并？

同时检查距离与区分度：最佳距离必须不大于 `0.50`，并且次佳距离减最佳距离至少为 `0.08`；否则新建 cluster，不强行归入最接近的人。

## 数据集

人脸识别/验证 LFW (Labeled Faces in the Wild) 人脸识别数据集 1000 pairs

检测指标是：
 - recall：真实目标有多少被找到了; 
 - precision：检测出来的人脸有多少是真的；
 - AP：综合结果
 - 通用性能：内存、cpu、峰值、耗时

 ## 自己建立数据集该怎么做

1. 先明确目标。比如是做人脸检测、人脸识别；室内还是室外、光照如何，是否有遮挡、模糊特殊情况。
2. 采集数据，可以来自用户授权数据、内部测试采集、公开数据集补充。
3. 制定标注规范。检测任务标人脸框、关键点、遮挡、模糊、姿态等；
4. 最后划分`train`（训练集）、`val`（验证集）、`test`（测试集）。

# NPU调度

以下交互按当前 MediaAI 工作区代码和设计描述；相关 Linux 测试、构建不能代替完整服务联调或 RK3576 板端验收。

## 架构

- ai-manager：负责服务的启停，模型的管理
- npu-scheduler：NPU 租约、优先级与资源准入
- 推理服务：持有模型，完成输入校验、推理、后处理

相册发起分析请求，`rknn-ai-svc` 执行分析并返回结果；每次实际运行 NPU 模型前，推理服务向 `npu-scheduler` 申请租约。调度器只负责准入，不加载模型或传输推理输入。

## 优先级

选择规则依次是：

1. 先选最高优先级；
2. 若有不同 PID 的 P0 同时等待，刚刚获批的 P0 PID 不能连续再次获批；
3. 在剩余候选中，deadline 更早者优先；
4. deadline 相同，再按先入队者优先。

它一次只维护一张 active lease，目标是让遵守协议的服务不同时进入 NPU 推理。当前严格优先级保证 P0 先于相册 P3；如果 P0 持续到来，P3 可能等待到截止时间，不能承诺它一定及时获批。

## 交互

`rknn-ai-svc` 执行 YuNet 前，向 `npu-scheduler` 发送一次 `ACQUIRE`：

| 参数 | 示例 | 含义 |
| --- | --- | --- |
| `pid` | 服务当前进程号 | 租约持有者；调度器还会核对连接的真实进程身份 |
| `request_id` | `abc-123:yunet` | 标识这一次模型调用 |
| `client` / `workload` | `rknn-ai` / `yunet` | 调度器据此校验工作负载并确定优先级 |
| `deadline` | 单调时钟截止时间 | 限制**等待和接受授权**的时间，不截断已开始的 `rknn_run` |

```text
A 持有租约，正在执行 rknn_run
B 发送一次 ACQUIRE → 调度器将 B 入队并回复 QUEUED
B 保持连接等待，不重复发送 ACQUIRE
A 发送 RELEASE → 调度器先持久化空占用记录
调度器选中 B → 先持久化 B 的占用记录，再主动推送 GRANTED
B 在等待期限内收到授权 → 执行 rknn_run，完成后 RELEASE
```

等待超时时，调度器可发 `TIMEOUT`，客户端也可发 `CANCEL`；超时与授权竞争时，客户端只能接受其中一个结果，迟到的授权要归还。断连或授权是否送达不确定时，调度器进入 `RECOVERING`，确认旧持有者状态前不再授权下一位。YuNet 检测完成并释放租约后，MobileFaceNet 特征提取再独立申请一次租约。

## 心跳和超时回收

这里的“心跳”是持有者在推理期间发送 `RENEW`。当前白名单工作负载的获批租约窗口为 30 秒；执行器按窗口的一半、且最多每 10 秒续一次。申请中的 `deadline` 只限制排队与接受授权，不截断已开始的 `rknn_run`，调度器也不因原请求的等待截止时间到达就直接拒绝有效持有者续租。

- 租约到期或连接状态不确定：调度器保留占用记录并进入 `RECOVERING`，暂停新授权；同一持有者可凭原租约对账，不能直接把 NPU 当作空闲。
- 确认持有进程已退出：核对 PID 和进程启动时间后，先将空占用记录持久化，成功后才允许调度下一项。
- 正常执行结束：持有者以原 `lease_id` 发送 `RELEASE`。释放未确认时保留待释放状态并重试；达到重试上限仍不能确认时报告故障，不能直接申请新租约。

## 心跳延迟，误回收怎么办

1. 使用unix domain socket，降低了常规延迟
2. 租约时长会大于续约间隔，比如 30 秒租约、10 秒续约，并使用单调时钟判断是否真正过期。  
3. 每个租约都带 lease ID 和递增的 fencing token。租约过期并重新分配后，旧持有者后续的续约、释放或执行请求都会因为 lease ID 或代际不匹配被拒绝，不能影响新持有者。
