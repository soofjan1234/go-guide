正常流程：

```
ACQUIRE
  ├─ 可立即授权 ──────────→ GRANTED
  └─ 需要排队 → QUEUED
                  ├─ 等到授权 → GRANTED
                  └─ 等待超时 → TIMEOUT（结束）

GRANTED → 执行推理
  ├─ 正常完成 → RELEASE
  └─ 租约到期 → EXPIRED（进入回收流程）
```

超时：

```
SDK 先发现超时：SDK → CANCEL → ai-control-svc 清理申请
服务先发现超时：ai-control-svc 清理申请 → TIMEOUT → SDK 结束等待
```

因为 SDK 和 ai-control-svc 是两个独立运行的进程。即使看的是同一个截止时间，线程调度、消息传输也有延迟，所以谁先发现超时不固定

授权与取消同时发生
```
SDK                         ai-control-svc
等待到期                     已发出 GRANTED
  ────── CANCEL ──────────→ 发现已授权，进入回收
  ←───── GRANTED ───────── 收到迟到授权
  ────── RELEASE ─────────→ 归还租约
向业务返回超时
```

如果推理服务在持有租约后崩溃，无法主动发出 RELEASE，应由调度器发现进程退出并回收：
应同时核对：
- PID：哪个进程。
- 进程启动时间（starttime）：是不是原来的那次进程实例。

如果是调度器崩溃
→ 调度器重启
→ RECOVERING（恢复租约记录，核对原持有者）
    ├─ 原持有者存活、租约有效 → 恢复原租约
    ├─ 原持有者已退出 → 回收
    └─ 租约已到期 → 停止原占用并回收
→ 确认占用状态后，恢复正常调度

授权或释放、取消请求已经处理，但对端收不到响应:
发送请求 → 响应正常 → 进入确定状态
        └─ 断连／响应超时 → UNKNOWN（结果未知）
                            → 用原标识核对或重试
                            → 进入确定状态

如果rknnrun一直占用 导致超时 即使调度器强行回收 npu依旧被霸占:
1. 首先这种情况极少发生 超时并且rknn那边没捕获到错误
    - Rockchip 官方的 RKNPU 内核驱动在提交硬件任务时，内部本身就挂了带有超时时限的等待队列（一般是 3~5 秒）
    - 如果硬件真挂死了，驱动自己大概率会超时抛错返回，rknn_run 绝大多数情况下都会返回一个错误码（如 RKNN_ERR_FAIL），而不会无限期挂死。无限挂死往往只出现在驱动极低概率的死锁、或者内存破坏踩了内核态这种极端边界场景。
2. 我们可以sigkill该进程 或者把worker放子进程里杀死子进程
