# 文件索引同步器
## 为什么不用fsnotify

1. 原因是 fsnotify 在目录规模上来后 watcher、句柄 数量多、内存压力大，而且有漏事件，稳定性不够。
2. 我们改成先做目录快照比对，再把新增/修改/删除投递到队列，worker 批量写库。
3. 这样实时性弱一点，但准确性和资源可控性更好，整体更适合我们的场景

## fsnotify的原理

1. 创建一个实例（拿到一个 fd 文件描述符）。
2. 派哨兵去盯具体目录/文件（每个 Watch 都耗内核内存）。
3. 出事了内核往 fd 里塞事件，Go 读出来消费。

### 三大系统底层差异

| 系统 | 底层 API | 核心差异 |
| :--- | :--- | :--- |
| **Linux** | `inotify` | **盯单点**：每个文件/目录都要单独设哨兵（文件一多吃爆内存）。 |
| **macOS** | `FSEvents` | **查日记**：直接读文件系统日志，天生自带递归，省资源且极快。 |
| **Windows** | `ReadDirectoryChangesW` | **填水池**：内核往你申请的内存缓冲区（Buffer）里塞事件，异步读取（IOCP）。 |

## 实验对比怎么做的

通过不同的目录树，比如占用500-1-2GB。

Go 堆仍用 runtime.ReadMemStats().HeapAlloc；RSS 则读取本进程 /proc/self/status 中的 VmRSS

Go 堆看程序在采样时持有多少 Go 对象，便于比较算法自身的内存开销；RSS 看进程当时实际驻留在物理内存中的页面，更接近设备承受的进程内存压力

Go 堆只数进程里由 Go 管理的对象，比如路径字符串、队列、监听状态。RSS数操作系统当前放在物理内存里的这个进程的页面，还包括 Go 堆以外的进程内存。Go 对象释放后，进程占用的页面也不一定立刻归还，所以两项数字不会相等。

## 百万级文件如何控制内存？如何优化？

1. 多goroutine处理，并控制等待数量
    - 满了就暂缓发现或把待办记录到数据库，等有空位再继续
2. 针对目录多的情况，采用流式读1000个
3. 数据库提交改为批量提交

## 任务状态机有哪些状态？

核心状态是 Pending 和 InProgress。

Pending 表示任务已提交但还没处理；worker 开始处理前把它改成 InProgress；处理完成后删除任务或标记为完成。失败时可以重新回到 Pending，等待后续重试。

# 其他

## NAS产品定价

200-500美元，各型号不同

## NAS是什么

可以理解为放在用户家里的个人私有云。

用户购买主机并自行安装硬盘，连接路由器以后，就能通过手机 App、Windows 客户端或网页，把照片、视频和文件备份到自己的设备里，也可以在外网远程访问。

我们既提供 NAS 硬件，也提供 LincOS 和配套客户端，所以它是一个软硬件一体化产品

## 规格

基于瑞芯微芯片（如RK3568、RK3588）的 ARM 架构 NAS

相比于 Intel 的 x86 芯片，价格更便宜、功耗极低

RK3576 的标称 NPU 算力为 6 TOPS。

## 硬盘

裸机，数据硬盘由用户自己购买。机器会自带用于系统运行的 eMMC 存储。有的系列可以装四个 M.2 NVMe、两个 SATA 数据盘

## 优点

从产品需求看，团队观察到家庭数据、照片视频和个人云存储需求不断增长，而传统 NAS 在体积、外观和使用门槛上还有改进空间，因此先做了紧凑型全闪存 LincStation。全固态设计、零噪音，散热也做的好

从公司战略看，慧为原本就具备智能终端的软硬件设计、制造和海外销售能力，做 NAS 可以复用这些能力，从单纯硬件进一步扩展到私有云系统和 AI NAS，提高产品附加值和用户黏性。

## 为什么主要做海外，没有做国内？

1. 已有渠道：原本就在欧美销售笔记本和平板，可以直接复用 Amazon、海外仓、认证和用户运营体系。
2. 产品定位更匹配：N1/N2 使用 Unraid，这类产品与海外已有的 Unraid 和自建服务器用户群比较匹配。
3. 避免重新建设一套国内体系：公司既然已经有海外用户和渠道，先在海外验证产品更符合现有基础。

## 为什么选择GO

1. Go 可以交叉编译并直接交付单个二进制，部署和升级比较简单
2. 系统里又有大量网络请求、文件扫描和异步任务，Goroutine 处理这类 I/O 并发比较合适。
3. 相比 C/C++，Go 的开发和维护成本更低

## 反馈与监控

1. 用户反馈入口
2. 上报错误
    - 接口错误：后端记录错误事件与 traceID。
    - 后台任务失败：后端主动记录，通过 taskID 关联日志。
    - 前端异常或请求超时：前端记录异常、操作和发生时间，附带可获取的请求标识，不强依赖响应中的 traceID。
3. 慢查询
    - GORM 可以写慢查询日志，Go 后台任务定期检测
    - 过去 10 分钟内：同一个 query_fingerprint 慢查询次数 >= 20；或者某个模块总数 >= 50 
    - 同一个 module + query_fingerprint，60 分钟内只生成一次告警

NAS 消息中心展示，用户选择是否上传诊断包
