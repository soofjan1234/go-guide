# BFS+Queue
## 为什么不用fsnotify

1. 原因是 fsnotify 在目录规模上来后 watcher、句柄 数量多、内存压力大，而且有漏事件，稳定性不够。
2. 我们改成先做目录快照比对，再把新增/修改/删除投递到队列，worker 批量写库。
3. 这样实时性弱一点，但准确性和资源可控性更好，整体更适合我们的场景

## fsnotify的原理

1. 创建一个实例（拿到一个 fd 文件描述符）。
2. 派哨兵去盯具体目录/文件（每个 Watch 都耗内核内存）。
3. 出事了内核往 fd 里塞事件，Go 读出来消费。

### 三大系统底层差异

| 系统 | 底层 API | 核心差异 |
| :--- | :--- | :--- |
| **Linux** | `inotify` | **盯单点**：每个文件/目录都要单独设哨兵（文件一多吃爆内存）。 |
| **macOS** | `FSEvents` | **查日记**：直接读文件系统日志，天生自带递归，省资源且极快。 |
| **Windows** | `ReadDirectoryChangesW` | **填水池**：内核往你申请的内存缓冲区（Buffer）里塞事件，异步读取（IOCP）。 |

## 实验对比怎么做的

通过不同的目录树，比如占用500-1-2GB。

Go 堆仍用 runtime.ReadMemStats().HeapAlloc；RSS 则读取本进程 /proc/self/status 中的 VmRSS

Go 堆看程序在采样时持有多少 Go 对象，便于比较算法自身的内存开销；RSS 看进程当时实际驻留在物理内存中的页面，更接近设备承受的进程内存压力

## 百万级文件如何控制内存？如何优化？

1. 多goroutine处理，并控制等待数量
    - 满了就暂缓发现或把待办记录到数据库，等有空位再继续
2. 针对目录多的情况，采用流式读1000个
3. 数据库提交改为批量提交

# 任务机
## 任务状态机有哪些状态？

核心状态是 Pending 和 InProgress。

Pending 表示任务已提交但还没处理；worker 开始处理前把它改成 InProgress；处理完成后删除任务或标记为完成。失败时可以重新回到 Pending，等待后续重试。

## 服务崩溃时正在处理的任务怎么办？

崩溃时任务可能停留在 InProgress。服务启动后会扫描任务表，把残留的 InProgress 任务重置成 Pending，然后重新投递到队列里。

因为目录扫描任务设计成幂等的，重复执行同一个目录不会造成错误。已经处理过且没有变化的文件会被比较逻辑跳过。
