## 多智能体架构

1. 为什么要设计 Simple、ReAct、Reflection、Plan-and-Solve 四种 Agent？它们分别适合什么场景？

   因为任务复杂度不一样，没必要所有问题都走最重的流程。Simple 适合直接问答；ReAct 适合边思考边调用工具；Reflection 适合对质量要求高、需要自我检查的任务；Plan-and-Solve 适合步骤多、依赖关系明显的复杂任务。

2. 从用户输入开始，一次 ReAct Agent 请求在项目中的完整执行顺序是什么？

   先把系统提示词、历史消息和用户输入组装起来，再把可用工具的 Schema 一起发给模型。模型如果要调用工具，Agent 就执行工具、回填结果，再发起下一轮模型调用；模型直接回答或调用 Finish 后，本次请求结束并保存消息和统计信息。

3. Reflection Agent 的“执行—反思—改进”流程与普通 ReAct 循环有什么区别？

   ReAct 主要围绕“模型判断—调用工具—观察结果”循环，目标是把任务做完。Reflection 会先产出一个答案，再单独让模型检查问题并生成改进版，直到模型认为“无需改进”或达到最大反思次数，更偏向提升答案质量。

6. Plan-and-Solve Agent 如何拆分规划阶段和执行阶段？为什么不直接使用一个 Prompt 完成任务？

   规划阶段先通过 `generate_plan` 生成结构化步骤；执行阶段再按顺序逐步处理，并把前面步骤的结果带给后面。拆开以后计划更稳定，也方便定位是哪一步出了问题，避免一个 Prompt 同时规划和执行时顾此失彼。

4. 模型一次返回多个 Tool Call 时，项目如何并行执行并保持结果顺序正确？

   ReAct Agent 为每个调用启动 goroutine，用 `WaitGroup` 等待完成，并提前按调用数量创建结果切片。每个 goroutine 只写入自己的下标，所以即使完成时间不同，最终回填顺序仍与模型返回顺序一致。

5. 哪些工具可以并行执行，哪些存在数据依赖而不能并行？当前实现如何识别这种差异？

   独立读取、查询和计算通常可以并行，同一文件上的读后写、连续编辑等存在顺序依赖。当前实现会并行处理同一轮的多个 Tool Call，并没有依赖分析，因此依赖关系主要依靠模型拆成不同轮次；这是现有实现的边界。


## 子 Agent 委派与容错

1. 为什么需要子 Agent，而不是让主 Agent 持有全部工具并完成所有工作？

   子 Agent 可以把复杂任务拆开，并使用独立上下文处理某个小目标，减少主 Agent 的上下文压力。它还可以只拿到任务需要的工具，权限边界更清楚，失败影响也更容易控制。

9. 子 Agent 的只读、全权限和自定义工具过滤策略是如何实现的？

   `ToolFilter` 统一提供过滤和权限判断。只读策略只放行 Read、LS、Glob、Grep 等工具；全权限策略默认只禁用终端执行类工具；自定义策略支持白名单或黑名单。运行前不允许的工具会被临时禁用，结束后再恢复。

11. 如何防止子 Agent 越权调用工具，或者再次递归创建不受控的子 Agent？

   关键是不要只在 Prompt 里提醒，而是在工具注册表这一层真正禁用工具。给子 Agent 使用白名单时，不把 `Task` 工具放进去，就能阻止它继续创建子 Agent；同时配合最大步数限制，避免递归或循环失控。

12. 如果子 Agent 执行失败、超时或达到最大步数，主 Agent 如何感知并处理？

   子 Agent 会返回 `success`、摘要和包含错误信息、耗时等内容的元数据。执行报错会变成失败或 partial 工具结果；达到步数上限时，ReAct Agent 返回未完成提示，主 Agent 可以根据这些信息选择重试、换方案或直接说明失败。

13. 子 Agent 返回完整执行历史还是摘要？这样设计有什么上下文成本和可解释性取舍？

   当前 `Task` 工具默认返回摘要和元数据，不把完整历史塞给主 Agent。这样能明显节省 Token，但排查细节会少一些；比较合适的做法是主上下文保留摘要，完整过程交给 Trace 保存，需要排障时再查看。

14. 如果需要同时运行多个子 Agent，你会如何设计并发控制、结果聚合和取消机制？

   可以给每个子任务启动一个受并发数限制的 goroutine，用 `context.Context` 统一处理超时和取消。结果通过带任务 ID 的 channel 汇总，聚合时按任务 ID 或原计划顺序整理；一个关键任务失败时，可以取消相关任务，其余任务是否继续则由任务依赖关系决定。

13. 文件编辑的乐观并发控制具体比较什么信息？为什么必须先通过 ReadTool 读取文件？

   ReadTool 会记录文件的毫秒级修改时间和大小，编辑工具实际使用传入的 `file_mtime_ms` 与当前 mtime 比较。先读文件才能获得编辑基线和待替换内容，否则没有可靠依据判断期间是否发生了外部修改。

14. 从读取文件到提交编辑期间文件被外部修改，EditTool 如何检测并拒绝覆盖？

   EditTool 写入前重新 `Stat` 文件，如果当前 mtime 与调用参数中的缓存 mtime 不一致，就返回 `conflict`，同时带回当前值和缓存值，不执行替换。调用方需要重新读取后再生成编辑操作。

15. 仅比较修改时间或文件大小有什么缺陷？如果升级为内容哈希，会带来什么成本？

   mtime 可能受文件系统精度影响，大小相同也不代表内容未变，极端情况下会漏检。内容哈希更可靠，但每次读写都要扫描完整文件，增加大文件的 CPU 和 I/O；可以按文件大小选择 mtime、大小与哈希的组合策略。

16. MultiEdit 执行到一半失败时是否具备原子性？如果没有，你会如何改进？

   同目录临时文件写入、同步落盘后原子 rename，并在替换前保留备份。

## 上下文工程与会话恢复

1. 项目如何统计 Token？所用 Tokenizer 与实际模型不完全一致时会有什么风险？

   `TokenCounter` 优先用 tiktoken 按模型获取编码，失败时退回 `cl100k_base`，再失败则按约四个字符一个 Token 估算，并缓存结果。非 OpenAI 模型的分词可能不同，估少会导致超窗，估多则会过早压缩，因此预算还需要保留安全余量。

3. 上下文总预算需要为系统提示词、用户问题、历史消息和模型输出分别预留多少空间？

   当前 ContextBuilder 默认窗口为 8000 Token，统一预留 15%，其余空间按系统指令优先、再按相关性选择内容，并没有为每类消息设置固定配额。生产中应根据模型输出上限和任务特征单独预留回答空间，避免输入占满窗口。

4. 系统如何判断需要压缩历史？触发条件是什么？

   每次添加消息后都会累计历史 Token，当它大于 `ContextWindow × CompressionThreshold` 时触发压缩。压缩后重新统计保留下来的摘要和最近轮次，作为新的历史 Token 基线。

6. 历史压缩后如何避免丢失用户约束、已完成事项和工具执行结论？

   智能摘要 Prompt 明确要求保留任务目标、关键决策、已完成工作、待处理事项和重要发现，同时 HistoryManager 保留最近若干轮原始对话。不过摘要仍可能遗漏细节，关键约束最好另外结构化持久化，而不能只依赖自由文本摘要。

8. ContextBuilder 如何从候选内容中筛选与当前用户问题相关的信息？

   它将查询和内容按空白切词并转小写，用词项重合比例计算相关度，再结合时间衰减形成 0.7 相关性加 0.3 新鲜度的排序分数。系统指令始终优先，其他内容需达到最小相关度并能装入 Token 预算。

9. 工具输出为什么同时设置最大行数和最大字节数？截取头部与尾部分别适合什么场景？

   行数控制日志和表格的纵向规模，字节数防止单行超长内容绕过限制。head 适合保留标题和首个错误，tail 适合最新日志，head_tail 同时保留上下文开头和最终结果。

10. 被截断的完整工具输出存放在哪里？Agent 如何在需要时继续读取？

   Truncator 会把完整内容和工具名、时间、元数据写入 `ToolOutputDir` 下的 JSON 文件，并在返回元数据中提供 `full_output_path`。Agent 可根据该路径再调用文件读取工具，按分页方式查看剩余内容。

11. 会话持久化保存了哪些状态？为什么除消息历史外还要保存配置、工具 Schema 哈希和读取缓存？

   会话文件保存 ID、时间、Agent 配置、消息历史、工具 Schema 哈希、读取缓存和元数据。
   
   因为恢复会话不能只恢复聊天记录，还要判断：当前运行环境是否仍然能够安全地继续执行旧任务，配置与哈希用于发现恢复环境是否变化，工具Schema哈希确认工具契约有没有变化，读取缓存用于延续文件编辑的冲突检测语义，而不仅是恢复聊天文本。

12. 加载会话时如何检查当前配置与历史配置是否一致？不一致时为什么采用警告而不是直接失败？

   当前比较 LLM Provider、模型和最大步数，并比较工具 Schema 哈希；差异会写日志和 Trace。配置变化不一定让历史失效，例如只换兼容模型仍可继续，因此采用警告，让调用方决定是否重新读取或重新开始。

13. 为什么恢复会话时需要恢复文件读取缓存？缓存已经过期时如何避免错误编辑？

   恢复缓存可以让后续编辑继续携带此前读取的版本基线。真正写入前仍会重新获取当前 mtime；如果文件在会话暂停期间变化，就会返回冲突并要求重新读取，所以恢复缓存不会直接绕过校验。

15. 如果会话历史非常大，你会如何优化持久化速度、文件大小和恢复耗时？

   可以采用追加式 JSONL 或分段快照，只增量写入新消息，并对旧工具输出单独存储和压缩。恢复时先加载最近快照和尾部增量，旧历史按需分页读取，同时保留临时文件加 rename 的崩溃安全写入方式。
