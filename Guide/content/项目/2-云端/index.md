# 一、穿透
## 客户端、服务端、云端及穿透端的通信流程

**情境** 

1. 核心问题是 NAT 会拦截无状态入站流量：内网设备只有先出站建立映射，外部回包才进得来
2. 所以要进行双方通信，会通过P2P穿透，那要进行穿透就得知道对方的公网地址
3. 而我负责的项目主要是信令服务器，在双方还没建立起直连通道之前，提供一个互相交换信息的媒介

**角色**

- 客户端：手机
- 服务端：nas
- 云端：我负责的项目，信令服务器
- 穿透端：公网上的"穿透服务器"

**链路**

1. 首先，都在同一局域网的时候，手机点击开启穿透，nas会请求云端领一些东西
    1. 穿透凭证，用于nas开启穿透
    2. 验证码，用于手机向云端获取信息，在明，可展示给用户
    3. 校验码，用于验证身份
2. 然后nas会拿着穿透凭证，去公网上的"穿透服务器"那里注册或创建会话
3. 手机现在在外面了，把验证码给云端，问他这人在哪，云端查到后就给他穿透测入口，并给他校验码
4. 最后就是完成身份校验与通道建立

## 怎么得到的公网 IP 地址和端口？

1. 在原理中，是通过stun服务器获取的，设备向stun服务器注册内网地址，服务器会记录公网地址
2. 在我们的实现中，客户端不需要得到公网地址，只需要知道对端是谁，然后调用穿透sdk封装了ConnectAdd即可

## 凭证有没有过期时间？过期、重复使用、被截获时怎么处理？

验证码是7天自动轮换。防重放是timestamp + nonce。被截获后重新生成相关凭证，记录安全审计日志

## 你们怎么排查“用户说连不上”的问题？会按哪些事件时间线定位？

1. 确定现象：用户的操作，具体结果，网络，版本
2. 看告警面板：会不会并发大，成功率，错误码多少
3. 按照时间线来排查：根据SN查整条链路，云端、服务端、穿透端

## 设计核心在哪？

对端发现（信令）、身份校验（三凭证 + 防重放）、NAT 穿透（SDK 打洞/中继）、可排查（全链路日志）

# 二、加密
## 为什么要加密

若在 VPN 场景，常见链路是：`设备 -> [VPN 隧道] -> VPN 节点 -> [公网 TLS] -> Cloudflare`。

有些公司或特殊网络会要求在设备上安装其自有根证书（Root CA）。此时需注意：

- 一旦你信任了该根证书，VPN/代理节点理论上可以做“解密后再加密”（TLS 卸载 / 中间人代理）。
- 发生了两次https请求

## 双方加密流程

角色是Host设备和云端通信

1. Host设备rand生成AES密钥，使用AES-GCM加密明文，得到data,nonce
2. Host设备使用**云端**的RSA公钥加密AES密钥，得到key
3. Host设备将data,nonce,key发送给云端

4. 云端调用DecryptAESString，使用**云端**RSA私钥解密key，得到AES密钥
5. 云端使用AES密钥解密data,nonce，得到明文
6. 云端调用EncryptAESString，再生成新AES，使用**Host**的RSA公钥加密返回

7. Host端用**自己**的RSA私钥解密AES密钥，再解密响应

## 云端、Host端私钥如何保存？

云端：

1. 托管在云端KMS中，私钥在 KMS 内部生成，物理锁死，没有任何 API 能导出私钥明文。
2. 需要解密或签名时，通过 IAM 角色授权，调用 KMS 接口在 KMS 内部完成，Go 服务只接收结果

Host：

1. 存在磁盘上，但是被加密锁死的。采集 Host 端的硬件唯一指纹（如：CPU 序列号 + 主板 UUID + 网卡 MAC 地址）融合成一个解密 Key。
2. Go 读取硬件指纹，解密到内存中，磁盘上永远没有私钥明文。

# 三、技术选型
## 为什么考虑用 STUN + TURN？而不是其它的

**为什么用 STUN + TURN 组合，而不是单选一个**

先 STUN 打洞，失败再 TURN 兜底——这是 WebRTC ICE 的标准思路，兼顾成功率与成本

**和其它方案比**

1. 端口映射 / UPnP
    - 端口映射（Port Forwarding）：在路由器上手动配置——把公网 x.x.x.x:8080 转发到内网 NAS 192.168.1.100:8080。
    - UPnP：让 NAS 或 App 自动跟路由器说「帮我开个端口」，不用用户手配
2. VPN
    - 在手机和 NAS 侧（或 VPN 服务器）之间建一条网络层隧道，连上后手机相当于进了内网网段。
3. 纯云端反向代理（frp 类）
    - 内网 NAS 作为客户端，主动连公网上的中继服务器，服务器暴露一个公网入口，外网用户连服务器，服务器把流量转发给 NAS
    - frp：应用层反向代理，通常代理 HTTP/TCP 端口
    - TURN：更底层的媒体中继，WebRTC/打洞生态里的标准兜底
4.  自建打洞
    - 要自己处理各种 NAT 类型、超时、重试、日志，运维和客诉成本高


## NAT穿透和VPN的区别

我们的穿透是应用级远程访问：外网手机通过邀请码找到家里 NAS，只访问 NAS 服务，不是把整个手机流量导入内网。

VPN 是网络层隧道，连上后设备相当于进了另一个网段，粒度更大、部署更重。

我们场景是「远程看 NAS 文件」，邀请码 + P2P 穿透更轻、对用户更友好。

## 这个流程是如何想到的

### 1. 先定要解决什么

- 核心矛盾：NAS 在内网，外网手机**不能直连**
- 产品目标：C 端用户远程访问

### 2. 拆成四个子问题

| 子问题 | 谁负责 | 对应设计 |
|--------|--------|----------|
| 双方怎么找到对方？ | 云端信令 | 邀请码 → 查 NAS 会话入口 |
| 怎么证明是本人？ | 云端 + 两端 | 穿透凭证（NAS 用）+ 校验码（碰头验） |
| NAT 怎么打通？ | 穿透端/SDK | STUN 打洞，失败 TURN 中继 |
| 连不上怎么查？ | 云端 | 按 SN 查全链路事件 |

### 3. 参考了什么

1. **WebRTC ICE 模型**：信令交换地址 + STUN 打洞 + TURN 兜底——行业成熟方案
2. **向日葵邀请码**：用户心智成熟，「输入数字远程访问」，不需要账号体系
3. **开源双用户系统方案**：云端一套账号、NAS 一套账号——功能全但各端代码多、边界 case 多，**否决**
