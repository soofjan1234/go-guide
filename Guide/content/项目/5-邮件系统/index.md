## 项目背景

把历史客服回复和FAQ沉淀为知识库，用户发邮件后利用RAG技术找到相似的并生成草稿，最后人工审核发布。

## 技术选型

### Python

项目瓶颈主要在模型调用、业务迭代，吞吐并不高，Python 能降低 AI 能力集成和效果验证成本

### FastAPI

1. FastAPI 基于 ASGI，适合异步 HTTP 接口：邮件系统有大量外部IO，比如调用模型网关、查询PostgreSQL
2. FastAPI 与 Pydantic 集成后，可以统一处理参数校验：这个项目的数据结构较多

**其它**

1. Flask 更轻，但项目需要类型校验、OpenAPI、异步接口和较多业务契约。如果用 Flask，这些能力通常需要额外组合多个扩展；FastAPI 在这些方面提供了相对统一的默认方案
2. Django 的后台管理、ORM很成熟，对于当前项目可能稍重

### PostgreSQL

1. 项目需要同时完成关系数据存储、全文关键词检索和向量语义检索。PostgreSQL 配合 GIN 和 pgvector，可以在一套数据库中完成三种能力，减少引入 Elasticsearch、Milvus 后的数据同步和运维成本。
2. 如果去掉知识检索需求，MySQL 同样能够满足这个项目的常规业务功能。

### pgvector

pgvector 是 PostgreSQL 的向量扩展；Milvus 是独立的专业向量数据库。

1. 本就需要 PostgreSQL 保存：入站邮件、审核任务、知识条目，使用 pgvector 后，向量也可以放同一套数据库中
2. 如果引入Milvus，维护增多，数据库一致性要处理
3. 项目规模，向量达到千万级、并发检索成为独立瓶颈后，再考虑迁移到 Milvus

## 业务

### 拉取怎么拉取的

第一次拉取没有 UID 时，使用配置的最早时间，通过 IMAP SINCE 查询。

循环拉取，并根据上一次成功处理的UID游标读取

通过 FETCH (UID RFC822) 获取完整 MIME 内容

### 内容向量化怎么做的

FAQ：问题 + 答案 → 一个向量

历史邮件：客户来信正文 + 客服回复正文 → 一个向量

### 相似匹配怎么做的

1. 召回：计算向量相似度，全文检索分数，最后`混合分数 = 0.6*向量相似度 + 0.3*全文检索分`
2. 校准：对客户邮件和知识条目计算 Jaccard 相似度，`最终分 = 0.9*混合检索分 + 0.1*本地词面分`

### 可能问题回复只有一对  但也有可能n对 甚至n对1 1对n

当前一对一。更合理的做法是先根据 Message-ID、In-Reply-To 和 References 构建完整邮件线程

对于 N 对 1，会合并客户的多次补充，形成完整的问题描述；对于 1 对 N，会判断多封客服回复是否共同构成一个解决方案，如果是就合并，否则按不同子问题拆分；对于 N 对 N，则按照问题处理阶段拆成多个知识单元，而不是把整个线程直接作为一条超长知识

### 如何确定候选回复的置信度阈值，怎么评估召回效果是否可靠？

当前是0.3作为低置信度阈值，是经验阈值，为了快速完成流程

后续如果要校准的话，会构建人工标注的评估集：用较早的邮件构建知识库，用较晚的客户来信作为测试查询，并由客服标注每封来信对应的正确知识。

用不同的阈值进行测试，观察候选准确率、知识覆盖率和错误高置信率。因为这是客服场景，我们会更关注“高分但答错”的情况

### 如何避免历史邮件中的错误回复、敏感信息或过期方案污染知识库？

1. 无关信息要做清洗
2. 敏感信息要做脱敏
3. 配对之后不进入知识库，而是进入审核库
4. 矛盾知识，可以最新优先，旧知识降权
5. 过期知识，可以停用和删除

### 模型服务、邮箱服务或者向量检索不可用时，业务如何降级？

1. Embedding 或向量检索失败时，先降级到 PostgreSQL 全文检索
2. 回复生成模型失败时保留审核任务，由客服手工处理
3. IMAP 拉取失败会重试且不推进 UID 游标，下一轮从原位置继续。
4. SMTP 失败则有限重试并记录失败状态，只有收到成功结果才标记为已发送。
5. 翻译服务还没回退，如果回退的话，可以做标记，让人来进行翻译，或者后续重试
