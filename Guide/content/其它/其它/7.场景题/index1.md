# 高并发

## 广告出价接口设计 +1

**背景**：服务收到万级 QPS；收到请求后需解析、过滤、打分、出价，**100ms 内**返回 Response；还要收集日志（什么流量、是否参与出价、打分多少）。

**主问**：
1. 如果是你，怎么设计这个接口？
2. 怎么确定一定是 100ms 以内返回？接口超时控制怎么做？
3. 日志是落库吗？你觉得日志要不要**同步**落库？除消息队列外还有什么更好的处理方式？
4. Goroutine 的生命周期在这个超时场景下怎么走？有没有遇到过 Goroutine 泄漏？

**口述主路径**：把 100ms 拆成解析、过滤、特征读取、打分和网络回包的预算，超时用 `context.WithDeadline` 向下传递。同步链路只做决定出价所必需的步骤；曝光与决策日志异步写入有容量和失败处理策略的队列，不能让同步落库拖住响应。并行 goroutine 必须监听 `ctx.Done()` 并有退出路径；用压测中的 p99 延迟、超时率和队列积压验证，而不是口头保证每次都在 100ms 内。

## 热门商品库存扣减 +1

**背景**：1000 件热门商品、10 万人同时购买。

**主问**：
1. 如何设计后端扣减方案？
2. 如何保证不能超卖，同时尽量提高吞吐？

**口述主路径**：先确定订单创建与库存扣减的一致性边界。热点库存可在 Redis 用 Lua 原子检查并扣减，再由订单事件异步落库，失败时补偿并对账；数据库侧仍要用条件更新 `UPDATE ... SET stock=stock-1 WHERE stock>0` 防止最终超卖。请求带幂等号，重复下单不能重复扣。Redis 故障时按业务取舍降级到数据库或拒绝，不承诺异步链路天然零误差。

## 短视频点赞系统 +1

**背景**：你负责一个短视频平台的点赞系统。某条视频突然爆火，5 分钟内收到 1000 万次点赞请求，峰值 20 万 QPS。用户点完赞后，需要立刻看到“已点赞”状态，视频详情页的点赞数也要尽快变化，同时系统还要更新作者通知、排行榜、推荐特征。

**主问**：

1. 这个场景下会出现哪些问题？你会如何处理？
2. 还有个浏览历史的功能，你会怎么设计？

**口述主路径**：先按 `user_id + video_id` 记录点赞状态，重复点赞和取消点赞要幂等；高并发写入可先更新 Redis 用户状态和分片计数，再通过队列异步落库及对账。详情页读缓存中的近实时计数，作者通知、排行榜和推荐特征异步消费事件，允许各模块短时间延迟。浏览历史按用户分区、按时间排序并设置保留策略，避免为每次曝光同步写多张业务表。

### 热点 Key / 大 Key 问题

**主问**：
1. 某条视频/某个明星/热门商品突然爆火，Redis 单 key 被打爆怎么办？
2. 热点 key 如何发现？

**口述主路径**：从 Redis 命令延迟、单 key 访问量和应用侧热点统计识别热点。极热的只读数据先用本地缓存、短 TTL 和请求合并挡住回源；计数写热点可按多个分片 key 分散，读取时聚合。大 key 要拆结构或分页，避免一次操作阻塞 Redis；缓存失效时用随机 TTL、互斥重建等方式防止同时回源。

# 业务设计

## 广告频控 +1

**背景**：对每个用户在**每一条广告**下做频控——最近 **1 分钟最多曝光 3 次**。

**主问**：
1. 你会怎么实现？
2. Redis 用什么数据结构？Key / Field 怎么设计？

**口述主路径**：Key 用 `ad:freq:{user_id}:{ad_id}`，时间窗口为最近 60 秒。需要精确频控时用 ZSET 记每次曝光的时间戳和唯一 member，在 Lua 中原子删除窗口外记录、判断是否达到 3 次、写入本次并设置 TTL。只有实际曝光成功才计数；广告展示失败不能算曝光，重复回调用事件 ID 去重。

## 连续签到 7 天奖励 +1

**背景**：用户连续签到 7 天要给奖励。

**主问**：你会怎么设计？

**口述主路径**：签到请求携带用户和业务日期，在数据库以 `(user_id, date)` 唯一约束保证同日只记一次；Redis Bitmap 可加速查询某月签到情况。连续天数按业务时区计算，达到第 7 天时生成带幂等号的奖励事件，发奖方按事件 ID 去重。补签、跨月和时区切换需先写清规则。

## 独立访客（UV）计数 +1

**背景**：统计独立访客数量。

**主问**：你会怎么实现？（考点常指向 HyperLogLog / Bitmap 等）

**口述主路径**：只要近似 UV，可按日期对访客 ID 做 `PFADD`，用 `PFCOUNT` 得到 HyperLogLog 估计值，节省空间但有统计误差。需要精确去重则用集合、数据库或在 ID 范围可控时用 Bitmap；先明确访客 ID 的口径和跨设备合并规则。

## 重复请求 / 防抖去重 +1

**背景**：第一个请求发出后，抖动还没结束又发了第二个请求。

**主问**：如何做去重，保证不重复操作？

**口述主路径**：由客户端或服务端生成稳定的幂等号，同一次业务重试复用该号。入口可用 Redis `SET key value NX EX` 快速拦截，但关键写入还要在数据库设置唯一约束并记录处理结果；重复请求返回第一次结果。处理中超时、进程崩溃时要能查询最终状态，不能把“抢到 Redis 锁”当成业务已完成。
