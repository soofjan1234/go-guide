# 协作

## code review

1. 业务逻辑与正确性
    - 需求符合度
    - 边界条件与空值防护
    - 状态机与并发安全：

2. 架构设计与扩展性
    - 单一职责原则（SRP）：一个函数/类是不是干了太多事？
    - 分层边界：业务逻辑有没有污染 Controller / API 接口层？
    - 模块解耦与复用

3. 性能与资源消耗
    - 数据库/存储瓶颈：有没有引起 N+1 查询问题？查询是否走了索引？有没有 `SELECT *`？
    - 内存与 GC 压力：在高频循环里有没有大量分配临时对象（引发 GC 抖动）？
    - 网络与 IO：RPC / HTTP 调用有没有设置合理的超时时间（Timeout）和重试策略？

4. 安全性与防御性编程
    - 注入漏洞：SQL 注入、Shell 注入、XSS / CSRF 攻击防护。
    - 敏感数据处理
    - 越权与鉴权

5. 可观测性与容错
    - 错误处理
    - 日志规范
    - 降级与熔断：核心依赖出现故障时，是否有兜底方案（Fallback）？

## 文档管理

一个需求到来之后：
1. 先写清目标、不做的事、约束和验收标准。
2. 再设计流程、接口、数据结构和失败处理。
3. 把设计拆成可执行的小任务，逐步实现与验证。
4. 最后复核代码、测试结果、操作记录和文档。

## 模型选择

按任务不确定性和成本选模型：需求含糊、跨模块设计或复杂排查用推理能力更强的模型；范围清楚、机械性修改用更快的模型。关键结论仍以代码、测试和真实运行结果验证，不以模型名称保证质量。

# 认知

## 对 AI 的看法？优势和局限是什么？ +1

AI的优势：
1. 快速生成原型、整理资料和给出排查候选路径。
2. 辅助 Code Review 和测试设计，缩短重复工作时间。

AI 的局限：可能编造 API、版本和性能数字，也会遗漏隐含边界。生成代码必须结合官方文档、测试和实际运行验证；需求边界、安全与最终取舍由人负责。

我的优势：
1. 理解需求，描述给AI
2. AI给的测试边界不全，需要自己考虑更多
3. AI给出技术方案，我来拍板做哪个
