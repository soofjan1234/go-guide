# 协作

## code review

1. 业务逻辑与正确性
    - 需求符合度
    - 边界条件与空值防护
    - 状态机与并发安全：

2. 架构设计与扩展性
    - 单一职责原则（SRP）：一个函数/类是不是干了太多事？
    - 分层边界：业务逻辑有没有污染 Controller / API 接口层？
    - 模块解耦与复用

3. 性能与资源消耗
    - 数据库/存储瓶颈：有没有引起 N+1 查询问题？查询是否走了索引？有没有 `SELECT *`？
    - 内存与 GC 压力：在高频循环里有没有大量分配临时对象（引发 GC 抖动）？
    - 网络与 IO：RPC / HTTP 调用有没有设置合理的超时时间（Timeout）和重试策略？

4. 安全性与防御性编程
    - 注入漏洞：SQL 注入、Shell 注入、XSS / CSRF 攻击防护。
    - 敏感数据处理
    - 越权与鉴权

5. 可观测性与容错
    - 错误处理
    - 日志规范
    - 降级与熔断：核心依赖出现故障时，是否有兜底方案（Fallback）？

## 文档管理

- MVP 主要定义第一版做什么、不做什么，大概的阶段以及什么条件算验收通过；
- Design 负责说明系统怎么实现，包括架构、数据模型、状态流和接口契约；
- Plan 则把已经确认的设计拆成具体开发任务、实施顺序和验证方式。

后续如果 MVP 完成后的增量功能：写进 roadmap.md 或对应版本文档，例如 v1.1.md。

## 挡位

几条可以直接参考的规则：
1. Codex CLI 官方建议从 Sol Low 起步，按需升档
2. 模糊任务 / 多步骤 → Sol High
3. 明确任务 / 单步执行 → Terra Medium 或 Terra High
4. 超高难度 → Sol Ultra，但要做好 token 快速消耗的准备
