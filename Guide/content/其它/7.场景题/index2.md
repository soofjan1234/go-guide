# cpu问题
## CPU\内存高怎么排查？

如果 CPU 或内存高，我会先用 top 看整体情况。

1. 如果是用户态高，通常是业务代码计算、死循环、JSON 编解码、正则、排序或者大量 GC，我会用 Go pprof 的 CPU profile 看热点函数。

2. 如果是系统态高，通常是系统调用、网络 IO、文件 IO、上下文切换或者锁竞争比较多，我会结合连接数、日志、网络和 IO 指标看。

3. 如果是内存高，我不会只看 free 里的 used，而是看 available，同时用 heap profile 看哪些对象占内存，检查缓存、全局 map、大 slice、goroutine 泄漏、channel 阻塞这些问题。

### 范围在MySQL的话呢？

全表扫、没索引、大 JOIN、Using filesort / Using temporary，都是「对很多行做很多事」：

- CPU：逐行比较、排序、哈希、函数计算
- 内存：排序/JOIN 的 buffer、内存临时表、结果集

## CPU周期性尖刺延迟排查

1. 查看 CPU 类型
2. 查看周期频率
    1. 定时任务
    2. 缓存失效

# 现实问题

先定影响面，再看变更；沿链路查监控、日志、资源和依赖；必要时先止血，再复现修复。

## 接口突然大量超时如何排查？

1. 先定范围：全接口还是某一个？所有用户还是一部分
2. 止血：影响面大就不要等根因，做回滚、限流、降级、扩容。
3. 再看链路：网关、服务、DB、Redis、MQ第三方；
4. 再看资源：CPU、内存、网络、连接池

## 错误率飙升怎么排查

1. 先定范围：看错误码以及错误分布
2. 止血
3. 再看链路：根据报错频发的应用节点看日志和资源
    - 可能是代码未捕获异常，后端挂了；网关超时、限流

## 官网访问慢排查

用户范围 → CDN → DNS/TCP/SSL → 服务端 → 前端资源 → 链路丢包

## 一部分用户出现下单失败的问题，让你去定位这个线上事故

先止血 → 收集用户特征 → request_id 查链路 → 看错误码 → 看数据特征 →  复现修复

## OOM怎么排查？

趋势 → 谁被杀 → heap → goroutine → 代码泄漏点  → 先保现场

## 慢查询怎么办

1. 确认是否稳定复现。
2. 定位具体哪条 SQL 慢。
3. 用 EXPLAIN / EXPLAIN ANALYZE 查看执行计划，重点关注 type、key、rows、Extra。
4. 检查索引是否命中，有没有索引失效。
5. 分析 SQL 本身，是否存在 SELECT *、返回数据过多、复杂 JOIN、排序或分组等问题。
6. 检查是否存在锁等待，事务过长。
7. 检查系统资源，例如 CPU、磁盘 I/O、内存是否成为瓶颈。
8. 优化后再次验证，确保确实改善。

## 已是核心功能，已知有发布，为何不直接回滚

回滚是默认止血手段，不是无条件。核心链路仍可能先不回滚，因为回滚本身会伤数据或伤兼容。

1. 带 schema / 数据迁移：新版本已写新表结构或改过存量，退回旧代码读不懂新数据，可能大面积写坏或读失败。
2. 多服务已按新接口切流：只回滚其中一个，契约对不上。
3. 回滚包没演练、或旧包依赖的配置/镜像已下线，回滚风险不可控。
4. 可用开关、降级、限流把错误从 20% 打回去，比整包回滚更小。
5. 问题像容量、下游、机房，而不是这版逻辑——回滚解决不了，还会引入一次抖动。

口述：先问「回滚会不会让数据/协议更糟」。会，就停新流量、开兼容、修正向；不会，核心 API 仍优先回滚。

## 故障复盘如何落地

复盘不是写一篇「为什么」，而是把动作变成有人、有期、能验收的改动。

1. 先写清时间线：发现、影响面、止血动作、根因（机制，不是点名）。
2. 每条改进拆成：告警/预案/测试/发布门禁/文档，指定负责人和截止日期。
3. 用机制卡住：同类故障要能被监控打到，或被 CI/发布检查拦住，而不是靠「下次注意」。
4. 复盘会后跟一次检查：到期没合代码、没上告警，条目不算落地。
5. 团队规则写进 runbook 或编码约定，新同学按说明书走，不要只存在聊天记录里。

## 如何做性能优化

我一般不会直接优化代码，而是先明确性能目标，比如接口的 P95、P99 延迟、吞吐量和资源上限，然后通过监控或压测稳定复现问题。

接着先判断瓶颈是在应用内部，还是数据库、网络、磁盘或下游服务。应用内部会用 pprof 分析 CPU、内存、Goroutine、锁竞争和阻塞：CPU 看 flat 和 cum，内存结合 inuse 和 alloc，阻塞则看 Goroutine、block 和 mutex profile。

找到热点以后再针对性优化，例如减少重复计算和内存分配、优化 SQL 和索引、增加缓存或控制并发。

最后使用相同流量重新压测，对比延迟、吞吐量、错误率和资源占用，同时跑回归测试，确认没有用正确性换性能。
