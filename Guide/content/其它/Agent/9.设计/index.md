## 如果要做一个智能客服类 AI 应用，整体链路怎么设计？

一般会先做问题分类，区分 FAQ、知识问答、工具调用和人工转接。

简单固定问题走模板回复，知识类问题走 RAG，查订单、查物流、查账户这类走工具调用，高风险或低置信度问题直接转人工。

核心链路要有会话管理、权限校验、敏感词过滤、日志追踪和效果评估，不然上线后很难控风险。

## 如果让你设计一个 Agent 的规划器，怎么避免它每一步都重新规划，导致路径震荡？

1. **分层分工**：规划器只定宏观阶段（如信息收集、证据校验、结果生成），不直接调用工具，也不碰执行细节；执行器只负责在当前阶段内微调动作，绝不改动全局计划。
2. **显式状态**：向模型注入明确的状态机（当前子目标、已完成步骤、失败归因、剩余预算），防止模型把每一步的新结果当成全新任务来重新理解。
3. **重规划门控**：默认按原计划一直走，规划器平时不介入；只有在关键前提失效、连续重试失败达到上限、或用户需求变更时，才触发全局重新规划。
4. **历史锁死**：已完成的步骤立即冻结为只读历史，保证进度单调向前；即使后续遇到困难重新规划，也只准修改未来的待办任务，绝不能推翻已完成的成果。
5. **降噪过滤**：网络超时、微小格式错误等局部异常由执行器原地重试自愈，不向上汇报；只把清洗后的关键进展摘要和致命阻塞上报给规划器，避免信息过载引发过度敏感。

## 如何优化一个Agent项目

1. 看数据：先接上链路监控（如 LangSmith）和真实任务集，统计任务成功率、工具选择及参数正确率、平均轮次、输入/输出 Token、延迟、费用和人工介入率。样本量按实际业务确定，不预设“几百条”就足够。
2. 找病因，分模块重构：
   - 规划能力不足：优化prompt结构，引入反思机制。
   - 找不着工具：重构tool description。
   - 答非所问，丢失上文：引入滑动窗口，做好记忆。
   - 响应太慢：我们可以做小模型分级路由、并行工具调用
3. 加护栏：设置最大重试次数防止死循环，高风险操作（如删库、发邮件）必须经过人工确认。

# 一个agent什么时候决定结束 

1. 目标已达成
2. 命中了预设的状态机节点
3. 触发了熔断，比如说最大轮次限制，token限制。

# 一个agent什么时候决定问用户

1. 关键参数缺失
2. 语义不明确
3. 高风险操作

# 失败恢复怎么设计

agent的一个失败呢可能分成好几类，所以要按类型进行一个不同的错误处理

1. 接口超时，我们可以限时的一个限次数的一个重试。
2. 参数缺失的话，我们可能要进行一个追问。
3. 如果是连续选错了工具就要进行一个降级。
4. 外部系统不可用，就要终止，并且返回失败的原因。
