## 锁的类型 +2

![事务与并发.锁体系](pic/事务与并发.锁体系.png)

锁是事务实现隔离性的手段
1. Latch：锁的是内存页
2. Lock：锁的是逻辑数据
    1. 粒度
        - 表级锁，还有意向锁（IS/IX，给表锁当路标）
        - 行级锁：Record、Gap、Next-Key；INSERT 还会在间隙上挂插入意向锁
    2. 类型
        - 共享锁，可以读读，不能写
        - 排他锁，只能一人获取，其它不能获取

## 行锁

假设现在表里只有三个值：5, 10, 15

1. 行锁（Record Lock）：精准打击

锁住后，别人不能修改 10，但别人可以 INSERT 8 或 INSERT 12。

2. 间隙锁（Gap Lock）：只防插队

它是一个开区间，比如 (5, 10)，不影响 5 和 10 这两行本身。别人不能在 5 到 10 之间插入新数据。（阻断 INSERT）

3. 临键锁（Next-Key Lock）

它是一个左开右闭区间，比如 (5, 10]。Record Lock + Gap Lock的结合体。

它既不准别人在 5 到 10 之间插队，也不准别人动 10 这行数据

## 意向锁

加行锁之前，先在表上挂一个标记：IS（准备加 S 行锁）、IX（准备加 X 行锁）。

有人要加表锁时，不用扫全表行锁。表上已经有 IX，直接知道没法 `LOCK TABLES ... WRITE`。

意向锁彼此兼容，也不挡别人的行锁，只挡整表请求。

## 插入意向锁 

INSERT 往某个空洞里塞行之前，先在这个 Gap 上挂插入意向锁（Insert Intention）。它是一种特殊的间隙锁，用来声明「我要插这里」，不是表级那套 IS/IX。

比如 5, 10, 15：

1. T1 `INSERT 6`、T2 `INSERT 8`，都落在 (5, 10)。两把插入意向锁互相不挡，各自拿到新行上的 X 锁就结束。
2. 如果已经有人用当前读把 (5, 10) 锁成普通 Gap / Next-Key（`SELECT ... FOR UPDATE` 扫过这段），INSERT 会堵在插入意向锁上，等间隙锁释放。

## 锁解决丢失修改问题

其实在任何隔离级别下，都不会导致数据库理论上的丢失修改问题，因为有行级锁，不会出现两个事务同时改同一数据的情况

但是在真实业务场景下，可能会出现这个问题，也就是先查后改：

![](pic/业务丢失修改.png)

如何解决：

![并发扣钱策略：悲观锁 vs 乐观锁](pic/抗衡丢失修改的悲观与乐观机制.png)

1. **悲观策略 (SELECT ... FOR UPDATE)**
   从查询的那一刻起，直接对这行数据挂上排他锁（X锁）。防范成功率 100%。阻塞其他当前读和写；普通 SELECT 仍走 MVCC。

2. **乐观策略 (版本控制 / CAS)**
   在业务表里自己多加一列 `version`（或时间戳）。
   每次读取带走这个 `version`，更新时附带条件：`UPDATE table SET balance = balance - 50, version = 2 WHERE id = 1 AND version = 1`。如果受影响行数为 0，说明在你犹豫的时候有人捷足先登了，你在业务层处理回滚重试即可。
