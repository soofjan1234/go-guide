# 一、 联合索引存储

## 为什么必须遵守最左前缀匹配原则？
联合索引只对应 **一棵 B+Tree**。数据在叶子节点上的排序规则是：**先按字段 `a` 排序；如果 `a` 相同，再按字段 `b` 排序；如果 `b` 也相同，再按字段 `c` 排序**。
- 物理节点内容：叶子节点存储的是 `(a, b, c, 主键ID)`。
- 结论推导：因为 `b` 和 `c` 在全局来看是**无序**的，只有在 `a` 确定的前提下 `b` 才有序。这就从物理底层解释了为什么会有“最左前缀原则”。

# 二、 失效规则

## 遇上范围查询（`>`、`<`、`BETWEEN`、`LIKE`）索引会怎样？

1. 如果 SQL 为 `WHERE a = 1 AND b > 2 AND c = 3`
    - `a` 和 `b` 能走索引定位，但 `b` 之后的所有列（即 `c`）将无法使用索引定位。因为在 `b > 2` 的多个区间里，`c` 是无序的。
2. `LIKE 'abc%'` 属于前缀范围查找，可以继续利用后续索引；
3. 如果为 `a IN (1, 2) AND b = 2`
    - 优化器进行 In-list Transform 拆分为多次“等值点查”（a=1 AND b=2 + a=2 AND b=2）

# 三、 优化机制与底层特性

## 什么是覆盖索引（Covering Index）？

1. 比如索引是（a,b,c）
2. 如果查询的列在联合索引的叶子节点上已经全有了（例如查 `SELECT b, c FROM t WHERE a = 1`）
3. 引擎直接从联合索引树上返回结果，**无需去主键树回表**。这是提升查询性能最有效的手段之一。

## 什么是索引下推（Index Condition Pushdown, ICP）？它是怎么减少回表次数的？

对于 `WHERE a = 1 AND c = 3`（联合索引 `(a, b, c)`）：
- 没有 ICP 时：
    - 存储引擎只用 `a = 1` 在索引树中找到所有符合条件的记录，将对应的主键 ID 全部返回给 Server 层；
    - 由 Server 层去主键树**回表**拿到完整行数据，再过滤 `c = 3`。
- 有 ICP 时：
    - 存储引擎定位到 `a = 1` 后，先**直接在联合索引树的叶子节点上检查 `c` 是否等于 3**。
    - 如果不等于 3，直接过滤掉；只对完全匹配的记录进行**回表**。大幅减少了磁盘随机 I/O 次数。

## 联合索引对 `ORDER BY` 和 `GROUP BY` 有什么帮助？

B+Tree 叶子节点的数据本身就是按照联合索引的列顺序排列的。

# 四、 实战设计与索引建立原则

##  如何给一条复杂的慢 SQL 设计最完美的联合索引？

1. **字段顺序原则（区分度优先）：** 尽量把区分度高（High Cardinality，即去重后数量大）的字段放在联合索引的最左边。

2. **三星索引设计原则（加分项）：**
    - **一星：** 把 `WHERE` 条件中等值匹配的列放在索引最前面（过滤最多数据）。
    - **二星：** 把 `ORDER BY` 的列放在索引中（消除排序）。
    - **三星：** 把 `SELECT` 查的列全部包含进索引中（避免回表，实现覆盖索引）。

3. **避免冗余索引：** 如果已经有了联合索引 `(a, b, c)`，那么单列索引 `(a)` 就是完全冗余的，可以安全删除；但单列索引 `(b)` 和 `(c)` 不能删。
