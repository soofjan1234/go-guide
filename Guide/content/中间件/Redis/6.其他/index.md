## Redis 是单线程吗？

以下以 Redis 6/7 的常见执行模型为准。

1. **命令执行**：同一个 Redis 实例主要由主线程依次执行命令，所以单条命令不会被其他命令插入。
2. **网络 I/O**：Redis 6 起可使用 I/O 线程处理套接字读写；它没有把普通命令改为多线程并行执行。
3. **后台工作**：`UNLINK` 的内存回收可交给后台线程；`BGSAVE` 和 AOF 重写使用 fork 出的子进程。不要把它们都叫作“命令执行线程”。

## Lua 适合解决什么问题？

以“读取库存，确认大于 0 后扣减”为例，客户端先 `GET`、计算、再 `SET`，需要 **2 次网络 RTT**。在两条命令之间，其他客户端可能修改库存，导致结果错误。若只是无条件加减，应优先使用 `INCR`、`DECR` 等单条命令。

Lua 可把有条件的读写放到 Redis 服务端：

1. **连续执行**：脚本运行期间，同一实例不会插入其他客户端的命令；多个 key 只要由这个实例处理，也可以在脚本中一起操作。
2. **减少往返**：一次脚本调用通常只需 1 次 RTT，客户端不必把中间结果取回后再提交下一条命令。
3. **注意耗时**：脚本运行太久会阻塞该实例处理其他请求，应保持短小。

这个保证只覆盖脚本操作的 Redis 数据，不能自动保护数据库、其他服务或不同分片上的操作。它也不意味着所有业务都不需要分布式锁；例如，锁可以用 `SET key token NX EX 30` 获取，再用 Lua 比较 token 后删除。

### Pipeline、事务和 Lua 的区别

| 方式 | 解决什么问题 | 边界 |
| --- | --- | --- |
| Pipeline | 把可提前确定的多条命令批量发送，减少 RTT | 命令之间可能插入其他客户端操作；上面依赖 `GET` 结果的 `SET` 不能直接合成一次往返 |
| `MULTI/EXEC`、`WATCH` | 队列命令连续执行；`WATCH` 可在执行前检查 key 是否被改动 | 客户端不能在事务执行到一半时读取结果并决定下一条命令 |
| Lua | 在服务端按读取结果分支，并连续执行相关命令 | 长脚本会阻塞实例；作用范围仍限于对应的 Redis 数据 |
