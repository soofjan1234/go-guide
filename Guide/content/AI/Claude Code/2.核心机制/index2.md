这一篇讲：**每次调用模型时，程序要给模型哪些指令，才能让它正确地完成任务。**

继续用同一个例子：用户输入“检查 `main.ts` 有没有问题”。下面的提示词和请求结构都是简化示意，用来理解各部分的职责。

# 模型只拿到用户请求，还缺什么信息？

模型还需要知道：

- 自己承担什么职责。
- 当前在哪个项目，项目有什么规范。
- 有哪些工具，每个工具怎么用。
- 用户这次具体要求什么，以及前面已经做过什么。

运行程序分别准备这些信息，再组织成模型请求。文中的提示词分类，就是在回答不同的问题。

# System Prompt：你是谁，应该怎样做事

System Prompt 是系统级指令，提供基本身份和行为规则。例如：

```text
你是一个编程 Agent。
根据用户要求分析项目，必要时使用工具。
```

模型因此知道，遇到“检查 main.ts”，可以先读取代码，再进行分析。

原笔记中的基础身份由 `constants/prompts.ts` 里的 `getSimpleIntroSection()` 等逻辑生成。

**指令指导模型怎样行动；运行程序决定实际提供哪些工具，以及是否允许执行。** 即使提示词写着“可以修改所有文件”，程序仍可以拒绝一次写入。

# Dynamic Sections：补充当前项目的信息

基本身份不会告诉模型，当前在哪个目录、项目有什么规范。因此运行程序会按环境准备不同的指令片段：

```text
基础身份：你是一个编程 Agent。
项目规范：遵守 CLAUDE.md，修改后运行指定测试。
环境信息：当前目录是 /workspace/project。
语言偏好：使用中文回答。
输出风格：回答简洁。
```

这些片段就是 **Dynamic Sections，动态组装的指令片段**。原笔记中使用 `systemPromptSection()` 组织它们，包括会话指导、项目记忆、环境、语言和输出风格等内容。

可以类比 Go 服务读取配置：基础程序相同，进入不同项目时，加载的配置不同。

Dynamic Sections 是构造 System Prompt 的组成部分，不是一种新的模型消息。

## 动态不等于每轮全部重算

有些内容可以缓存，有些内容需要随环境变化更新。例如 MCP 连接发生变化时，相关指导可能需要更新。

具体更新时机要看实现，不能仅凭某个函数名称推断所有指令片段的缓存策略。

# Tool Prompt：有哪些工具，什么时候用

模型知道要检查代码后，还需要知道可用工具的用途：

| 工具 | 使用场景 |
| --- | --- |
| Read | 读取本地文件 |
| Grep | 搜索文件内容 |
| Glob | 查找文件路径 |
| Bash | 运行测试、构建等命令 |

工具定义中的两部分，职责不同：

| 内容 | 回答的问题 |
| --- | --- |
| Schema：参数结构 | 需要传哪些字段，字段是什么类型 |
| Tool Prompt：工具描述 | 工具干什么，什么时候用，有什么使用要求 |

以 Read 为例：

```text
工具描述：读取本地文件，使用绝对路径，不能直接读取目录。
参数结构：需要传入 file_path，值为字符串。
```

模型据此提出工具调用：

```text
Read(file_path="/workspace/project/main.ts")
```

之后由 Harness，也就是模型外围的运行程序，检查参数和权限，再真正读取文件。

**工具说明帮助模型选对、用对工具；参数校验和权限检查负责拦住不合法的执行。** 例如搜索项目中的 TODO，可以使用 Grep，而不必默认通过 Bash 执行搜索命令。

# 这些信息怎样交给模型？

一次请求可以理解为：

```text
模型请求
├─ System：身份和规则
│  ├─ 基础身份
│  ├─ 项目规范、环境、语言等动态片段
│  └─ 适用时加入角色协作规则
├─ Tools：可用工具定义
│  ├─ 工具名称
│  ├─ 参数 Schema
│  └─ 工具描述与使用要求
└─ Messages：实际对话内容
   ├─ 用户：检查 main.ts
   ├─ 前面的对话和工具调用
   └─ 工具返回的文件内容等结果
```

**工具说明通常放在工具定义里，用户请求和工具结果放在消息里，并非所有文字都拼成一段 System Prompt。**

# 其他提示词什么时候用？

## 自定义 Prompt：补充或替换默认规则

如果只想补充“用中文回答”，可以追加指令：

```bash
claude --append-system-prompt "请使用中文回答"
```

如果需要替换默认 System Prompt，可以使用：

```bash
claude --system-prompt "你是一个代码审查助手"
```

追加会保留默认系统指令；替换会改变默认系统指令。两者都不能绕过工具权限和运行时校验。

## Teammate Prompt：指导协作角色

假设当前 Agent 负责审查代码，另一个 Agent 负责开发。审查者除了知道如何检查代码，还需要知道自己的职责，以及如何交付结论：

```text
你负责代码审查。
完成后，通过 SendMessage 向开发 Agent 发送审查结论。
```

Teammate Prompt 规定如何协作；SendMessage 工具和运行程序负责真正投递消息。普通文本输出不一定会自动送达其他成员。

## 专项 Prompt：为某件事提供专门指导

例如执行 `/init` 时，可以提供分析项目结构、构建测试命令和编码规范的任务指导；总结过长的工具输出时，则提供总结要求。

这些指令按需使用，不必让每个普通请求始终携带。它们可能作为主会话中的任务指令，也可能用于独立模型调用。其他例子还包括生成记忆、生成输入建议，以及指导子 Agent 执行特定任务。

**这些提示词名称是按用途分类，不代表模型 API 有六种对应的消息类型。**
