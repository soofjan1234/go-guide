Claude Code 在长时间执行任务时，会积累用户消息、工具调用、源码和测试日志。**上下文管理是持续进行的，但不意味着每一轮都会真正压缩；Autocompact 通常是在上下文接近预算阈值、轻量处理不足时才触发，而不是等窗口完全装满。**

# 为什么需要压缩

假设用户要求优化数据库查询：Agent 先读取多个 Go 文件，再搜索 SQL、运行测试、修复问题。每一次工具返回的代码和日志都可能进入后续模型请求。若一直携带完整历史，Token 占用就会持续增长，最终可能超过 Context Window。

这里要区分两种信息：**完整会话历史**与**本轮实际发送给 LLM 的上下文**。Harness 可以保留会话记录，同时裁剪、折叠或总结模型当前看到的内容。

# 分级压缩：先轻量处理，再整体总结

可以按以下顺序理解 cc8b 介绍的六类机制。这是概念上的处理路径，不表示每一轮必定执行六次压缩。

| 机制 | 主要作用 | 简单理解 |
| --- | --- | --- |
| Tool Result Budget | 控制过大的工具输出 | 测试日志太长，先限制输出规模 |
| Snip | 裁剪局部低价值内容 | 删除部分不再重要的搜索结果 |
| Microcompact | 压缩局部工具调用记录 | 已找到目标文件，减少早期探索记录 |
| Context Collapse | 折叠历史上下文视图 | 保留当前关键过程，折叠早期内容 |
| Autocompact | 总结历史并重建消息序列 | 把几十轮对话整理为任务摘要 |
| Reactive Compact | 处理请求超限后的恢复 | API 报上下文过长后再次尝试压缩 |

## 轻量压缩：不必等到窗口满

例如模型为了定位一个函数，先后执行三次 Grep，最后通过 Read 找到了真正需要修改的代码。前面的大量搜索结果已经没有那么重要，Harness 可以优先裁剪这些冗余内容，而不必立即总结整个会话。

这些机制可能在请求前检查上下文，但**检查不等于实际发生压缩**。如果内容不大、没有达到条件，消息可能保持不变。

## Autocompact：接近阈值时整体总结

当轻量处理仍不足以满足上下文预算，并达到自动压缩条件时，Claude Code 可以把历史过程总结为较短的摘要。例如：

```text
压缩前：
用户要求优化 SQL
→ 阅读代码 → 搜索调用位置 → 修改 SQL
→ 运行测试 → 发现分页错误 → 多轮修复

压缩后（示意）：
任务：优化 SQL 查询性能
约束：不能修改 API 返回结构
已完成：修复 N+1 查询
当前问题：分页边界测试失败
下一步：修复测试并重新验证
```

摘要能够大幅减少 Token，但属于**有损压缩**：一些没有被写进摘要的早期细节可能丢失。因此通常优先采用更局部的处理方式。

Autocompact 不是必须等到 Context Window 100% 用完才执行。可以用一个假设的 200K Token 窗口理解：

```text
90K  / 200K：正常运行
156K / 200K：轻量处理后继续运行
180K / 200K：假设达到自动压缩阈值
 56K / 200K：Autocompact 后的示例占用
```

以上数字仅为示意，**不是 Claude Code 的真实固定阈值**。具体触发还与版本、配置、可用预算和实际压缩结果有关。

## Reactive Compact：超限后的兜底

即使请求前进行了估算，实际调用模型时仍可能因为上下文或媒体内容过大而失败。Reactive Compact 是失败后的恢复路径，不是每轮都会发生的第六次压缩。

# 与上下文准备的关系

上一篇的 Context Preparation 负责把 Git 状态、CLAUDE.md 等必要背景提供给模型；本篇的 Context Compaction 则在消息越来越多时，决定哪些信息需要裁剪、折叠或总结。

**一句话：Claude Code 持续管理上下文，优先轻量压缩；当接近预算阈值且轻量处理不够时，再执行 Autocompact，超限失败时可能启动 Reactive Compact。** 关键项目约束最好保存在明确的文档中，不要只依赖很久以前的聊天记录。
