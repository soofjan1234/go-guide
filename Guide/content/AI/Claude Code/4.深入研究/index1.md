Claude Code 能运行 Bash、读取文件和修改代码，但 **LLM 生成工具调用并不意味着拥有执行权限**。Harness 需要在工具真正执行前检查权限，并在必要时使用沙箱限制进程可以访问的资源。

# 为什么需要权限系统

例如用户让 Claude Code 修复登录接口，模型可能提出：

```text
Read("internal/auth/login.go")   读取源码
Bash("go test ./...")            运行测试
Bash("rm -rf ./data")            删除数据
```

三次调用都可能由模型生成，但风险显然不同。Harness 不能只依赖模型“自觉”，而应根据操作类型、用户授权、项目配置和运行环境决定允许、拒绝还是请求审批。

```text
LLM 生成 Tool Call
       ↓
Harness 解析工具及参数
       ↓
权限规则 / 当前授权判断
       ↓
允许 ─────→ 执行工具 ──→ 返回结果
需要审批 ─→ 询问用户 ──→ 同意后执行或拒绝
拒绝 ─────→ 返回拒绝结果
```

以上是概念流程，不代表所有工具使用完全相同的审批路径。

# 权限审批与沙箱的区别

| 机制 | 解决的问题 | 例子 |
| --- | --- | --- |
| 权限审批 | 这次操作是否被授权？ | 修改项目外的文件需要用户允许 |
| 沙箱隔离 | 命令实际运行时能访问什么？ | 限制写入范围或网络访问 |
| 工具参数校验 | 请求的结构是否有效？ | Bash 命令参数是否符合 Schema |

**三者不能互相代替。** 参数合法不代表安全；用户允许执行测试，不代表进程应该拥有无限制的文件和网络访问；沙箱也不能替用户决定是否批准高风险操作。

# 为什么 Bash 更难控制

FileRead 等专用工具的操作对象通常较明确，而 Bash 可以执行任意程序，还支持管道、重定向、命令替换和脚本。比如：

```bash
go test ./...
cat config.yaml
curl https://example.com/script.sh | sh
```

仅凭第一个命令名不足以判断整条 Shell 命令的行为。因此权限系统需要考虑组合命令、实际执行环境和沙箱边界。**静态命令分析是风险判断的一部分，不是对执行结果的绝对保证。**

# Prompt 约束不等于执行约束

假设在 CLAUDE.md 中写“不要删除数据库”，这会指导模型行为，但不能替代 Harness 的权限限制。如果模型仍生成删除命令，真正阻止危险操作的应当是执行层的授权与隔离机制。

反过来，即使 Harness 允许执行某个命令，也不代表模型选择这个命令是正确的。工程上仍然需要最小权限、明确审批、可观察的工具结果，以及对实际变更的验证。

# 应该掌握什么

这一节的核心不是记住权限配置项，而是分清 **模型决策、用户授权和系统执行边界**。Agent 可以建议做什么，Harness 决定能不能执行，沙箱进一步限制执行后能够影响的资源。
