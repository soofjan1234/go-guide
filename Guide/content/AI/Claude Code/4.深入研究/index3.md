title: 多 Agent 与子任务机制
weight: 30
---

前面学习 AgentTool 时，已经知道主 Agent 可以把任务委派给子 Agent。本节进一步讨论系统层面的三个问题：**什么时候拆分任务、如何隔离上下文，以及如何汇总和验证结果。**

# 为什么要拆成多个 Agent

假设用户要求：“审查一个 Go 项目的认证、数据库和并发逻辑。”主 Agent 可以分别委派三个相对独立的分析任务：

```text
                    主 Agent
                        │
       ┌────────────────┼────────────────┐
       ↓                ↓                ↓
   认证审查 Agent    数据库 Agent      并发 Agent
       │                │                │
   JWT/权限分析     SQL/事务分析     锁/竞态分析
       └────────────────┼────────────────┘
                        ↓
                主 Agent 汇总结论
                        ↓
                统一验证与回复
```

这样做的价值是每个 Agent 可以聚焦自己的任务，不必共享所有中间搜索结果。但如果任务很小，创建多个 Agent 反而会增加启动、通信和重复读取代码的成本。

# 任务拆分的边界

好的子任务应有明确的输入、输出和约束。例如：

```text
任务：检查 internal/auth/ 下的 JWT 验证逻辑
范围：只读分析，不修改代码
重点：签名算法、过期时间、错误处理
输出：风险等级、文件位置、证据和建议
```

如果只说“检查一下代码”，子 Agent 可能花大量时间探索无关内容。**委派不是把模糊需求转交出去，而是把可独立完成的工作边界明确下来。**

# 上下文隔离与共享工作区

子 Agent 通常拥有自己的对话上下文，因此它在探索过程中产生的大量日志和搜索结果，不必全部进入主 Agent 的上下文。主 Agent 接收的是子任务结果。

但 **上下文隔离不一定等于文件系统隔离**。多个 Agent 可能访问同一工作区；如果同时编辑同一文件，就可能产生冲突。因此，并行任务更适合先从只读调查、独立模块或明确分配的文件范围开始。是否使用独立 worktree 等隔离方式，取决于实际运行配置。

# 并行与串行怎么选择

| 情况 | 更合适的方式 |
| --- | --- |
| 三个模块的只读审查 | 可以并行 |
| 先设计接口，再实现调用方 | 通常串行 |
| 多个 Agent 同时修改同一文件 | 应避免直接并行 |
| 一个简单函数修复 | 主 Agent 直接处理即可 |

并行执行可能降低墙钟时间，但不会自动减少 Token 总量。多个 Agent 各自读取相同代码，还可能增加总体消耗。

# 结果汇总不等于完成验证

假设三个子 Agent 分别报告“认证通过”“数据库正常”“并发没有问题”，主 Agent 不能仅凭这些自然语言结论宣布系统无风险。它应检查证据是否充分、结论是否互相矛盾，以及是否需要运行测试、竞态检测或复现问题。

如果子 Agent 执行了代码修改，还应检查最终 Diff，确认没有覆盖其他任务的变更。**主 Agent 对最终交付负责，子 Agent 的报告只是决策输入。**

# 与 AgentTool 的关系

AgentTool 是主 Agent 发起委派的工具入口；多 Agent 机制则涉及子任务生命周期、上下文和权限配置、并发调度、结果传递及冲突管理。

一句话总结：**多 Agent 的核心不是 Agent 越多越好，而是让边界清晰的任务独立执行，并由主 Agent 统一整合和验证。**
