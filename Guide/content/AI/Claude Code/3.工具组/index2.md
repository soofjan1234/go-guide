SkillTool 的价值是**让 Agent 按需获取一套可复用的任务指导**，而不是把所有领域知识、流程和规则都塞进长期生效的 System Prompt。

# Skill 到底是什么

假设项目经常需要进行 Go 性能分析。你可以创建一个 Skill，说明何时使用 pprof、如何采集 CPU Profile、如何比较优化前后的结果，以及报告应该包含哪些指标。

```text
用户：分析这个 Go 服务的 CPU 性能瓶颈
  ↓
Agent 判断适合使用性能分析 Skill
  ↓
SkillTool 定位并加载对应指导
  ↓
Agent 根据 Skill 说明调用 Bash、Read 等工具
  ↓
生成性能分析结论
```

**Skill 本身通常不是一个执行程序。** 它首先是可被 Agent 发现和读取的任务说明；具体操作仍需要模型选择工具，由 Harness 执行。

# Skill 与普通 Prompt、Tool 的区别

| 概念 | 解决的问题 | 示例 |
| --- | --- | --- |
| Prompt | 给模型行为指令 | 回答简洁、遵循项目规范 |
| Tool | 提供可调用的实际能力 | Bash 执行命令、Read 读取文件 |
| Skill | 封装特定任务的知识与流程 | Go 性能分析、代码评审流程 |

一个 Skill 可以指导 Agent 使用多个 Tool，但它不会因为写在 Markdown 里就自动获得新权限。

# 为什么要按需加载

如果把几十种工作流程全部写进 System Prompt，会增加上下文占用，还可能让无关规则干扰任务。Skill 采用按需发现与加载的方式：在需要时让模型获得相应指导。

可以把流程分成三个阶段：

1. **发现**：Agent 知道有哪些 Skill 可以使用，以及各自适合什么场景。
2. **加载**：选择目标 Skill，取得详细指令、参数或关联资源。
3. **执行**：Agent 按指导继续调用工具，并根据实际结果调整。

例如“修复一个简单拼写错误”通常不需要性能分析 Skill；而“定位服务的 P99 延迟瓶颈”才可能触发它。

# SkillTool 的执行边界

文章涉及 Skill 查找、参数处理、与命令或 MCP 能力的衔接等机制。需要注意不同 Skill 的具体执行方式可能不同：有的主要注入指导内容，有的可能关联可执行命令或委派执行。不能把所有 Skill 都理解为“读取 SKILL.md 后直接运行一段脚本”。

**Skill 提供的是工作方法，不是执行权限。** 例如 Skill 要求运行部署命令，Harness 仍然需要按当前权限和安全策略决定是否允许。

# 什么时候值得写 Skill

只有在流程具有复用价值时，Skill 才比普通提示词更合适。例如：

- 每次都要执行相同的基准测试步骤，并记录 P50、P95、P99。
- 每次代码评审都要检查并发安全、错误处理和回归测试。
- 每次写技术文档都要遵循固定的章节结构和验证规范。

反过来，只有一句“回答尽量简洁”，直接写在项目规则中即可，没必要单独创建 Skill。

# 与 Agent Loop 的关系

SkillTool 帮助 Agent 获得完成任务的流程知识；Read、Bash 等工具提供真实操作能力；Agent Loop 负责根据执行结果继续决策。**Skill 是可复用的方法，Tool 是可执行的能力，Agent 是选择和协调它们的主体。**
