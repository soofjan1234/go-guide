AgentTool 的作用是**把一个相对独立的任务委派给另一个 Agent 执行**。主 Agent 不必在同一条上下文里完成所有搜索、分析和验证，而是可以把部分工作交给子 Agent，最后接收结果。

# 为什么需要子 Agent

假设用户要求：“分析 Go 项目中的认证模块，找出安全风险并给出修改建议。”主 Agent 可以把认证代码审查委派给子 Agent，同时自己继续分析相关业务逻辑。子 Agent 在自己的上下文里读取文件、搜索调用链并得出结论，最终将摘要交回主 Agent。

```text
用户请求
  ↓
主 Agent 判断需要独立分析
  ↓
AgentTool（任务说明、Agent 类型等）
  ↓
Harness 创建子 Agent 执行上下文
  ↓
子 Agent：模型决策 → 工具执行 → 结果反馈
  ↓
子 Agent 返回结果
  ↓
主 Agent 整合结果并决定下一步
```

**AgentTool 不是普通函数调用后直接得到确定性结果**。它启动的是另一个可能进行多轮推理和工具调用的 Agent 执行过程。

# 子 Agent 与普通 Tool 有什么区别

| | 普通 Tool | AgentTool |
| --- | --- | --- |
| 执行对象 | 预先实现的工具逻辑 | 一个独立的 Agent 执行流程 |
| 是否自行推理 | 通常不需要 | 需要 |
| 是否可继续调用工具 | 由工具实现决定 | 可以使用分配给它的工具 |
| 返回内容 | 文件内容、命令输出等 | 子任务的分析或执行结果 |

例如 `Grep` 只负责查找匹配内容；子 Agent 可以先 Grep，再 Read，再分析调用关系，必要时继续调查。

# 上下文隔离：为什么不是把所有消息交给子 Agent

如果主 Agent 已经经历几十轮对话，其中包含大量无关日志，那么直接复制完整上下文会增加 Token 开销，也可能干扰子任务。子 Agent 通常拥有独立的消息历史，并接收明确的任务说明以及适当的项目背景。

例如主 Agent 给子 Agent 的任务可以是：

```text
审查 internal/auth/ 中的 JWT 验证逻辑。
只分析，不修改文件。
重点检查过期时间、签名算法和错误处理。
返回有证据的风险点及文件位置。
```

这比“帮我看看项目有没有问题”更有效，因为明确了目标、范围、约束和期望输出。**上下文隔离不代表子 Agent 自动拥有完整项目知识**；它仍需按需读取代码。

# 工具与权限边界

主 Agent 能使用的工具，不一定全部开放给子 Agent。Harness 可以按 Agent 类型和执行配置分配可用工具，例如只读审查 Agent 主要使用搜索与读取能力，而不需要修改文件。

要区分：**Prompt 中写“不要修改”属于行为约束，工具权限限制才是执行层面的边界**。即使模型产生了不合适的工具调用，Harness 仍应根据实际授权决定是否执行。

# 返回结果与主 Agent 的责任

子 Agent 返回“发现两个风险”，不代表主 Agent 可以不检查就宣称已修复。主 Agent 应判断结论是否有文件位置、复现条件或测试证据；如果子 Agent 修改了代码，还需要验证实际工作区状态。

另外，子 Agent 并不总能节省资源。创建独立上下文、重复读取代码和协调结果都可能产生额外成本。**任务可独立、边界清晰、探索量较大时更适合委派；简单修改通常直接使用普通工具更高效。**

# 与 Agent Loop 的关系

AgentTool 对主 Agent 来说是一次工具调用；对子 Agent 来说，则是一次完整或部分独立的 Agent Loop。Harness 负责建立执行环境、管理权限与生命周期、收集子 Agent 结果，再把结果返回主 Agent。
