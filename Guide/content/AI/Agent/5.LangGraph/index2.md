# 状态保存

## Checkpointer

按执行引擎的检查点规则保存状态、消息和进度，用来延续会话、暂停审核和失败恢复。

保存当前目标、消息、已完成步骤、待办和必要工具结果。具体保存时机与恢复位置由执行引擎决定。

编译图时传入 `checkpointer`；使用高层 Agent 时，也可以在创建时配置保存器。

| 保存方式 | 特点 |
| --- | --- |
| `InMemorySaver` | 适合演示，进程退出后数据丢失 |
| 数据库保存器 | 支持持久化，需要连接、初始化与访问控制 |

跨进程恢复要连接同一存储，并加载兼容的图定义。检查点不会把 Python 调用栈和所有局部变量原样保存下来。

### Checkpointer 与 Store

Checkpointer 保存某个线程的状态；Store 保存跨线程复用的资料，如用户偏好与历史事实。长期资料按需读取，也需要更新与删除，不是全部追加到每轮 Prompt。

## thread_id

在执行配置的 `configurable.thread_id` 中传入，用来找到同一线程的状态。

1. 相同 ID：关联已保存的状态。
2. 不同 ID：进入另一条线程，不自动继承旧任务。
3. 恢复待审核任务：沿用原 ID，并提交对应的恢复输入。

`thread_id` 不等于用户 ID，也不是权限凭据。服务端要校验当前用户是否能访问或审核这条任务。

## get_state

读取已有状态与待执行信息，不会推动图继续运行。

看到有待执行节点，不代表它正在后台自动执行；动态中断仍需要外部提交恢复输入。

# 人工介入

## interrupt 与 Command

`interrupt(payload)` 把待审核内容交给调用方，暂停当前流程；`Command(resume=...)` 带回外部意见，成为对应 `interrupt()` 的返回值。

动态中断要配置 checkpointer，并使用稳定的 `thread_id`。通过普通 `invoke()` 调用时，暂停信息可以出现在 `__interrupt__` 中，调用会返回，不是一直阻塞等待用户回复。

| 方向 | 传递什么 |
| --- | --- |
| `interrupt(payload)` | 待审核内容，如草稿与版本 |
| `Command(resume=...)` | 审核意见，如批准、编辑或拒绝 |

恢复输入不会自动成为 State 字段。节点需要校验意见，再返回状态更新。载荷应使用可序列化的数据，不能塞入数据库连接或模型客户端。

## 审核流程

生成草稿 → 暂停审核 → 编辑后再次审核，或批准后执行 → 结束。

1. 草稿在独立节点生成，结果写入 State。
2. 审核节点通过 `interrupt` 展示草稿、版本和待确认操作。
3. 调用方使用同一线程提交审核意见。
4. 编辑后保存新版本，再次暂停；批准后进入执行节点。

一次恢复可能再次遇到中断，不一定直接结束。调用方要检查返回的执行状态。

## 审核版本与并发

审核意见应绑定草稿版本，旧版本的批准不能直接用于新草稿。

提交恢复前检查权限、载荷格式、任务状态和版本。版本字段本身不能阻止并发重复提交，还需要业务锁、条件更新等并发控制。

# 恢复与副作用

## 节点从哪里恢复

包含动态 `interrupt()` 的节点在恢复时会从头执行；再次走到对应中断时，读取恢复值，再继续后面的逻辑。

因此中断前的代码要允许重复执行。不要把发送邮件放在 `interrupt()` 前面，否则首次运行就可能发送，恢复时还可能再次发送。

普通审核恢复通常不需要重跑已经完成的草稿节点，但审核节点内的准备逻辑可能重跑。

## 批准后执行

将发送邮件、创建工单等动作放在批准后的独立节点。外部动作仍可能因失败恢复而重跑，幂等与回执核验见 [工程设计]({{< relref "AI/Agent/6.工程设计/index1.md" >}})。

## 中断容易踩的坑

1. 不要用宽泛异常捕获吞掉 `interrupt` 的控制信号。
2. 同一节点有多个中断时，保持调用顺序稳定，避免恢复值错位。
3. 节点恢复时，不能依赖上一次调用的局部变量仍然存在。
4. 固定节点前后的静态断点与动态中断不同，不能混用恢复规则。

静态断点常用于调试和外部控制；动态中断适合在节点内部提出具体的审核或补充信息请求。
