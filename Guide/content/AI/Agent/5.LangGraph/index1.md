# State、Node、Edge

State 保存当前数据，Node 执行一个步骤，Edge 决定下一步去哪。

比如文本处理：原文进入状态 → 清洗节点 → 摘要节点 → 检查节点 → 输出或重试。

## State

保存原文、处理结果、校验状态、尝试次数等流程数据。

| 定义方式 | 特点 |
| --- | --- |
| `TypedDict` | 描述字典结构，主要用于静态类型检查；不自动校验或补默认值 |
| Pydantic `BaseModel` | 在模型构造等边界做类型与约束校验，可定义默认值 |

节点通常只返回变化字段，其他字段继续保留。不要因为用了 Pydantic，就认为每次状态更新和业务结果都已经通过校验。

## Node

读取当前状态 → 调用模型、工具或业务逻辑 → 返回局部更新。

例如摘要节点返回 `summary` 和新的 `attempts`，不需要把原文再返回一遍。优先显式返回更新，不依赖原地修改状态传递结果。

## Edge

| 类型 | 作用 |
| --- | --- |
| `add_edge` | 固定前后关系 |
| `add_conditional_edges` | 按状态选择后续路线 |
| 回到已有节点的边 | 形成循环，必须配退出条件 |

`START`、`END` 是入口和出口标记。注册节点不会自动执行，还要将它接入路线。

# 状态更新

## Reducer

Reducer 决定某个字段的旧值与新值如何合并。

1. 没有 Reducer：通常用新值覆盖旧值。
2. 列表拼接：例如 `operator.add`，把节点新返回的记录追加进去。
3. 消息合并：使用 `add_messages` 或 `MessagesState`，按消息 ID 追加或更新。

已有记录为 `["清洗完成"]`，节点只返回 `["摘要完成"]`。如果返回旧列表加新记录，追加 Reducer 会重复拼接旧内容。

## 并发写同一字段

同一轮多个节点写同一字段，默认覆盖规则通常会触发并发更新错误。

让分支写不同字段，或者为共享字段定义适当的 Reducer。Reducer 负责合并数据，不负责安排执行顺序。

# 流程编排

## 顺序

清洗 → 摘要 → 输出。后一步读取前一步更新后的状态。

## 条件分支

检查通过 → 输出；不通过 → 兜底。

互斥路线交给条件边选择。不要再额外连一条固定边来充当“默认分支”，否则固定路线也可能执行。

## 循环

生成 → 检查 → 合格结束，不合格时带失败原因重新生成。

业务状态中记录尝试次数，达到上限就降级或结束。重复调用模型不一定改善结果，长度合格也不等于内容正确。

`recursion_limit` 限制超步骤数量，不是模型调用次数，也不能替代业务退出条件。

## 并行与汇合

清洗后的文本同时交给摘要和关键词节点，等两条分支完成，再进入汇总节点。

1. 分支之间不能存在数据依赖。
2. 分别写 `summary`、`keywords`；共享记录字段需要合适的 Reducer。
3. 用显式汇合边等待需要的前驱，不能假定汇总节点会自动发现依赖。
4. 事件或追加记录的顺序，不一定是业务要求的顺序。

如果关键词需要新摘要，就应改成摘要 → 关键词，不能放在同一轮并行。

# 执行机制

## compile 与 invoke

构图声明状态和连线；`compile()` 检查部分结构约束并生成可执行图；`invoke()` 带输入真正运行。

编译不会执行节点，也不证明业务逻辑正确。没有配置状态保存时，不能指望下一次调用自动继承前一次的进度。

## Super-step

运行时按超步骤推进，每轮可以执行一个节点或多个并行节点：

选择本轮节点 → 读取可见状态并执行 → 合并更新 → 进入下一轮。

**同一轮写入的更新，不会立刻被同一轮其他节点读到。**

| 轮次 | 执行节点 | 可用数据 |
| --- | --- | --- |
| 1 | 清洗 | 原文 |
| 2 | 摘要、关键词 | 已清洗文本 |
| 3 | 汇总 | 合并后的摘要与关键词 |

这里仅统计业务节点轮次。清洗结果在下一轮可见，并行结果合并后再供汇总使用。

## 流式观察

| 模式 | 主要输出 |
| --- | --- |
| `updates` | 节点提交的增量 |
| `values` | 合并后的完整状态 |
| `messages` | 模型消息片段与元数据 |

流式输出用于观察执行或展示内容，不会改变节点依赖。某条路线到达 `END`，也不意味着强制取消其他正在执行的分支。

## 工具调用图

模型节点 → 检查工具调用 → `ToolNode` → 工具结果回到模型；没有工具调用时结束。

可以用 `MessagesState` 管消息，用 `tools_condition` 路由，用 `ToolNode` 执行工具。这是高层 Agent 封装的基本循环；跨请求会话和人工中断还需要配置状态保存。
