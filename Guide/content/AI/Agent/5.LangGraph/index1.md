# 状态
## State、Node、Edge

1. State 保存当前数据
  - 保存原文、处理结果、校验状态、尝试次数等流程数据。
2. Node 执行一个步骤
3. Edge 决定下一步去哪。
  - START`、`END` 是入口和出口标记。注册节点不会自动执行，还要将它接入路线。

## Reducer

Reducer 决定某个字段的旧值与新值如何合并。

1. 没有 Reducer：通常用新值覆盖旧值。
2. 列表拼接：例如 `operator.add`，把节点新返回的记录追加进去。
3. 消息合并：使用 `add_messages` 或 `MessagesState`，按消息 ID 追加或更新。

已有记录为 `["清洗完成"]`，节点只返回 `["摘要完成"]`。如果返回旧列表加新记录，追加 Reducer 会重复拼接旧内容。

### 并发写同一字段

同一轮多个节点写同一字段，默认覆盖规则通常会触发并发更新错误。

让分支写不同字段，或者为共享字段定义适当的 Reducer。Reducer 负责合并数据，不负责安排执行顺序。

## 流程编排

1. 顺序
   - 清洗 → 摘要 → 输出。后一步读取前一步更新后的状态。
2. 条件分支
   - 检查通过 → 输出；不通过 → 兜底。
   - 互斥路线交给条件边选择。不要再额外连一条固定边来充当“默认分支”，否则固定路线也可能执行。
3. 循环
   - 生成 → 检查 → 合格结束，不合格时带失败原因重新生成。
   - 业务状态中记录尝试次数，达到上限就降级或结束。重复调用模型不一定改善结果，长度合格也不等于内容正确。
   - `recursion_limit` 限制超步骤数量，不是模型调用次数，也不能替代业务退出条件。
4. 并行与汇合
   - 清洗后的文本同时交给摘要和关键词节点，等两条分支完成，再进入汇总节点。
   - 分支之间不能存在数据依赖。
   - 分别写 `summary`、`keywords`；共享记录字段需要合适的 Reducer。

# 状态保存
## Checkpointer

按执行引擎的检查点规则保存状态、消息和进度，用来延续会话、暂停审核和失败恢复。

保存state、进度、中断

| 保存方式 | 特点 |
| --- | --- |
| `InMemorySaver` | 适合演示，进程退出后数据丢失 |
| 数据库保存器 | 支持持久化，需要连接、初始化与访问控制 |

## thread_id

在执行配置的 `configurable.thread_id` 中传入，用来找到同一线程的状态。

1. 相同 ID：关联已保存的状态。
2. 不同 ID：进入另一条线程，不自动继承旧任务。
3. 恢复待审核任务：沿用原 ID，并提交对应的恢复输入。

`thread_id` 不等于用户 ID，也不是权限凭据。服务端要校验当前用户是否能访问或审核这条任务。

# 人工介入
## interrupt 与 Command

`interrupt(payload)` 把待审核内容交给调用方，暂停当前流程；`Command(resume=...)` 带回外部意见，成为对应 `interrupt()` 的返回值。

动态中断要配置 checkpointer，并使用稳定的 `thread_id`。通过普通 `invoke()` 调用时，暂停信息可以出现在 `__interrupt__` 中，调用会返回，不是一直阻塞等待用户回复。

| 方向 | 传递什么 |
| --- | --- |
| `interrupt(payload)` | 待审核内容，如草稿与版本 |
| `Command(resume=...)` | 审核意见，如批准、编辑或拒绝 |

恢复输入不会自动成为 State 字段。节点需要校验意见，再返回状态更新。

## 审核流程

生成草稿 → 暂停审核 → 编辑后再次审核，或批准后执行 → 结束。

1. 草稿在独立节点生成，结果写入 State。
2. 审核节点通过 `interrupt` 展示草稿、版本和待确认操作。
3. 调用方使用同一线程提交审核意见。
4. 编辑后保存新版本，再次暂停；批准后进入执行节点。

一次恢复可能再次遇到中断，不一定直接结束。调用方要检查返回的执行状态。

## 节点从哪里恢复

包含动态 `interrupt()` 的节点在恢复时会从头执行；再次走到对应中断时，读取恢复值，再继续后面的逻辑。

因此中断前的代码要允许重复执行。不要把发送邮件放在 `interrupt()` 前面，否则首次运行就可能发送，恢复时还可能再次发送。

普通审核恢复通常不需要重跑已经完成的草稿节点，但审核节点内的准备逻辑可能重跑。
