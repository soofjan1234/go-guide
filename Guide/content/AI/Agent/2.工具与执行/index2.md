## ReAct

根据当前信息判断下一步 → 调用工具 → 观察结果 → 再决定下一步。

比如排查订单：先查订单状态，发现已发货，再查物流；物流正常就解释进度，异常则查处理规则。

1. **适合**：需要边查边判断，步骤不确定的任务。
2. **优点**：可以及时利用外部反馈。
3. **代价**：调用轮次可能较多，容易重复查询或循环。

原始 ReAct 使用 Thought、Action、Observation 表达过程。工程实现可以用结构化 Tool Calling 执行类似循环，不必靠解析模型写出的 `Action:` 文本。

## Plan-and-Execute

先拆任务 → 按计划执行 → 根据关键反馈调整剩余计划。

比如生成报告：收集资料 → 核验数据 → 生成草稿 → 检查引用。

1. **适合**：任务较长，可以拆成多个阶段。
2. **优点**：目标和进度清晰，方便检查和恢复。
3. **代价**：初始计划可能有错，规划和执行需要共享状态。

### 怎么避免每一步都重新规划

1. 保存当前目标、已完成步骤、剩余任务和预算。
2. 普通超时或格式错误由当前步骤处理。
3. 只有关键前提失效、连续失败或需求改变时才重规划。
4. 复用仍然有效的结果；前提改变时，也要重新核验受影响的已完成步骤。

## Reflection

先生成结果 → 按标准检查 → 根据反馈修改。

适合回复草稿、代码、报告等可以明确检查的产物。检查依据可以是测试、规则、引用或人工反馈。

**增加一次反思不等于增加一份正确证据。** 同一个模型可能重复原来的错误，额外检查也会增加成本和延迟。

## 怎么选

| 情况 | 优先考虑 |
| --- | --- |
| 一次检索或模型调用可以完成 | 简单调用 |
| 步骤和分支可以提前规定 | 工作流 |
| 要根据外部结果不断选下一步 | ReAct 类工具循环 |
| 任务长，需要阶段与进度管理 | Plan-and-Execute |
| 有明确检查标准，需要修订结果 | 增加 Reflection |

这些方式可以组合：先规划阶段，阶段内边查边做，最后检查结果。先验证简单方案的效果，再增加复杂度。

## 多 Agent

把任务拆给不同 Agent，各自处理后再汇总。

有独立子任务、不同工具权限或不同专业职责时可以考虑。比如资料收集与独立核验，再汇总报告。

### 为什么不一开始就用多 Agent

1. 多次调用增加费用和延迟。
2. 需要处理任务分工、消息传递、重复工作和结果冲突。
3. 更多模型不一定带来更正确的结果。

先确认单 Agent 的具体瓶颈，再判断拆分是否有效。
