# 框架
## 代码框架与平台怎么选

标准问答和业务工作流，平台可以减少搭建工作；需要细粒度状态、复杂分支、业务代码集成和自动化验证时，代码框架更方便控制。

选型还要看部署、权限、版本维护和团队能力。流程很简单时，模型 SDK 加业务代码也可以完成。

| 需求 | 选择方向 |
| --- | --- |
| 流程简单，追求少依赖 | 模型 SDK 加业务代码 |
| 需要模型、检索和工具组件 | LangChain 等组件框架 |
| 需要状态、分支、循环和恢复 | LangGraph 等编排框架 |
| 主要研究多 Agent 协作 | 再比较 AutoGen、CAMEL、AgentScope 等 |
| 主要由业务人员搭建和调整 | 比较 Dify、Coze 等平台 |


选型看流程控制、调试、部署、权限和维护成本。具体 API、授权协议和功能要按使用版本核对，不能只按框架名字决定。

## LangChain 与 LangGraph

| 框架 | 主要作用 |
| --- | --- |
| LangChain | 连接模型、检索和工具，提供高层 Agent 接口 |
| LangGraph | 用状态、节点和边组织执行，支持循环、分支、检查点和中断 |

LangChain Python v1 的 `create_agent` 基于 LangGraph 构建，已经封装常见的模型与工具循环。

标准工具助手可以先用 `create_agent`。需要自己定义节点、状态和路由时，再直接构建 LangGraph。需要记忆或人工审核，不代表一定要绕过高层 Agent 接口。

## 包怎么分

1. `langchain-core`：消息、工具、Runnable 等基础抽象。
2. 模型与存储集成包：适配具体服务商和外部系统。
3. `langchain`：高层 Agent 与相关开发接口。
4. `langgraph`：图编排、状态与执行能力。

在 LangChain Python v1 中，**LangChain 更接近高层 Agent Framework，LangGraph 更接近底层 Agent Runtime / Orchestration Framework**。

# 核心组件

## 模型与消息

聊天模型接收消息，通常返回 `AIMessage`，其中可能包含文本、工具调用和用量信息，不只是一个字符串。

| 消息 | 用途 |
| --- | --- |
| `SystemMessage` | 规则与角色说明 |
| `HumanMessage` | 用户输入 |
| `AIMessage` | 模型回复或工具调用请求 |
| `ToolMessage` | 工具执行结果，与调用 ID 对应 |

统一使用 `invoke()`，不代表所有组件的输入输出类型相同。文本模型、本地 pipeline 和聊天模型仍要分别确认数据格式。

切换服务商时，也要检查工具调用、结构化输出、流式返回等能力，不能只换地址就认为功能完全相同。

## 提示词模板

`ChatPromptTemplate` 组织消息模板，把固定规则与动态输入分开；`PromptTemplate` 主要生成字符串。

模板填充变量后交给模型。它不会自动校验回答，也不能代替业务权限和规则检查。

## 输出解析

商品描述可能写着“无线鼠标，售价 99 元”，业务需要的是名称、价格等字段。

输入参数 → Prompt → Model → Parser → 业务数据。

| 方式 | 做什么 |
| --- | --- |
| `StrOutputParser` | 提取适合后续使用的文本输出 |
| `JsonOutputParser` | 把 JSON 内容解析成对应的 Python 数据 |
| `PydanticOutputParser` | 解析后按字段类型与约束校验 |
| `with_structured_output(...)` | 使用模型集成支持的结构化输出方式，并封装解析 |

### 三层校验

1. **格式合法**：能解析成 JSON。
2. **结构合法**：必填项、类型、枚举、范围符合要求。
3. **业务正确**：价格真实、商品存在、信息有来源。

合法 JSON 也可能写着负数价格。Pydantic 校验通过，也不能证明价格来自真实数据。

### Pydantic 容易混淆的地方

`description` 是字段说明，真正的限制来自类型、枚举和范围等规则。Pydantic v2 中，`T | None` 没有默认值时，表示允许空值，字段仍然必须提供。

默认模式可能进行类型转换；需要拒绝转换时使用严格配置。

### 结构化输出就一定正确吗

不一定。JSON 格式约束与严格 Schema 约束不同，具体能力取决于模型和集成。即使结构符合 Schema，仍需处理拒答、截断、调用失败和事实错误。

解析器通常不会自动重新调用模型。失败后应显式反馈校验问题、有限重试，超过次数就返回失败或转人工。

# 工具与会话接口

## 工具怎么定义

`@tool` 将业务函数暴露为工具：名称和说明描述用途，参数 Schema 描述输入，函数体执行真正的业务操作。

比如查询商品：模型填写商品标识，程序查业务服务，返回价格和库存。名称与说明应能区分“查商品资料”和“查实时库存”。

参数格式通过后，仍要检查商品是否存在、用户是否有权限。工具参数校验与模型输出校验，发生在不同位置。

## bind_tools 与 create_agent

| 方式 | 负责什么 | 还需要自己做什么 |
| --- | --- | --- |
| `model.bind_tools(...)` | 给模型绑定工具定义，让它生成调用请求 | 执行工具、回填结果、继续调用和控制循环 |
| `create_agent(...)` | 封装常见的模型与工具调用循环 | 接入业务工具，配置权限、上下文、限制和审核 |

`bind_tools` 返回绑定后的模型对象，不会自动修改原对象，也不会替你运行本地函数。

### 手动执行与回填

读取 `AIMessage.tool_calls`，执行对应函数，再构造带 `tool_call_id` 的 `ToolMessage`。原始调用消息与结果一起交回模型，继续本轮处理。调用流程与校验原则见 [工具调用与能力接入]({{< relref "AI/Agent/2.工具与执行/index1.md" >}})。

## create_agent 的会话状态

`create_agent` 将消息保存在状态的 `messages` 中。配置 checkpointer 后，用 `thread_id` 关联同一会话的状态。

### 连续对话怎么传消息

沿用同一个保存器、同一个 `thread_id`，通常只提交本轮新增消息，由框架恢复并合并历史。

如果再次提交已经保存的整段历史，可能造成重复消息。每轮新建内存保存器，也会丢失上一轮状态。

## 检查工具与会话是否生效

用商品查询助手验证：第一轮明确商品，第二轮只问“它还有多少库存”。

1. 同一线程是否能理解“它”的指代。
2. 是否出现正确的工具调用、参数和对应结果。
3. 换一个线程后，是否保持会话隔离。
4. 实时库存是否重新查询，而不是复制上轮答案。

消息和执行日志用于检查公开的调用过程，不等于模型完整的内部思考。提示词要求“必须查工具”，也不能替代业务侧的执行核验。
