# 记忆

记忆是系统保存的信息，上下文是本轮实际给模型的信息。

完整历史可以存在数据库里，但模型每轮只看到传入的部分。存过不等于这次能看见。

## 保存哪些信息

| 信息 | 内容 | 怎么使用 |
| --- | --- | --- |
| 近期消息 | 当前对话、刚返回的工具结果 | 按预算放入上下文 |
| 任务状态 | 目标、已完成步骤、待办、执行结果 | 每轮提供必要状态 |
| 用户偏好与历史事实 | 表达方式、过去确认的信息 | 按相关性读取，允许纠正 |
| 业务知识 | 规则、文档、历史案例 | 检索后提供相关片段 |

模型参数中的知识与应用保存的用户记忆不同。向数据库写入偏好，不会直接更新模型参数。

# 上下文工程

本轮上下文按三个步骤准备：检索相关信息 → 压缩过长内容 → 组装并核验来源。


检索部分见 [RAG 构建与评估]({{< relref "AI/Agent/3.记忆与上下文/index2.md" >}})，本篇重点是历史压缩与上下文组装。

## 历史太长怎么办

1. 为本轮输入和输出预留 Token 预算。
2. 保留当前任务、近期消息和关键约束。
3. 旧消息生成摘要，完整历史另外保存。
4. 细节需要时从原文检索，不能只依赖摘要。

### 摘要怎么做

用“旧摘要 + 新移出的消息”增量更新。重点保留目标、用户修正、已确认事实、已执行动作和未完成事项。

金额、ID、收件人等不能模糊的信息单独结构化保存。摘要可能遗漏或改写细节，需要保留回查来源。

### 能按轮数直接截断吗

不能只看轮数，还要看 Token 大小和消息关系。工具调用与对应结果要成对保留，并满足模型接口要求，避免只剩结果却找不到调用。

### 上下文策略的取舍

| 策略 | 本轮提供什么 | 代价 |
| --- | --- | --- |
| 全量历史 | 所有消息 | Token 不断增长，可能超出窗口 |
| 窗口裁剪 | 近期消息与必要状态 | 可能遗漏早期信息 |
| 摘要加近期消息 | 历史摘要与近期原文 | 摘要可能遗漏或改写细节 |

可以使用消息裁剪或摘要 middleware。每轮把全部历史重新摘要，摘要步骤本身仍会越来越贵。

## 上下文怎么组装

目标与规则 → 当前状态 → 相关历史与资料 → 本轮请求。

这是一种组织示例，具体消息顺序按接口和任务验证，不把“放在首尾”当成普遍最优策略。

1. 去掉无关和重复内容。
2. 长工具结果只取需要的字段。
3. 标注来源、时间和适用范围，纠正时更新旧信息。
4. 区分指令、参考资料和工具返回。

### 来源冲突怎么办

按字段判断权威来源。订单当前状态看授权业务接口，退款规则看适用的业务规则，表达方式可以参考用户偏好。

没有适用于所有信息的固定优先级；还要核对时间、权限和适用范围。

## 缓存

| 缓存 | 缓存什么 | 主要边界 |
| --- | --- | --- |
| 工具结果缓存 | 可复用的只读查询结果 | Key 包含相关身份与参数，设置失效规则 |
| 推理 KV cache | 历史 Token 的 K/V | 减少重复计算，占用推理资源 |
| API Prompt Caching | 服务商支持复用的输入前缀 | 命中条件、费用和延迟收益看服务规则 |

缓存不能替代长期记忆。写操作不能靠工具缓存跳过，副作用要靠幂等与结果核验控制。

线程状态和跨线程资料的具体保存方式放在 [LangGraph 状态保存]({{< relref "AI/Agent/5.LangGraph/index2.md" >}})。
