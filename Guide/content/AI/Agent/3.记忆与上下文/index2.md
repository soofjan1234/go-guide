# 知识库构建

加载清洗 → 分块 → Embedding → 保存索引、原文和元数据。

RAG 在回答前提供外部资料，不修改模型权重。知识文档适合查说明书和规则，实时库存等动态事实优先查业务接口。

## Document

`page_content` 保存正文，`metadata` 保存来源、章节、版本、权限等信息。

清洗时去掉重复内容和导航噪声，检查表格是否丢失行列关系。切分后仍要保留来源，便于引用和更新。

## 分块

块太大容易混入噪声，太小容易丢失语义；重叠保留边界信息，也会增加存储和重复召回。

| 方式 | 适合什么情况 |
| --- | --- |
| `CharacterTextSplitter` | 有明确分隔符的简单文本，可能留下超长段落 |
| `RecursiveCharacterTextSplitter` | 按分隔符优先级继续拆过长内容，适合作为通用基线 |
| `MarkdownHeaderTextSplitter` | 按标题分组，并保存标题层级元数据 |
| Token 计数分割 | 需要对齐模型输入预算 |

Markdown 可以先按标题分组，再递归限制长度；章节内做重叠，不必跨章节拼接。

### 参数怎么理解

1. `chunk_size`：目标块大小上限，单位取决于长度函数。
2. `chunk_overlap`：目标重叠量，不保证每对块恰好重叠这么多。
3. `len`：按字符计数，不是 Token 数。
4. `separators`：优先按较大边界拆，再尝试更小边界。

中文资料优先考虑标题、段落和句号。按 Token 分块时使用匹配的 tokenizer，并分别核对 Embedding 单次输入和生成模型总上下文预算。

普通分割器的 `split_text` 通常返回字符串列表，`split_documents` 返回文档列表并保留元数据；标题分割器的 `split_text` 则可以直接返回 Document。

## Embedding 与向量存储

Embedding 计算向量，向量存储负责保存向量、文本、元数据和 ID，并提供索引查询。

1. `embed_documents`：文本列表变成向量列表。
2. `embed_query`：问题变成查询向量。
3. 建库与查询使用匹配的模型、维度、归一化和指令配置；维度相同不代表向量可以混用。
4. 更换 Embedding 模型时，通常需要重新计算文档向量。

向量不是文本的可逆编码，也不是唯一标识。型号、编号等精确查询，往往还需要关键词检索。

### 向量库常见接口

| 接口 | 用途 |
| --- | --- |
| `from_documents` / `add_documents` | 初始化或添加文档，通常调用文档嵌入 |
| `similarity_search` | 返回相近文档 |
| `similarity_search_with_score` | 返回文档及实现相关的分数 |
| `as_retriever` | 包装成可组合的检索组件 |

FAISS 是向量索引库，封装后可以关联文档，但不自动提供完整的权限和服务治理。加载已有索引仍要配置匹配的 Embedding；索引文件不包含服务端模型权重。

只加载可信索引，不能对陌生文件启用危险反序列化。文档更新、删除和版本失效也要同步处理。

# 检索与生成

问题 → 检索候选 → 过滤与重排 → 组装资料 → 模型回答 → 核对引用。

`vector_store` 保存与查询向量，`retriever` 接收问题并返回文档，可接入 LCEL。


## 混合检索与重排

关键词检索适合编号、专有名词等精确匹配；向量检索适合语义相近、说法不同的内容。需要时组合，是否有效看任务集评估。

不同检索分数不能直接相加时，可以用 RRF 按排名融合。重排是在候选集内重新排序，召回阶段漏掉的资料不能靠重排凭空找回。

## Top-K 与检索分数

Top-K 只限定候选数量，不保证候选相关，也不保证资料足够回答问题。

分数含义由实现决定：有的是相似度，有的是距离。默认 FAISS L2 距离越小越近，不能直接当成置信概率，更不能照搬其他索引的阈值。

## 回答链要保留什么

1. `question`：原始问题。
2. `docs`：检索候选，保留来源与版本。
3. `context`：实际传给模型的资料文本。
4. `answer`：模型生成的回答。

有了这些字段，才能分清“检索到了什么”和“模型用了什么”。引用标记存在，不代表它支持对应结论，仍要核对。

权限过滤应在资料进入模型前完成。证据不充分时补查、追问或说明缺口，不能因为返回了候选就强行回答。

# 评估与调优

## 先分清失败位置

| 问题 | 优先检查 |
| --- | --- |
| 答案不在知识库 | 资料覆盖、版本、解析和清洗 |
| 有答案但检索不到 | 分块、Embedding、查询表达、关键词匹配 |
| 候选有答案但排得靠后 | 候选数量和重排 |
| 找到证据仍答错 | 噪声、资料组织、提示词和模型使用证据的能力 |
| 无答案还编造 | 证据充分性判断与拒答策略 |

## 指标

1. **Recall@K**：找到的相关项 / 全部标注相关项。
2. **Precision@K**：相关返回项 / 实际返回项。
3. **MRR**：每题取首个相关结果排名的倒数，无相关结果记 0，再求平均。
4. **生成质量**：事实正确、证据支持、引用准确、无答案时处理合理。
5. **工程表现**：延迟、Token、费用。

评测单位要明确是文档还是分块。分块方案改变后，相关标签也要重新对应。

固定任务集和基线，一次改一类因素，再用独立测试集确认效果。增加 K 或重排会增加开销，要一起比较质量、延迟和成本。

普通 RAG 预先规定检索与生成流程；Agentic RAG 让模型决定何时检索、是否继续补查，两者都需要同样的证据核验和评估。
