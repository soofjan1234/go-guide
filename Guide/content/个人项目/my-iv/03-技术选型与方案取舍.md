## 6. RabbitMQ 与异步设计

### 为什么选择 RabbitMQ

异步解耦、削峰填谷

视频发布成功后还需要执行缓存预热、关注流 Fanout 和推荐向量生成。

如果多人全部同步执行，会阻塞发布接口并影响用户体验，可能造成数据库、Redis 压力大

RabbitMQ 将他们解耦，让 API 只完成核心事务和事件投递；将瞬时请求转换为队列积压，由 Worker 按自身消费能力处理。

### 为什么没有选择其他消息队列

当前业务主要是视频 Fanout、缓存预热和互动异步落库，更看重灵活路由、手动 ACK/NACK、失败重试和较低的使用复杂度，不需要 Kafka 的超高吞吐、长期日志保留与事件回放能力。

如果未来曝光和播放行为发展为大规模事件流，并需要被推荐、分析等多个下游反复消费，可以考虑将这类链路迁移到 Kafka。

Redis 已经承担 Feed 缓存、热榜、关注索引、点赞状态等职责。如果再使用 Redis Stream，会让缓存与消息系统共享资源和故障域，增加压力与故障风险。

当前场景也没有强依赖 RocketMQ 的事务消息、延时消息、顺序消息等能力，因此 RabbitMQ 更符合项目复杂度。

### 使用

1. 使用持久化的 Topic Exchange

通过 Routing Key 将互动、视频发布和曝光事件路由到对应队列。其中 video.published 同时绑定 Fanout 队列和 Embedding 队列，实现一条发布事件被不同业务独立消费。当前以精确 Routing Key 为主，选择 Topic 是为了后续扩展事件类型和通配符订阅。

2. 使用 WorkQueue 以及 Publish/Subscribe

- 点赞、收藏状态变更采用单队列竞争消费
- 视频发布事件需要同时触发两项独立任务：缓存预热和向量生成

### 问题

1. 消息处理失败

消息格式不对，会拒绝入队；业务处理失败，比如某服务不可用，会重新入队再次消费

如果遇到永久性错误，就会出现死循环，所以应该加上指数退避，最大重试次数，死信队列等

2. 重复消费

RabbitMQ 的手动 ACK 模式保证的是“至少一次”，不能保证“只消费一次”。消费者还没返回ACK，MQ这里就再次发送，所以业务必须幂等

- 点赞/收藏/取消事件重复消费
    - 如果两次消费携带的 IdempotencyKey 相同， MySQL + Redis 都不会产生任何写操作
    - 没有幂等键（比如 MQ 事件没有传），也通过" 只有状态真正变化才改计数 "保证幂等。
    - 行级锁防并发乱序
    - 评论创建用 MySQL 唯一索引 ( user_id + idempotency_key ) 做最后兜底
- Embedding 模块
    - 使用 video_id + model upsert，重复发布事件会覆盖同模型向量。
- Fanout 模块
    - ZSet 的 member（成员）是唯一的
    - 同一个 videoID + authorID + publishedAt 重复插入，不会产生重复项

3. 消息丢失

- 生产端开启 Publisher Confirm：
    - `ack`：RabbitMQ 已接收该消息
    - 可以同步等待，也可以异步批量处理
- MQ端：
    - Exchange 设置为 durable。
    - Queue 设置为 durable。
    - Message 设置为 persistent。
- 消费端：
    - 手动 ACK 模式，确保消息被正确处理后返回 ACK。
    - 失败重试机制，处理失败的 ACK 回调。
- 额外：
    - Confirm 只说明消息到达 RabbitMQ，不保证消息一定路由到了 Queue。还需要设置 `mandatory=true` 并处理 Return 回调。
    - 需要更强数据安全时，可以使用 Quorum Queue，让消息复制到多个节点后再确认。

4. 顺序消费

当前消费者在单 Worker 内使用循环串行处理，同一队列正常情况下基本按投递顺序消费，但项目没有承诺严格顺序。多 Worker、失败重入队和断线重投都可能导致乱序。

点赞与取消点赞存在同一业务键的顺序要求，后续应在事件和数据库记录中增加单调递增版本号，只允许新版本覆盖旧版本。这样不需要牺牲全局吞吐，也能保证最终状态正确。

## 8. 视频

### 上传

1. 大小限制
    - 视频不能大于512MB
    - 图片不能大于20MB
2. 类型限制，通过MimeType检测
    - .mp4/.mov/.webm
    - .jpg/.jpeg/.png/.webp
3. ffprobe 读取真实媒体信息
    - 检查视频时长、轨道、宽高等播放元数据
4. 保存时间戳-随机后缀.扩展名

### 大文件

1. MaxBytesReader 在读取请求体前限制上传大小：c.Request.Body = http.MaxBytesReader
2. c.FormFile("file") 底层使用 Go 的 multipart 解析。较小的表单内容保存在内存中，超过内存阈值的文件内容会写入操作系统临时目录。
3. Gin/Go 常见的默认 multipart 内存阈值约为 32 MiB。SaveUploadedFile 打开 multipart 文件，然后分块复制到目标文件

### 播放

1. MP4 faststart

MP4 文件主要包含两类重要数据：
- mdat：实际音视频数据。
- moov：视频时长、轨道、时间轴、关键帧位置等播放元数据。

一些 MP4 文件的结构是：mdat 大量视频数据，moov 元数据，浏览器需要先读到 moov 才知道如何解码和定位视频。

MP4 faststart 会把播放所需的 moov 元数据移动到文件前部。浏览器拿到文件开头后就能更快解析并开始播放。对短视频首帧体验非常关键。

2. Range 请求

浏览器播放视频时会通过 Range 请求加载部分字节。支持 Range 后，用户拖动进度、断点加载和分段缓冲都更顺畅

项目通过静态文件服务支持浏览器分段请求，g.Static("/uploads", "./uploads") 返回 206、Content-Range 和指定字节段内容

3. 视频预加载

服务端根据当前视频返回后续若干条视频资源，客户端提前加载封面和视频元数据，把部分网络和解析工作移动到用户观看当前视频期间，从而降低下一条视频的首帧耗时和切换卡顿

4. QoS

播放 QoS 用于衡量视频实际播放质量。客户端采集首帧耗时、卡顿次数和观看时长，通过带幂等键的接口写入 QoS 流水，后台可以按视频和时间窗口统计首帧 P95、卡顿率等指标

## 9. 登录和鉴权

JWT是一种基于JSON的开放标准，用于在客户端和服务端之间安全传递身份信息。思想是用户信息直接放到token里面，服务器不用保存状态。

它由Header、Payload和Signature三部分组成，其中Header描述JWT信息，Payload存储用户声明信息，Signature用于防止数据被篡改

### 问题

1. 无法注销
2. JWT太大
3. Payload 信息泄露

因为JWT本身无状态，如果access token设置很长有效期，会增加泄露风险；设置很短又会导致用户频繁登录。

所以采用access token和refresh token机制，access token用于访问业务接口，生命周期较短，refresh token生命周期较长，用于换取新的access token，同时refresh token可以在服务端存储并主动吊销，提高安全性。

### 其他方式

1. Seesion + Cookie
    - 服务器端保存用户状态，客户端保存会话ID到cookie
    - 会话ID在服务端存储，分布式得共享
2. OAuth2
    - 登录找Google认证，返回授权码
    - 不共享密码，只共享授权。
