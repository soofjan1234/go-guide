# 排查

Grafna 看 API QPS、5xx 错误率、API P95、Feed P95、Feed 缓存命中率、上传处理耗时和 Worker 成功率

## Feed P95 升高时，你会按什么顺序排查？

1. 先看是否某个 scene 单独升高，再看缓存命中率。
2. 然后看 MySQL 慢查询、Redis 命令耗时。最后结合最近发布、热点内容和 MQ 积压判断是否有突发写入影响读链路。

## 缓存命中率下降时，可能有哪些原因？

先区分是哪类缓存下降：
- 只有 page 下降：优先看 TTL、游标和 limit 是否让请求过于分散。
- card 或 stat 下降：看新内容访问、预热与写入是否成功；Stat 本身 TTL 短，也更容易过期。
- 三类同时下降：优先检查 Redis 是否重启、淘汰数据，以及最近是否修改了 key 规则。

## 如何区分 API 慢、MySQL 慢、Redis 慢和 MQ 积压？

| 情况 | 看什么证据 | 怎么判断 |
|---|---|---|
| **API 自身慢** | 接口 P95、CPU、请求排队，以及各处理步骤耗时 | MySQL、Redis 都快，但接口仍慢，继续查计算、数据组装、锁竞争等 |
| **MySQL 慢** | SQL 耗时、慢查询、锁等待、连接池等待 | 时间主要花在执行 SQL 或等待数据库连接 |
| **Redis 慢** | Redis 调用耗时、超时、连接池等待、服务端慢命令 | 时间主要花在访问 Redis；命中率高也可能读得慢 |
| **MQ 积压** | 待消费数、未确认数、发布/消费速率、最老消息等待时间 | 消息进入速度持续超过处理速度，或消费者停止、反复失败 |

## 如果 Feed 首页突然被打爆，你的应急方案是什么？

先保护数据库，让首页还能提供基本内容，再查流量来源和瓶颈：
1. 先限流，控制进入系统的请求量。
2. 尽量复用首页缓存，减少回源。
3. 降低非核心功能的消耗。
   - 如果推荐计算成为瓶颈，可以暂时返回已有的最新流或热门列表；必要时暂停低优先级后台任务，给读请求留出资源。
3. 观察指标，确认是否止血。

## 如果 Redis 故障 10 分钟，核心功能如何降级？

保留基本浏览，限制数据库回源；依赖 Redis 的实时功能允许降级
1. 最新流、视频详情、关注流：都走数据库，限制查询大小
2. 热门流：返回已有榜单快照；没有快照则暂时返回最新流
3. 推荐流：没有影响
4. 点赞收藏：
   - 暂停点赞收藏，明确提示稍后重试
   - 限流后直接写 MySQL
   - 内存存一份

## 如果 MySQL 主库 CPU 打满，你怎么定位和止血？

1. 先看慢查询、连接数、QPS、锁等待和当前最重 SQL。
2. 止血动作包括提高缓存 TTL、关闭低优先级回源、限流热点接口、暂停部分 Worker 写入和扩容只读能力。
3. 根因可能是缓存失效、索引缺失、N+1 回源或批量任务冲击。

## 如果点赞数短时间显示错误，你怎么解释最终一致性？

1. 点赞接口先更新 Redis 实时状态和计数，MySQL 由 Worker 异步落库。
2. 短时间内 Redis、Feed 计数缓存和 MySQL 可能存在延迟差异，TTL 过期和 Worker 落库后会修正。
3. 核心要保证幂等和最终事实一致。

## 你在这个项目里做过最复杂的技术决策是什么？

最复杂的是 Feed 主链路的性能设计：
1. 页缓存只保存排序结果，卡片和计数独立缓存，读取时批量聚合并恢复原顺序。
2. 这个设计同时处理性能、缓存一致性和业务扩展。
3. 它也支撑 timeline、hot、following、recommend 多种 Feed 复用同一响应组装链路。

## 有遇到什么问题吗/做了什么优化

1. 补齐行为上报

我在短视频 Feed 项目里，用 AI 协助补齐过推荐反馈链路，主要分四步。

第一，定位问题。 原来前端主要上报曝光，播放、完播和跳过记录不完整，观看时长也不可靠。网络重试还可能造成重复流水、重复计数和重复消息。

第二，明确业务规则。 我和 AI 一起确定，用用户、请求和视频标识一次观看会话。首次播放记 play，播放进度达到 90% 记 complete，播放后未完播就离开记 skip，暂停、缓冲和页面隐藏期间不累计观看时长。

第三，让 AI 按测试驱动实施。 前端提取独立的观看状态机，用单调时钟累计有效播放时间，测试暂停恢复、循环播放、重复上报等场景。后端通过唯一索引和冲突处理实现幂等，避免重试重复写入、计数和发消息。

第四，验证完整链路。 我让 AI 控制真实浏览器执行观看操作，再检查数据库和 RabbitMQ，确认未完播产生“曝光、播放、跳过”，完播产生“曝光、播放、完播”，同一会话没有重复事件。

最终补齐了有效观看时长、完播和跳过数据，为后续推荐优化提供了更可靠的反馈。

2. 完善 MQ 失败治理

主队列设置有限重试

超过次数进入 DLQ

保存失败原因、原消息和重试次数

增加队列积压、消费失败率和死信数量告警

提供人工重放或补偿工具
