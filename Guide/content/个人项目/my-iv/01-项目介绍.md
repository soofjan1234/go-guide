# 1. 项目总览

## 请介绍一下项目

项目能干什么？GCFeed 是一个短视频 Feed 系统，覆盖内容发布、Feed 分发、刷流消费和用户互动等功能。

项目用的技术是：使用 Gin、React、MySQL、Redis、RabbitMQ，并通过 Prometheus 和 Grafana 进行监控。

核心链路是：
- 视频发布后写入 MySQL，并投递发布事件到 RabbitMQ；Worker 消费事件，完成缓存预热和关注流分发
- 用户请求 Feed 时，系统根据不同场景读取轻量分页结果，再批量组装视频、作者和互动数据。

## 项目有哪些 Feed 场景

| 场景 | 读取方式 | 适用用途 |
| --- | --- | --- |
| `timeline` | 按发布时间倒序读取公开视频 | 最新流 |
| `hot` | 合并 Redis 分钟桶，读取最近一小时热榜 | 热门流 |
| `following` | 合并用户 Inbox 和关注作者 Outbox | 关注流 |
| `recommend` | 推荐服务生成候选，再复用 Feed 卡片组装链路 | 个性化推荐流 |

## 项目的分层架构

| 层 | 职责 |
| --- | --- |
| Domain | 实体、领域规则、领域错误和 Repository 接口，定义核心业务 |
| Infrastructure | GORM、Redis、RabbitMQ、JWT、配置和迁移等具体技术实现 |
| Application | Service、Strategy 和 Worker，负责同步与异步用例编排 |
| Interfaces | HTTP Handler、DTO、路由和中间件，负责系统与外界交互 |

## 为什么不用传统三层 MVC，而用 DDD？

传统 MVC 在业务简单的时候开发效率比较高，但是随着业务复杂度增加，Service层容易变得臃肿，业务规则、数据库操作、缓存以及消息处理会耦合在一起。

DDD主要解决的是业务复杂度问题，通过Domain封装核心业务规则，让业务逻辑和基础设施解耦。Application层负责流程编排，Infrastructure负责具体技术实现。

在我的 Feed 项目中，比如视频发布流程，会由Application负责协调保存视频、发送消息等流程，而视频状态变化、关注关系等业务约束放在Domain层，这样后续扩展推荐、审核等功能时，代码维护成本更低。

## Feed 读取链路

Feed 请求先根据不同场景，获取带排序信息的轻量分页结果，再批量组装视频详情、作者信息和互动计数。

1. 减少宽表 Join 和排序成本
2. 拿到视频 ID 后，批量查询视频详情、作者信息和互动计数
    - 不同数据变化频率不一样，可以分别缓存
    - 所有用户都能共享 Card 和 Stat 缓存，只在最后补充自己的行为状态
3. 多种 Feed 策略可以复用详情组装

# 2. Redis 与缓存设计

Redis 主要用于降低 MySQL 压力、提升 Feed 读取速度，并支持高频排序和互动操作。MySQL 仍然是最终事实源。

## Feed 相关

刷 Feed 是典型的读多写少场景。如果每次请求都关联查询视频、作者和统计表，数据库压力会很大。

分页缓存、Feed Card、Feed Stat，使用的都是 Redis String

1. Feed 分页缓存

这一页有哪些视频、按什么顺序排、下一页从哪儿开始

首页缓存 TTL 是 5 秒，后续页缓存 TTL 是 45 秒，并通过 key hash 增加抖动。首页对新内容敏感，TTL 更短；后续页访问稳定性更强，TTL 可以更长。

2. Feed Card、Feed Stat

Feed Card 存储视频的标题、封面、作者等稳定信息，相对稳定，TTL 15 分钟。

Feed Stat 存储点赞、评论、收藏等互动计数，变化频繁，TTL 15 秒。

读取时使用 MGET 批量取多个 key；写入时用 Pipeline 批量发送 SET，减少网络往返

## 热榜分钟桶、滑动窗口

Redis ZSet 适合增量更新和按分数排序：

- key: feed:hot:minute:v1:202611161200
- member：视频 ID。
- score：这个视频在这一分钟获得的热度分。

点赞权重是 3，收藏权重是 4，评论权重是 5

项目将互动热度写入分钟桶，查询时通过 `ZUNIONSTORE` 合并最近 60 个分钟桶，形成最近一小时的滑动热榜。相比在 MySQL 中持续聚合和排序，这种方式更适合高频变化的实时排名。

## 关注流 Inbox / Outbox

普通作者发布后，视频写入粉丝 Inbox；大 V 发布后，视频写入作者 Outbox。

这两类索引都需要按发布时间排序、快速插入、截断旧数据和游标范围查询，因此使用 Redis ZSet。

Redis 缺失时，可以根据 MySQL 中的关注关系和视频记录回源查询。

### 为什么阈值选2000

1. 用同一份数据测了多个阈值，每档都跑了**读多**和**发布多**两种场景，比较读取延迟、分发延迟和 CPU。
2. **比 10,000 分发快。** 阈值降到 2,000 后，分发 P95 从 124～128 毫秒降到 22～23 毫秒，读取 P95 仍在 6～7 毫秒。
3. **比 1,000 更省 CPU，读取也更快。** 继续降到 1,000，分发只再快几毫秒，但读取和 CPU 开销都上去了

## 点赞、收藏

点赞、收藏属于高频写操作。项目使用 Redis 保存即时状态和分片计数：用户操作后快速返回，通过 `WATCH` 和事务 Pipeline 原子更新，再由 RabbitMQ Worker 异步落库，减少对 MySQL 的高频更新。

1. 用户点赞、收藏

保存用户即时点赞/收藏状态

2. 点赞、收藏分片计数器

16个分片。如果热门视频的所有点赞都更新同一个 Redis Hash 字段，会形成热 Key。拆成 16 个分片，可以把写压力分散到多个 Key

FeedStat 是读模型，最终给 Feed 页面使用的统一结构
