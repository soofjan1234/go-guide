# 面试月度复盘

## 2026.02-03

> 来源：`26.2`、`26.3`。当时项目与简历和现在差异较大，因此只保留仍有复习价值的共性问题。

### 知识理解不足

- **Go runtime 是 3 月最明显短板**：Channel 只会基本收发流程，追到 sendq/recvq、阻塞与唤醒、何时触发调度就断；Select 不清楚 case 轮询、公平性和 `runtime.selectgo`；Mutex 对 state、自旋、正常/饥饿模式及 Unlock 唤醒链路不完整。
- **GMP / GC 知道框架但串不起来**：work stealing、系统调用阻塞、抢占等局部知识存在，但状态转换和“为什么这样设计”不稳；GC 三色标记连颜色含义都会混，写屏障不会解释。
- **网络基础持续暴露**：2 月 NAT/P2P 已不稳，3 月虽能讲映射与 STUN，但 TCP/UDP、三次握手、异常网络排查仍明显薄弱。
- **Redis / MySQL 基础**：2 月场景题暴露穿透/击穿/雪崩、布隆、过期/淘汰、RDB/AOF，以及索引、页、Change Buffer、资源排障需要从原理解释，而不是背结论。

### 项目实现不清楚

- **穿透链路**：跨月都被追问。对手机、NAS、云端信令、STUN/穿透服务、SDK 的职责逐渐能讲，但可靠性、低延迟、P2P→Relay 降级仍缺完整闭环。回答应固定为“主路径 → 降级 → 可观测”。
- **消息可靠性 / 顺序性**：被问 NSQ 如何保证不丢和顺序时，只答 ACK、持久化、按时间排序，缺生产确认、消费重试/幂等、队列顺序边界等完整机制。
- **文档分块与结果聚合**：能描述主/子索引和聚合流程，但为什么 5MB 判大文件、1MB 分块，以及更小/更大块的代价仍不够清楚。

### 验证依据说不清

- **性能数字缺上下文（跨月重复）**：2 月被追问数据量和内存量级，3 月又被追问 1MB 分块为什么最好、其他参数差多少；说明“有做实验，但记不住实验条件和结果”是持续问题。
- **参数来源说不清**：分块大小、批量大小、并发数等只说“测试后最佳”不够，至少要记住候选组、数据规模、核心指标、最终结果与副作用。
- **选型需要 Benchmark**：回答选型时应带数据规模、测试方法、资源限制、性能/效果指标及最终取舍，而不只是“更轻量”。



## 2026.04

> 来源：`26.4` 的 4 月 9 日、15 日、27 日、29 日面试记录。单场记录中的 A/B/C/D、√ 是当时的自评；以下只归纳反复出现或影响回答完整度的问题。

### 知识理解不足

- **Go 基础有进步，但追问仍不稳**：9 日 Mutex 加锁流程、Interface、Select 随机选择答得弱；15 日 GMP、Channel、逃逸和 Map 并发安全已有改善，27 日 GMP、Select、Channel 多数能答。下一步要把“机制为什么这样设计”讲清，例如 P 的作用、Select 的用途，而不只复述结构。
- **MySQL 从概念题转向排障题后断层**：B+ 树、事务、锁等基础题能答；27 日“除了 EXPLAIN 如何确认索引生效”没有答好，29 日又被追问慢查询、用了索引仍慢、Join 与分布式锁。需要掌握从慢日志、执行计划到实际扫描量和等待的排查顺序。
- **系统与网络基础仍有空缺**：9 日 Time Wait、进程工作目录、端口和 Shell 基础失分；27 日又出现 IP/掩码、交换机与路由器；29 日高负载但低 CPU 的 Linux 排障也被追问。应能先解释指标含义，再给检查命令和可能原因。

### 项目实现不清楚

- **项目介绍缺稳定主线**：9 日“印象深刻的项目”自评 B，29 日开场仍需临时选择项目。固定一个主项目，用“问题 → 我的职责 → 关键方案 → 结果”讲完，再接受追问。
- **方案取舍能讲结果，边界还需补齐**：27 日 NSQ、Bleve 为什么选用均自评 B；29 日同步方案已能说明“用户触发 + 定时兜底”相对实时监听的取舍，但继续追问文件层级建模、查询代价和联想词召回时，需要把数据结构、更新成本与适用规模说完整。
- **实现细节要落到代码行为**：29 日 Gin 参数校验追问 `required`、空字符串和空格；只说“做参数校验”不够。类似问题要能明确默认行为、额外校验规则及错误返回。

### 验证依据说不清

- **性能与选型还缺可复述证据**：同步方案能讲 watcher 数量、内存和漏事件风险，但“目录规模到什么程度、比较了哪些方案、结果差多少”尚未形成固定口径。为 NSQ、Bleve、同步方案各准备一组约束、候选方案、测量指标和取舍结果；没有实测数字就明确说是观察或设计判断。
- **排障回答缺验证步骤**：面对 OOM、慢查询、索引已用但仍慢、系统负载高等问题，先确定现象与指标，再列检查顺序和判断条件，避免直接猜原因。

## 2026.05

> 来源：`26.5` 的 5 月 6 日、13 日、18 日、25 日记录。6 日总结和 18 日记录有明确自评；其他仅列出题目的地方，不据此判断答错。25 日面试记录标注“已过”。

### 知识理解不足

- **Go 基础能答，底层追问和现场题仍有缺口**：6 日对 GMP、Channel、Map 的基础有准备，但 G 的上下文、Map 迁移条件答得不稳；18 日对 `sync.Map` 的适用场景与优化、分段锁不熟，`defer` 题虽给出输出却没说明闭包取值。复习时要能把机制落到使用边界和一段代码的实际结果。
- **网络、操作系统和 MySQL 的链路题较弱**：6 日总结明确记下网络轮询 IO 模型、TCP 拥塞控制、QUIC、gRPC、进程调度，以及 MVCC 快照、Redo Log 恢复和两次写等回答不足。这些题需要按“触发条件 → 处理过程 → 保证范围”串起来。
- **场景题需要把方案落地**：13 日被问连续签到、独立访客计数和重复请求；18 日出现 SQL 排序、员工关系树与路径题。18 日自评中，SQL 的 `ORDER BY access_count DESC` 写错，关系树和路径题不会做；应练习先明确输入输出，再给数据结构、边界和复杂度。

### 项目实现不清楚

- **项目难点与消息链路被反复追问**：6 日、13 日、18 日多次出现“最困难的项目”、NSQ 选型、事件记录、消息丢失和顺序性。除了说方案，还要说清业务为什么需要事件、失败后如何恢复，以及哪些保证由队列提供、哪些要业务补齐。
- **网络穿透与安全要形成完整链路**：6 日被追问 NAT 类型、多级路由和 P2P；25 日继续追到移动端与 NAS 的打洞、失败后的 STUN/TURN 路径、信令协议，以及 HTTPS 之外再加密的理由。25 日已通过，说明项目主线有进展；这些边界仍值得固定成可复述的流程。
- **技术选型和个人贡献要能经受细问**：18 日问到 ES/Bleve、NSQ 内存问题和搜索压缩机制，自评后两项不了解；25 日还追问 fsnotify 改为队列加广度遍历、延迟同步的具体场景。介绍方案时区分“我实现了什么”“组件本身做了什么”“尚未验证什么”。

### 验证依据说不清

- **性能数字和线上规模要有来源**：13 日问到文件索引同步器“下降 90%”如何测、项目真实 QPS；同月还反复出现 CPU/内存高、线上故障和 Go 内存泄漏排查。准备每个数字的测量方法、前后条件和指标口径，并能说明排查从哪项观测开始。
- **AI 使用和协作流程需要可验证的回答**：6 日、13 日、18 日多次问 AI 生成代码如何检查、需求变动后如何避免改坏旧实现、代码评审和协作流程。回答应落到具体的约束、测试、Diff 审查和最终由谁确认，而不只说“用 AI 提效”。
