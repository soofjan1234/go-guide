# 面试月度复盘（二）

> 范围：2026 年 6～9 月。6～7 月多为题目清单，除原记录明确写出的复盘外，不把“被问到”视为“答错”；8～9 月结合问答稿和单场自评判断表现。`同类追问预测`不作为真实面试证据。

## 2026.06

> 来源：`battle/26.6` 的 1、3、4、8、10、12、15、18、29、30 日记录。

### 知识理解不足

- **Go 从定义题转到运行场景**：Channel 关闭、Slice 共享底层数组、Map 并发、GMP、netpoll 和系统调用反复出现；12 日还考了跨 Goroutine 的 `recover` 与 WaitGroup 计数错误。要能对具体代码说明结果、阻塞条件和修复方式，而不只背结构。
- **数据库与网络要串成故障链路**：MySQL 的索引选择、MVCC、Redo/Undo、慢查询，Redis 的过期与持久化，以及 TCP 的 `TIME_WAIT` 均被追问。答题顺序应是“现象 → 机制 → 如何验证”，避免只列术语。
- **系统设计题开始增多**：12 日的机器状态覆盖、重复任务、热门库存和网站访问慢，18 日的 LRU 与点赞服务，都要求同时考虑并发、幂等、存储和可观测性。12 日记录明确把状态、库存、慢站点列为需复盘项。

### 项目实现不清楚

- **文档中心被持续下钻**：Bleve 与 ES 的选择、索引峰值内存、分块大小、中文分词、数据规模和用户慢操作上报几乎每场都出现。需分清搜索引擎基础开销、解析峰值和分块/批量提交各自解决的问题。
- **文件同步的取舍已能说出，但边界要完整**：10 日记录把 fsnotify 内存开销和跨平台监听列为复盘项；18 日已总结 BFS 扫描用实时性换稳定性，同时会增加 IO、重复触发和扫描中间态风险。回答还需覆盖删除检测、任务去重及恢复。
- **NSQ、穿透和加密需要交代责任边界**：被反复问消息丢失与重复、顺序保证、对称型 NAT 失败后的路径、TLS 之外再加密和密钥分发。先明确 SDK、Broker 与自己实现的部分，再讲业务补偿。

### 验证依据说不清

- **性能数字仍缺实验口径**：内存降低 76%、同步器内存变化、百万文件遍历耗时、项目 QPS 和 NSQ 吞吐收益均被追问。每个数字至少准备测试设备、数据集、优化前后值、采集工具及代价；没有测量的量级不要估成事实。
- **线上问题要给定位证据**：29 日问到少量用户下单失败且测试环境无法复现。要能说明如何用请求标识、日志、指标和版本变更缩小范围，再验证假设，而不是直接猜数据库或网络。

## 2026.07

> 来源：`battle/26.7` 的 2、3、4、6、10、14、22 日记录。大部分只记题目，以下是高频追问与待准备项，不代表这些题都答错。

### 知识理解不足

- **Go 并发与内存仍是基础盘**：Channel 收发和关闭、Map 1.24 前后结构、Slice 扩容、逃逸、竞态、GMP 与 `atomic`/锁的选型重复出现；3 日还要求现场写反转链表并用测试验证。准备应落到代码行为、使用条件和并发风险。
- **数据库和网络从概念走向机制**：MySQL Buffer Pool、Doublewrite、Redo/Undo、隔离级别、Redis ZSet、TCP 拥塞控制与 TLS 密钥协商被集中提问。需要能区分“持久化保证、隔离保证、传输保证”各自的边界。
- **工程能力被单独考察**：Gin 请求链路、中间件、API 版本化、优雅关闭、Docker/Compose/K8s、监控与链路追踪多次出现。要明确真实使用过的部分与仅了解的部分，避免把概念储备说成项目实践。

### 项目实现不清楚

- **NAS 的真实部署与个人职责是主线**：6 日连续追问设备芯片和内存、服务部署、SQLite/Ristretto、团队分工，以及云端和文档中心由谁负责。准备一张准确的组件关系图，能逐项说明运行位置、数据流、负责人和故障后表现。
- **穿透与文件同步的异常路径要讲透**：信令、邀请码、SDK、P2P 失败兜底，以及 BFS+Queue 的扫描频率、断点恢复、索引与文件不一致，均被持续追问。主流程之后必须接上失败、重试和一致性收敛。
- **文档中心的优化不能只讲降低内存**：被问分块后的排序/高亮、解析失败、索引中断、中文分词质量和资源预算；要说明优化换来了什么成本，哪些功能是产品范围外。

### 验证依据说不清

- **“为什么这么选”仍要落在约束和数据上**：Bleve/ES、NSQ/RabbitMQ、fsnotify/BFS、解析工具等选型持续被问。统一按“设备约束 → 候选方案 → 测量 → 代价”准备，而不是只说轻量或简单。
- **项目指标和算法效果要可核验**：文档内存、文件同步内存、人脸识别准确率等被追到基线、测试集与团队归属。不能把算法组结果、第三方 SDK 能力或估算值算作自己的实现或实验。

## 2026.08

> 来源：`battle/26.8` 的问答稿和 `iv*.md` 记录。部分 `iv` 只有题目或为空；只对明确标出“卡住”“未答完整”的内容判断表现。

### 知识理解不足

- **Go 底层掌握面扩大，但机制解释仍会断**：Map Swiss Table、GC/写屏障、逃逸、`sync.Map`、Data Race、Channel 和网络 IO 被反复问到。14 日问答里 Go 内存分配回答未完整；18 日还把缓存穿透说成雪崩。应把版本、机制和实际用途对齐，避免术语混用。
- **数据库与网络基础仍需场景化**：联合索引列顺序、SQLite 取消写入、MySQL 崩溃恢复、证书链验证、TCP 对端宕机后的行为和 NAT 故障排查反复出现。按具体请求/事务过程推演，比孤立背概念更有效。
- **系统设计题跨度更大**：分片上传与取消、限时排队执行器、数据库与 MQ 双写、计账超时和下游不幂等均有记录。先冻结输入输出与失败语义，再谈锁、队列或缓存。

### 项目实现不清楚

- **文档中心能讲流程，方案副作用与证据不足**：8 日问答已能说明长文档分块和主/子文档；但搜索引擎性能量级答“不记得”，解析器抽象未答完整。另有记录指出索引时间增加多少、76% 从多少降到多少未给数值。
- **相册、穿透和加密的归属边界被继续核对**：模型由算法组提供、Kotlin/JNI/C++ 推理链路、RK 芯片侧优化、应用层 AES+RSA、穿透 SDK 与中继兜底均被问。21 日明确标出 RK 优化答偏、混合加密协作卡住。说明自己的代码范围和上下游接口，比泛讲算法更重要。
- **AI 开发流程和项目交付闭环要具体**：11 日记录项目从需求到上线时长停顿；15 日问答指出跨端修改与联调闭环未答完整。用一项真实需求说明设计、实现、测试、联调和发布各步由谁负责、留下什么证据。

### 验证依据说不清

- **指标不能只报百分比**：Bleve 内存下降 76%、分词 CPU 下降 63%、索引体积变化都被追问基线、采样条件与质量代价。尤其要解释“分块省峰值内存”是否增加索引时间、体积或结果聚合成本。
- **故障排查要从观测推进到验证**：内存上涨、CPU 周期尖刺、穿透挂了、SQLite 慢查询和大文件上传被问到。准备可执行的检查顺序，并说明如何区分进程 heap、系统内存、磁盘 IO 和下游等待。

## 2026.09

> 来源：`battle/26.9` 的 1～12 场转写与 `iv*.md`。`iv3` 记“终面，无问题”，`iv8` 为空；不据此推断整体通过率或面试结果。

### 知识理解不足

- **Go 会背结构，但遇到变化场景仍可能答偏**：15 日一场能讲 Slice、Channel、GMP 的常见结构，但文件 IO 调度与网络轮询混在一起、GC 写屏障追问答偏；另一场 Slice 共享数组的现场推演反复改口。应从具体执行路径出发，再讲底层名词。
- **中间件选型缺“场景—机制—代价”**：15 日对 RabbitMQ/Kafka/RocketMQ 先给产品标签，追问吞吐的存储与批量机制时未答上；缓存一致性只覆盖删除失败。Redis、MySQL 和 MQ 的回答要讲适用条件与异常窗口，不要把产品能力等同于业务强保证。
- **新领域知识与原有经历之间有边界**：2 日网络岗位追问 VIP 映射数量和令牌桶时卡住；8 日 SRE 面试追问滚动发布 502、RSS 上涨但 heap 平稳时未答完整；10 日 gRPC metadata 未答。对目标岗位新增知识要明确准备，不靠熟悉的 NAS 项目绕开题目。

### 项目实现不清楚

- **项目叙述更丰富，但异常路径仍暴露缺口**：MediaAI NPU 租约被问误回收与旧持有者继续请求，8 日记录标明未答完整；AI 异步任务恢复、文件同步积压、相册扫描的 SQLite 单写者方案也被连续追问。要把状态流转、过期判断、重启恢复、去重和幂等画成一条链。
- **Agent 项目成为新追问中心**：上下文压缩、摘要错误、原文回查、LangGraph 的 State/Checkpoint/Interrupt、工具调用和会话存储多次出现。回答应先交代自己实际实现和测试过的功能，再说参考框架能做什么；2 日对摘要缺细节后的可靠回查未给出完整方案。
- **网络与加密仍不能只讲高层流程**：NAT 穿透保活、报文映射、TLS 之外的应用层加密，以及客户端偶发连接超时的分段排查均被问；8 日网络超时问题未能区分 DNS、TCP、TLS 与应用层阶段。

### 验证依据说不清

- **优化数字的基线仍是跨月重复问题**：11 日文档中心 76% 内存降幅追问时没有具体起止值；23 日继续问分块与批量写入对索引时间、相册 Worker 数、SQLite 写入和“缩短 90 毫秒”的测试条件。为每项数字固定“原值、现值、样本、机器、测量工具、代价”，无法确认的数值从口述中移除。
- **线上故障回答要收束为验证闭环**：8 日错误率从 0.1% 升到 20%、发布期间 502、RSS 增长等场景要求区分影响范围、近期变更、分层指标、止血动作与复盘验证。说出可能原因只是起点，下一句应说明用什么证据排除或确认。
