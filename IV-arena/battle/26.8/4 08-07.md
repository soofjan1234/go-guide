## 网络协议、HTTP/HTTPS 与 TCP

**问：** 从浏览器输入一个 URL 之后，请求和响应之间大概走了哪些协议、发生了哪些事情？

**答：** 首先输入 URL 后会进行 DNS 解析。
先查本地缓存，没有再查解析器，通过迭代方式到几层解析器，解析出一级域名、二级域名，最终得到 DNS 结果。
然后进行 TCP 三次握手。如果是 HTTPS，还会加 TLS。
之后每一层都会进行封装，比如 IP、TCP 都会加头部，再发送给另一端。
另一端解析这些头部后返回结果，再包装返回到调用端。调用端再渲染 CSS、JS、HTML 之类的内容。

**问：** HTTP 协议具体格式了解过吗？大概有哪几部分，或者 HTTP 和 HTTPS 有什么区别？

**答：** 请求有请求头、请求 body、content 这些。
HTTPS 比 HTTP 多了 TLS 的部分，使用混合加密来保证传输可靠性。
我理解它会使用 DH 算法，双方各自生成私钥和公钥，进行公钥交换，然后使用公钥和私钥生成共享密钥，后续用共享密钥进行加密和解密请求。

**问：** TCP 三次握手和四次挥手流程能简单讲一下吗？

**答：** 三次握手的话，A 先向 B 发送第一个握手请求，B 知道 A 的发送能力正常。
B 再发送第二次握手请求给 A，A 知道自己的接收能力和 B 的发送能力正常。
然后 A 发送第三个请求给 B，B 就知道自己的发送、接收能力，以及对方的发送、接收能力都正常，后续就能正常通信。

四次挥手的话，A 向 B 提出挥手，发送第一个挥手请求，B 回复知道了。
之后 A 不再发送请求，但 B 可能还有数据要发送，所以 A 还可能继续接收。
B 发送数据完毕后，也要关闭请求，就发送第三次挥手，A 再返回给 B 说知道了。
然后进入 TIME_WAIT，大概等待 2MSL，确保报文都消失；如果超时，也能够进行重传。

**问：** TCP 和 UDP 的区别，以及使用场景是什么？

**答：** TCP 主要特点是可靠性，它是基于字节流的。
UDP 是不可靠的，包比较小，适合游戏或者语音通话。
可靠性要求比较高的场景一般使用 TCP。
TCP 有一系列机制保证可靠性，比如滑动窗口、ACK、序号等。

**问：** 简历里有 SSE，这个协议和 WebSocket 有什么区别？

**答：** WebSocket 是双向的，双方都能通信。
SSE 是单向推流。在我的场景里，它是镜像拉取，前端只需要知道镜像拉取进度，所以由后端返回事件进度给前端，不需要 WebSocket。

## 大文件上传与 NAS 使用场景

**问：** 上传大文件有什么优化吗？

**答：** 网盘那边不太清楚，可能会做分段上传或者断点续传。
相册和文档中心是根据路径判断和获取文件。比如用户上传很多文件到某个路径里，网盘可能会做上传操作；相册、文档中心、音乐这些应用会根据路径寻找文件。

**问：** 这些任务是主动触发，还是系统有任务？

**答：** 有定时，也有按钮能够触发。

**问：** 用户买了你们产品后，会有一个管理平台给他们用吗？具体使用场景是什么？

**答：** 对。家庭场景下，比如出去旅游拍照，可以直接上传到家里的 NAS。
公司场景下，可以把重要资料存在 NAS 里。在外面也能通过穿透查看或者保存。

**问：** 如果用户上传特别大的文件，需要分片上传，你会怎么设计后端接口？

**答：** 前端可以把文件拆成多个小文件，并发上传。
后端按长度分片接收，保存到缓存位置，并记录进度。
当进度满了以后，进行文件拼接。
还需要判断文件在传输过程中有没有损坏，比如前端传一个 hash 值，后端拼接完成后计算文件 hash，比对文件大小和 hash 是否一致。

**问：** 前端分了 N 片，都传到服务器后，用户又取消上传，这些缓存文件怎么处理？

**答：** 取消上传时，可能使用 Context 做后续取消，避免还在上传文件。
对于已经在缓存区的部分文件，我可能会保留 TTL，方便用户后续又点击上传。比如 TTL 设置为 5 分钟，后续通过后台任务删除。

**问：** 这种一般是单节点部署，还是会有集群？

**答：** 都是单节点，单体机器。

## Gin 请求流程、中间件与缓存

**问：** 一次请求到 Gin 框架里面的完整流程是什么？

**答：** 请求发送到后端后，会先到中间件。
中间件可能做鉴权、同源策略处理、缓存等。
接着到路由。路由里有根节点、普通节点、通配符节点，以及类似 `:id` 这种参数节点。它使用路由前缀树，所以性能会好一些。
然后到后端 handler 处理。handler 把具体逻辑交给 service，service 调用 model 以及 DAO 层方法。
得到结果后返回给 handler，再像进来一样返回给中间件。中间件可能记录日志或做其他操作，最后返回给前端。

**问：** Gin 中间件执行顺序怎么控制？项目里有哪些中间件，分别做什么？

**答：** 项目里有鉴权、跨源策略处理、缓存、限流。
鉴权主要是要求传 NAS token 或 admin 之类的内容。
跨源策略是加一些 `Access-Control-Allow-Origin` 相关请求头。
限流使用 rate，它是一个令牌桶，以固定速度往桶里加入令牌，请求取到令牌才能放行。
缓存是对一些查询数据做短时间缓存，比如 1 分钟内不用再去后面取。缓存的是请求和响应内容。

**问：** 缓存存在哪里？

**答：** 我们用的是 Go 里的 Ristretto，它是内存型缓存，支持并发读写。

**问：** 如果 Web 服务重启，缓存是不是就没了？

**答：** 对。因为缓存的是某个请求的请求内容和响应内容，主要是为了加速返回，所以丢了也无关紧要。

**问：** Gin 的 context 和标准库 context 有什么区别？

**答：** 标准库 context 可以在请求范围内传递 TraceID、鉴权 ID、取消信号和超时信号。
Gin 里的 context 做了什么优化，我没有学习过。（未答完整）

**问：** 服务里的定时任务通过什么形式实现？

**答：** 可能会起一个 goroutine。定时任务可能用 ticker 做，一个 for select 循环不断监听定时器信号。
没有信号就继续监听，有信号就执行操作。

## MySQL 索引、Explain 与事务

**问：** 索引了解过吗？什么应用场景会建索引，建索引时有哪些想法？

**答：** 了解过 MySQL 的索引。
一般读多写少，并且读是瓶颈时适合建索引。
第二种是 where 查询条件稳定出现。
第三种是排序和分组场景，有些情况下也能使用索引。
第四种是唯一索引，用来保证某些数据唯一性。
第五种是使用 EXPLAIN 命令看到可以通过加索引进行优化。

**问：** EXPLAIN 可以看 SQL 的执行过程，它大概会返回哪些字段和信息？

**答：** 会返回 type，比如 ref、const 这些表现比较好，range 是范围搜索，index 表示用到了索引但可能还是查了很多。

Extra 信息可以看到有没有 using temporary 或 filesort，表示使用了临时表或文件排序。

**问：** 项目里有用到事务吗？

**答：** 相册里应该会用到。

## Elasticsearch 到 Bleve、中文分词与资源配置

**问：** 从 ES 转到另外一个搜索引擎，当时是什么场景？

**答：** 当时做文档中心，需要解析文档，把内容放到数据库里，并进行关键词搜索。
ES 基于 Java，启动就需要 2GB 左右内存，在我们内存受限的 NAS 环境里不可接受。
后来对比了 Meilisearch、Typesense 和 Bleve。Meilisearch、Typesense 搜索速度比 Bleve 快，但构建索引速度比 Bleve 慢。
最后选择 Bleve，因为它是嵌入式搜索引擎，类似 SQLite，性能和内存更适合我们。

**问：** Bleve 搜索灵活度和 ES 比怎么样？比如分词、插件这些能力有吗？

**答：** 分词上我们做了自己的中文分词，用的是 CJDict。
对比过几个中文分词方案，比如 gse、jieba、sego。jieba 需要 cgo，为了省去编译麻烦没有选择。
gse 和 sego 的效果没有 CJDict 好，所以选择了 CJDict。

后续我发现 CJDict 分词还有问题：它是由词组成的字典，分词时会先从最长词开始匹配，再不断缩短一个字一个字匹配，这样内存和 CPU 占用都会增多。
所以后续我改成前缀树，节省查找时间。
但前缀树内存占用又比较高，所以又把它拍平成两个数组，一个记录边，一个记录节点，从而把内存和 CPU 占用降低了很多。

**问：** 最后这一套跑起来，最小应用配置是怎么样的？

**答：** 我们现在环境大概是 4G 内存、四核。
服务有很多，比如网盘、相册、音乐、影视、文档中心，以及底层的 storage manager、network 等。

**问：** 这些服务之间会相互调用吗？走什么方式？

**答：** 会相互调用。我们走的是 HTTP。

**问：** gRPC 了解过吗？

**答：** 我今天刚好看到，比如写一个 C++ 服务，好像可以用这种方法调用 C++ 里面的函数。
它类似于调用函数一样去调用其他服务接口。除此之外了解不多。（未答完整）

## 文件索引同步系统

**问：** 文件索引同步系统是用来做什么的？

**答：** 用来做真实文件和数据库中文件记录的同步。
比如一个路径下添加了 10 个文件，又删除了 2 个文件，同步时文件索引同步器会工作。
它会查询目录下有什么文件和目录，再处理这些文件，把目录加入队列，以 BFS 宽度优先遍历的方式遍历文件，达到数据库和真实文件数据的一致。

**问：** 一致性怎么保证？数据库里会存某个文件或哪些内容吗？

**答：** 比如 A 目录下面有 B、C 两个文件，数据库里就有 A 是文件夹，B、C 是文件，以及它们的具体路径和相关文件信息。

**问：** 如果用户像群晖一样把 NAS 目录挂载到 Linux 上，然后在挂载目录里移动或重命名文件，怎么触发写数据库？

**答：** 如果使用 Linux 命令进行文件操作，不会直接触发。
只有定时器，或者用户在我们界面上进行文件操作，才会触发同步。

**问：** 后端接收分片上传时，如何记录和继续传后面的分片？

**答：** 后端接收到某一片后，会记录片的例子，并告诉前端下一片需要什么。
比如文件分片上传，已经收到 2 片，后端继续记录已经收到 2，然后告诉前端需要 3 和 4。
如果又上传了 2，就丢弃。上传完毕后，还会检查文件是否损坏。
