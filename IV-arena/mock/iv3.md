## 1. Go

### 1. 代码变程序会经历哪些步骤

从 Go 源码到可执行程序，大体是：词法/语法分析、类型检查、中间代码生成、优化、汇编、链接，最后生成可执行文件。

面试可以这么说：

1. 编译器先解析 `.go` 源码，检查语法、类型、包依赖是否正确。
2. 然后生成中间表示，做一些逃逸分析、内联、死代码消除等优化。
3. 再把中间表示转成目标平台的汇编和机器码。
4. 最后链接 runtime、标准库、第三方包和自己的代码，生成最终可执行文件。

Go 的特点是编译速度快，最后产物通常是一个可直接运行的二进制，部署会比较简单。

### 2. 抢占调度

抢占调度是为了解决一个 Goroutine 长时间占用 CPU，导致其他 Goroutine 饥饿的问题。

Go 的抢占机制主要经历过两阶段：

1. Go 1.14 之前偏协作式抢占。
   编译器会在函数入口插入 `stack check`。如果 sysmon 发现某个 G 运行太久，比如超过 10ms，就把 `stackguard0` 标记成 `stackPreempt`。这个 G 下次函数调用时检查到标记，就主动调用 `runtime.goschedImpl` 让出 CPU。
   缺点是 `for {}` 这种没有函数调用的死循环不容易及时抢占。
2. Go 1.14 之后支持信号抢占。
   sysmon 发现某个 M 上的 G 跑太久，会给 M 发 `SIGURG` 信号。M 被操作系统中断后进入 runtime 的 `sighandler`，runtime 修改寄存器，把 `asyncPreempt` 插入到当前执行点，再切到 g0 栈执行调度逻辑，把当前 G 抢占下来。

一句话总结：协作式抢占靠函数调用点主动让出，信号抢占靠 runtime 给运行中的线程发信号强行插入调度点。

### 3. make 和 new 的区别

`new` 是分配内存，返回指针；`make` 是初始化内置引用类型，返回可直接使用的值。

具体区别：

1. `new(T)` 适用于所有类型，返回 `*T`，这块内存是零值。
2. `make` 只用于 `slice`、`map`、`channel`。
3. `make` 返回的是类型本身，不是指针，比如 `make([]int, 0, 10)` 返回 `[]int`。
4. `map` 和 `channel` 只 `new` 出来还不能直接用，通常要 `make` 初始化内部结构。


### 4. sync.Map

`sync.Map` 适合多读少写、写一次读多次，或者多个 Goroutine 操作不相交 key 的场景。

它的使用要点：

1. 用 `Store` 写、`Load` 读、`LoadOrStore` 做并发下的只初始化一次。
2. 不要在热路径频繁 `Range`，因为遍历全表成本较高，也可能影响其他读写。
3. 大 value 最好存指针，因为 key/value 是 `interface{}`，大对象直接存会有拷贝成本。
4. 它牺牲了类型安全和部分业务表达能力，所以不是所有并发 map 的默认选择。

和 `Mutex + map` 的选择：

1. 读写逻辑简单、需要强类型、需要复杂组合操作，用 `map + Mutex/RWMutex` 更直观。
2. key 独立、读多写少、缓存类场景，可以考虑 `sync.Map`。

### 5. 协程的使用场景

Goroutine 适合 I/O 密集、高并发、后台任务和并行计算。

常见场景：

1. HTTP/RPC 服务端每个请求一个 Goroutine。
2. 批量 IO，比如并发读多个文件、并发查多条 DB/Redis。
3. 生产者消费者模型。
4. 后台定时任务、探测、保活。
5. 带超时、取消的长耗时任务，比如配合 `context` 和 `select`。
6. 并行计算，把大任务拆成多个小任务，再汇总结果。

回答时可以强调：Goroutine 初始栈小，调度在用户态完成，切换成本比 OS 线程低，所以适合高并发，但不是无脑开，仍然要控制数量、超时和退出。

### 6. 如何接收用户输入的命令

如果是命令行程序，常见有三种方式：

1. 用 `os.Args` 获取启动参数，适合简单参数。
2. 用 `flag` 包解析命令行选项，适合 `-port=8080` 这种。
3. 用 `bufio.NewReader(os.Stdin)` 或 `fmt.Scanln` 从标准输入读取交互式命令。

如果要执行用户输入的系统命令，可以用 `os/exec`，但要注意安全：不要直接拼接 shell 字符串，最好把命令和参数拆开传，避免命令注入。

示例口述：

```go
reader := bufio.NewReader(os.Stdin)
line, _ := reader.ReadString('\n')
line = strings.TrimSpace(line)
```

## 2. 网络

### 1. 在多级路由器穿透的可能

多级路由器本质上是多层 NAT。能不能穿透取决于 NAT 类型。

常见思路：

1. 两端先向 STUN 服务器探测自己在公网侧的 IP 和端口。
2. 通过信令服务器交换双方的公网地址。
3. 双方同时向对方发包，在各自 NAT 映射表里留下记录。
4. 如果 NAT 类型比较友好，比如全锥型、受限型、端口受限型，就有机会直接打洞成功。
5. 如果遇到对称型 NAT，端口会随目标变化，STUN 成功率低，通常需要 TURN 中继。

多级 NAT 会让穿透难度增加，因为每一级都可能改端口、限制来源。如果不能直连，就走 TURN/中继，代价是服务端带宽和延迟更高，但连通性更好。

### 2. 有写过 socket 编程吗

可以按是否真实做过来回答。没写过底层 socket，也可以说用过 HTTP/RPC，本质底层也是 socket。

参考答案：

我没有大量手写过原生 socket，但了解基本模型。服务端一般是 `socket -> bind -> listen -> accept`，每 accept 一个连接后读取数据、解析协议、处理业务、再写回响应。客户端一般是 `socket -> connect -> write/read -> close`。

在 Go 里，通常用标准库 `net` 包封装：

```go
ln, _ := net.Listen("tcp", ":8080")
conn, _ := ln.Accept()
```

真正业务里我更多是通过 HTTP/Gin/RPC 这层使用网络能力，底层连接管理、超时、读写 buffer 由框架和标准库处理。

### 3. 网络轮询 IO 模型

Go 网络 IO 底层不是一个连接一个线程阻塞等待，而是 runtime 里有 netpoller。

可以这么说：

1. 网络 fd 会设置成非阻塞。
2. Goroutine 读写 socket，如果数据没准备好，不会一直占着 M 阻塞。
3. runtime 会把这个 fd 注册到操作系统的 IO 多路复用机制里，Linux 上主要是 epoll。
4. 当前 G park 掉，M 和 P 继续执行其他 G。
5. 当 fd 可读/可写时，netpoller 收到事件，把对应 G 标记为 runnable，重新放回调度队列。

这样 Go 可以用少量线程管理大量连接，避免每个连接都占一个 OS 线程。

### 4. 拥塞控制

TCP 拥塞控制是为了避免发送方把网络打爆。核心是维护拥塞窗口 `cwnd`。

主要阶段：

1. 慢启动：刚开始窗口指数增长，比如 1、2、4、8。
2. 拥塞避免：到达阈值 `ssthresh` 后，窗口线性增长。
3. 快重传/快恢复：如果收到多个重复 ACK，说明可能丢包但网络还没完全堵死，把阈值降低，继续拥塞避免。
4. 超时重传：如果直接超时，说明拥塞更严重，把窗口降到很低，重新慢启动。

可以补一句：TCP 可靠性靠序号、ACK、校验和、超时重传、快速重传；拥塞控制负责“别发太猛”。

## 3. 操作系统

### 1. 进程状态

常见进程状态可以按 Linux 口径说：

1. Running/Runnable：正在运行或在运行队列里等待 CPU。
2. Sleeping：等待 IO、锁、事件等，分可中断和不可中断。
3. Stopped：被信号暂停，比如调试时暂停。
4. Zombie：子进程已经退出，但父进程还没有回收退出状态。

面试可以补充：进程是资源分配的最小单位，线程是 CPU 调度的最小单位，协程是用户态轻量线程，切换开销更小，适合 I/O 密集高并发。

### 2. 用户组怎么分的

Linux 权限模型里，一个文件有三类身份：

1. Owner：所有者。
2. Group：所属组。
3. Others：其他用户。

每类身份都有 `rwx` 权限：

1. `r` 是读，数值 4。
2. `w` 是写，数值 2。
3. `x` 是执行，数值 1。

例如：

1. `755` 表示所有者 `rwx`，组和其他人 `r-x`。
2. `644` 表示所有者可读写，组和其他人只读。
3. `600` 常用于私钥文件，只有所有者可读写。

用户组的作用是把一批用户归到同一组，方便用组权限统一控制文件、目录、设备或服务的访问。

## 4. MySQL

### 1. 如果同步进磁盘了，就一定保证不丢失吗

不一定，要看“同步进磁盘”的是哪一层，以及是否真的完成了持久化。

InnoDB 里通常靠 redo log 做崩溃恢复。写事务时先写 redo log，这是 WAL 思想：顺序写日志比随机刷数据页更快。崩溃后从 checkpoint 之后的 redo 重放，恢复已提交修改，未提交的再靠 undo 回滚。

但是仍然有几个风险：

1. 只写到操作系统 page cache，不等于真正落到物理介质。
2. 磁盘或文件系统可能有缓存，断电时仍可能丢。
3. 数据页写一半可能出现 partial page write，所以 InnoDB 还有 doublewrite buffer 保护页完整性。
4. 参数也会影响可靠性，比如 redo/binlog 的 fsync 策略。

面试回答可以说：如果 redo log 已经按强一致策略 fsync 落盘，InnoDB 崩溃恢复通常能保证已提交事务不丢；但如果只是写入 page cache，或者磁盘本身故障，就不能绝对保证。

### 2. 使用索引的情况

适合建索引的情况：

1. `WHERE`、`JOIN` 条件稳定且高频出现。
2. 查询明显变慢，`EXPLAIN` 显示扫描行数多、type 较差。
3. 需要排序、分组，且数据量较大。
4. 有唯一性约束，比如手机号、订单号。
5. 读多写少，读性能是主要瓶颈。

使用索引时要注意：

1. B+ 树索引适合等值、范围查询，叶子节点有链表，范围查询友好。
2. 联合索引要遵循最左前缀原则。
3. 索引列参与函数/运算、隐式类型转换、`like '%xxx'`、`or` 中部分列没索引，都可能导致索引失效。
4. 回表次数太多、区分度太低、返回结果集太大，即使用了索引也可能慢。

排查时先用 `EXPLAIN` 看 `type`、`key`、`key_len`、`rows`、`extra`。

## 5. 排查

### 1. CPU 或者内存高怎么排查

先区分是 CPU 高还是内存涨。

CPU 高：

1. 先看机器指标：CPU、load、QPS、错误率、延迟是否同时变化。
2. 用 pprof 抓 CPU profile：`/debug/pprof/profile?seconds=30`。
3. 进入 pprof 后看 `top`、`top -cum` 找热点函数和入口链路。
4. 用 `list` 定位到具体源码行。
5. 常见原因是死循环、正则/JSON/加解密热点、日志过多、锁竞争、大量分配导致 GC 压力高。

内存高：

1. 抓 heap profile。
2. 重点看 `inuse_space` 和 `inuse_objects`，不要只看 `alloc_space`。
3. 如果 `inuse_space` 持续涨，怀疑存活对象没释放。
4. 常见原因是全局 map/缓存只加不删、slice 引用大数组、goroutine 泄漏、连接/文件没关闭、定时器/订阅没释放。
5. 可以抓两次 heap，用 `go tool pprof -base old new` 做对比。

一句话：CPU 看 `profile`，内存看 `heap`，goroutine 涨看 `goroutine`，锁竞争看 `mutex`，阻塞看 `block`。

### 2. 单体项目如果出问题了怎么办

单体项目出问题，先按影响面和链路排查，不要一上来就改代码。

我的思路：

1. 先看监控：CPU、内存、磁盘、网络、QPS、错误率、延迟。
2. 看日志：是否有 panic、错误码、慢接口、异常堆栈。
3. 确认影响范围：是所有接口出问题，还是某个模块、某类用户、某个版本。
4. 如果是性能问题，用 pprof 抓 CPU/heap/goroutine。
5. 如果是数据库问题，看慢查询、连接池、锁等待、索引是否命中。
6. 如果短时间无法修复，先降级、限流、重启故障模块或关闭非核心功能，保证主流程可用。
7. 最后复盘，把监控、日志和告警补齐。

### 3. 线上出问题怎么排查

线上问题我会按“止血、定位、修复、复盘”的顺序。

1. 止血：确认是否需要回滚、限流、降级、扩容、重启。
2. 定位：看监控趋势，找到出问题的时间点、版本、流量变化。
3. 日志：查错误日志、请求 ID、用户操作路径。
4. 资源：看 CPU、内存、磁盘、网络、goroutine、GC。
5. 依赖：看 DB、Redis、MQ、第三方接口是否异常。
6. 复现：如果可能，在测试环境用相同数据或流量复现。
7. 修复：小步修复，上线后持续观察指标。
8. 复盘：补测试、补告警、补文档，避免同类问题再发生。

### 4. 用户反馈 AI 效果不好怎么办

先不要直接换模型，要先确认“不好”具体是什么。

排查路径：

1. 收集样本：用户输入、AI 输出、期望输出、业务场景。
2. 判断问题类型：是答非所问、幻觉、格式不对、知识没召回、语气不符合，还是响应太慢。
3. 如果是上下文不够，补充 prompt、业务规则或知识库。
4. 如果是 RAG 问题，看召回内容是否相关，必要时优化切分、embedding、召回数量、重排。
5. 如果是输出格式问题，用更强的结构化约束，比如 JSON schema、模板、示例。
6. 如果是模型能力问题，再比较不同模型的效果、成本和延迟。
7. 对高风险场景增加人工审核或规则兜底。

可以结合你仓库 AI 规范回答：我会先验证 AI 结果，再反馈具体错误；如果上下文污染就清空，如果任务太大就拆模块，最后把易犯错误沉淀成 rules 或 skill。

## 6. AI

### 1. 如何规范 AI，比如加注释、文件不要太长

我会从输入规范、执行流程、验收规则三层约束 AI。

1. 输入规范：
   - 需求先说清楚背景、目标、非目标、边界条件。
   - 明确代码风格，比如注释只写关键逻辑，不写废话注释。
   - 明确文件大小，比如单文件过长要拆模块，但不要为了拆而拆。
2. 执行流程：
   - 大任务先让 AI 出 plan，我确认后再改。
   - 一次只做一个任务，避免上下文污染。
   - 用 `@` 或文件路径精确给上下文，减少无关内容。
3. 验收规则：
   - 要求 AI 自测、跑测试、说明改动点。
   - 对生成测试做 review，确认测试来自需求，而不是迎合实现。
   - 对复杂逻辑要求 code review，检查边界、错误处理、并发安全。
4. 规则沉淀：
   - 个人规则放 Cursor Rules 或 AGENTS.md。
   - 常见流程沉淀成 Skill，比如 brainstorm、TDD、code review、systematic debugging。

面试可以举例：比如我会要求“函数太长要拆”“文件超过一定规模先提出拆分方案”“注释解释为什么，不解释代码在做什么”“改完必须列出验证命令和风险点”。
